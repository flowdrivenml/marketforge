Market and ranking commands

Collect or browse current market data and manage immutable ranking snapshots. Workflow and prerequisites · Shared CLI behavior

Synopsis and arguments

mf markets sync

mf markets sync [-h] [--silent] [--testing | --production]
                                [--exchange {binance,bybit,okx,gateio,bitget}]
                                [--market {spot,linear,inverse}]
                                [--instrument INSTRUMENT]
Argument or option Parser contract
--silent Default false. Suppress collection progress; retain the final result and failures.
--testing, --production Mutually exclusive. Defaults to production.
--exchange Optional. Accepted binance, bybit, okx, gateio, bitget. Repeatable. Optional, repeatable exchange filter; omitted means every supported exchange.
--market Optional. Accepted spot, linear, inverse. Repeatable. Optional, repeatable market filter; derivatives include perpetuals and dated futures.
--instrument Optional. Exact native symbol, without changing market identity.

mf markets list

mf markets list [-h] [--base-asset BASE_ASSET]
                                [--quote-asset QUOTE_ASSET] [--match MATCH]
                                [--silent] [--testing | --production]
                                [--exchange {binance,bybit,okx,gateio,bitget}]
                                [--market {spot,linear,inverse}]
                                [--instrument INSTRUMENT] [--limit LIMIT]
                                [--sort {identity,turnover,freshness}]
Argument or option Parser contract
--base-asset Optional. Exact base asset, case-insensitive, e.g. ETH.
--quote-asset Optional. Exact instrument quote asset, case-insensitive; independent of ranking comparison currency.
--match Optional. Case-insensitive glob over the full native symbol: * matches zero or more characters, ? one. Quote it in the shell: --match 'ETH' or --match 'BTC'. Percent and underscore are literal.
--silent Default false. Suppress collection progress; retain the final result and failures.
--testing, --production Mutually exclusive. Defaults to production.
--exchange Optional. Accepted binance, bybit, okx, gateio, bitget. Repeatable. Optional, repeatable exchange filter; omitted means every supported exchange.
--market Optional. Accepted spot, linear, inverse. Repeatable. Optional, repeatable market filter; derivatives include perpetuals and dated futures.
--instrument Optional. Exact native symbol, without changing market identity.
--limit Default 50. Integer. Maximum stored instruments displayed (1..10000); no network access.
--sort Default identity. Accepted identity, turnover, freshness. Turnover sorts within native denomination groups, never across currencies.

Supported Exchanges

The current market-discovery workflow supports five cryptocurrency exchanges.

Exchange CLI identifier
Binance binance
Bybit bybit
OKX okx
Gate.io gateio
Bitget bitget

MarketForge supports several market categories within these exchanges.

Supported market categories

Category Description
spot Direct trading of supported assets.
linear Derivative markets using the applicable linear contract conventions.
inverse Derivative markets using the applicable inverse contract conventions.

These categories describe market structure.

They are not identical to instrument types.

For example, a linear market can contain perpetual contracts and dated futures.

Current collection coverage

Exchange Spot Linear Inverse
Binance Spot Perpetuals and dated futures Perpetuals and dated futures
Bybit Spot Perpetuals and dated futures Perpetuals and dated futures
OKX Spot Swaps and futures Swaps and futures
Gate.io Spot Perpetuals and delivery contracts Perpetuals only
Bitget Spot Perpetuals and delivery contracts when listed Not collected

When no filters are provided, MarketForge collects all 14 currently supported exchange/market scopes.

There are five exchanges and three market categories, but Bitget inverse is excluded.

What about options?

Options are not currently collected through this market-discovery workflow.

This does not mean MarketForge's broader catalogue has no concept of options.

It means the current automatic markets sync and markets refresh adapters do not include options collection.

What about expired futures?

The current exchange endpoints do not necessarily provide a complete history of every expired contract.

MarketForge retains known historical instrument records rather than assuming that an instrument has ceased to exist simply because it is absent from a current API response.

However, the current market API does not establish an exhaustive historical futures catalogue.

Additional historical evidence may be required for old contracts.

See Instrument Discovery.

Exchange-Specific Statistic Differences

The following examples illustrate why MarketForge preserves native measurement units.

Exchange / market Interpretation
Binance spot and linear Reported quote volume provides monetary turnover; base volume remains separate.
Binance inverse Uses native quote turnover when available, otherwise supported contract-value calculations.
Bybit spot and linear turnover24h is quote-denominated; volume24h is base-denominated.
Bybit inverse volume24h supplies quote turnover, while turnover24h supplies base quantity.
OKX spot volCcy24h and vol24h are interpreted according to the spot mapping.
OKX linear Base quantity multiplied by last price can provide an explicitly estimated turnover.
OKX inverse Contract count and verified quote face value can establish monetary turnover.
Gate.io Uses the supported spot or derivative turnover fields and retains native volume units.
Bitget Uses the applicable product-specific turnover fields, including Reality-market distinctions.

These mappings describe the current supported statistic interpretation.

They should not be generalized to every possible endpoint or instrument offered by a provider.

Why not normalize all statistics immediately?

Some conversions require additional evidence.

For example, turning contract volume into BTC quantity requires the appropriate contract specification.

Comparing USDC turnover with USDT turnover requires an explicit currency-conversion rule.

MarketForge therefore retains native measurements and their interpretation information.

Ranking policies perform the supported comparison using explicitly defined rules.

Open interest and funding

Open interest can be reported in:

Base units
Quote units
Contracts

depending on the provider and market.

Funding rates are optional and apply to relevant perpetual products.

MarketForge does not invent missing funding values for dated futures.

A missing statistic remains missing.

What Happens During a Partial Standard Update?

A standard update can contain several independent outcomes.

For example:

Statistics Refresh     Partial

Turnover Ranking       Published
Volume Ranking         Failed

This is an illustrative result.

Does one ranking failure undo the other?

No.

The standard policies are published independently.

A successful ranking publication can remain available even when another policy fails.

What happens to older snapshots?

Existing published snapshots are not rewritten.

A failed new build does not delete an older successful snapshot.

Why can the overall command return a failure code?

The update operation reports the completeness of the combined workflow.

If statistics refresh or ranking publication is incomplete, the overall result can be partial.

This may return a nonzero exit code even when one ranking was successfully published.

How should I inspect the result?

Look at:

  • Overall update status.
  • Statistics refresh result.
  • Failed exchange scopes.
  • Turnover publication outcome.
  • Volume publication outcome.
  • Returned snapshot UUIDs.

Do not assume a nonzero exit means every independent operation was rolled back.

Ranking Snapshot Maintenance

Snapshot deletion

MarketForge preserves published rankings because they represent historical observations evaluated under specific policies.

However, you may eventually want to remove snapshots.

For example:

  • You created a ranking while testing a policy.
  • A snapshot is no longer needed.
  • A temporary research ranking should be cleaned up.
  • You want to remove obsolete stored ranking evidence.

MarketForge provides an explicit deletion workflow.

Why is deletion guarded?

A ranking snapshot may be referenced by another managed operation.

For example, a historical processing job might record the ranking UUID used to select or order streams.

Deleting that snapshot could remove information needed to explain the processing decision.

MarketForge therefore checks concrete dependencies before allowing removal.

What can block deletion?

A snapshot may be protected by:

  • Registered historical jobs.
  • Dataset references.
  • Retained managed job artifacts.
  • Other supported concrete dependencies.

A referenced snapshot is not silently deleted.

Preview Snapshot Deletion

Before applying deletion, inspect the selected snapshots.

Preview one snapshot

Use its UUID:

mf markets rank delete SNAPSHOT_UUID --testing

Replace SNAPSHOT_UUID with an actual snapshot identifier.

Preview snapshots for one policy

For example:

mf markets rank delete activity --testing

This selects the published snapshots belonging to the policy named activity.

Preview all ranking snapshots

Use:

mf markets rank delete --all --testing

This selects all ranking snapshots, including drafts.

Important: the selectors mean different things

Selector What it selects
Snapshot UUID Exactly one matching snapshot, including a draft.
Policy name All published snapshots belonging to that policy.
--all All snapshots, including drafts.

Exactly one selector is required.

Does preview delete anything?

No.

Without --apply, the command performs a nondeleting preview.

The result reports the selected snapshots and whether they are eligible for deletion.

Why inspect exact UUIDs?

A policy name can refer to several published snapshots.

If you only intend to remove one, use its UUID.

This avoids accidentally selecting an entire policy's snapshot history.

Apply Snapshot Deletion

Once you have reviewed the selection, you can explicitly apply deletion.

For one snapshot:

mf markets rank delete SNAPSHOT_UUID \
    --testing \
    --apply

For all published snapshots of a policy:

mf markets rank delete activity \
    --testing \
    --apply

Does MarketForge ask for confirmation?

The current ranking deletion command does not use an interactive confirmation prompt.

The explicit --apply option authorizes the operation.

Review the selected targets carefully before using it.

Does apply use a saved preview file?

No.

Unlike managed raw-storage deletion, ranking snapshot deletion does not require a saved preview artifact.

The command resolves the selected snapshots again when applying deletion.

Why does this matter?

Suppose you preview all snapshots of a policy.

Then another process publishes a new snapshot before you run --apply.

When you apply deletion by policy name, the selection is resolved again.

That new snapshot may now be included.

How can I avoid this?

Use exact snapshot UUIDs when you want to remove specific known entries.

For example:

mf markets rank delete SNAPSHOT_UUID --testing --apply

This is more precise than deleting by policy name or using --all.

What happens if some snapshots are protected?

A mixed selection may contain eligible and blocked snapshots.

MarketForge can delete eligible snapshots while retaining protected ones.

The result reports the blocked entries.

The overall command may return a nonzero exit code.

Does deletion remove the policy TOML?

No.

Deleting ranking snapshots does not delete the corresponding policy file.

It also does not remove:

  • The instrument catalogue.
  • Retained market observations.
  • Raw acquisition files.
  • Registered datasets.
  • Historical archive records.

The operation targets the selected ranking snapshots and their owned ranking evidence.

Command Reference

Market Command Options

Option Meaning
--testing Select the guarded testing database.
--exchange Restrict to supported exchange codes; repeatable.
--market Restrict to spot, linear, or inverse categories; repeatable.
--instrument Select an exact native symbol.
--base-asset Exact case-insensitive base-asset filter for list.
--quote-asset Exact case-insensitive quote-asset filter for list.
--match Case-insensitive full-symbol glob for list.
--sort Select list ordering by identity, turnover, or freshness.
--limit Maximum number of stored list results.

Important scope differences

sync and refresh use exchange, market, and exact-symbol selection.

They do not support the same asset and glob filters as list.

markets list does not provide an --instrument-type option.

Use the returned instrument type information and supported identity filters.

Collection limits

The parser accepts hidden --limit and --sort options on some collection commands.

However, these do not limit or sort the actual network collection.

Do not rely on them for controlling the number of instruments collected.

Ranking Limits and Options

Every ranking subcommand accepts the supported --silent and --limit options.

The default limit is:

50

The accepted range is:

1–10000

However, the limit has different meanings for different commands.

Command Meaning of limit
rank list Number of returned snapshot entries.
rank show Maximum human-displayed included or excluded rows.
rank build Does not narrow the evaluated universe.
rank update Does not narrow the statistics refresh or policy evaluation.
rank delete Does not narrow the deletion target selection.

Important: --all depends on the command

For rank show:

--all

removes human row limits.

For rank delete:

--all

selects all ranking snapshots, including drafts.

These are different operations.

Do not confuse them.

JSON Output

The global JSON option is available for market and ranking operations.

For example:

mf --json markets list --testing

mf --json markets show bybit.spot.BTCUSDT --testing

mf --json markets rank list --testing

mf --json markets rank show activity --testing

Why use JSON?

JSON can be useful for:

  • Inspecting full instrument metadata.
  • Saving market collection results.
  • Examining observation timestamps.
  • Extracting ranking UUIDs.
  • Inspecting conversion evidence.
  • Comparing published snapshots.
  • Automating diagnostics.

Important details

Global --json must appear before markets.

For market lists, the configured result limit still applies.

For ranking inspection, JSON returns all matching entries regardless of the human show limit.

Decimal quantities are represented as strings where required to preserve precision.

Missing values remain null rather than being converted into zero.

Global application options

The relevant global options include:

--json
--project-root PATH
--config PATH

These appear before the main command.

For example:

mf --config ./workspace-settings.toml \
    --json markets list --testing

The global --config selects application settings.

It does not select a ranking policy.

Ranking policies are selected by their managed names.

Which Commands Change State?

The market commands have different effects.

Command Contacts exchanges Writes database records
markets sync Yes Yes
markets refresh Yes Yes
markets list No No
markets show No No
markets rank new No Creates a local TOML file
markets rank validate No No
markets rank build No Yes
markets rank list No No
markets rank show No No
markets rank update Yes Yes
markets rank delete preview No No
markets rank delete --apply No Yes

The table describes the main state-changing behavior.

For example, rank build reads retained observations and publishes a new snapshot without contacting providers.

Meanwhile, rank update includes a new global statistics refresh.

Common Questions

Exit Codes

The market and ranking commands use the common MarketForge CLI exit behavior.

Code Meaning
0 The operation or inspection completed successfully.
1 Partial collection, incomplete standard update, or blocked snapshot deletion.
2 Command, configuration, database, identity, validation, or setup error handled by the CLI.
130 Handled cancellation or interruption.

Important: partial results may contain successful work

For example, a statistics refresh can fail on one scope while successfully updating another.

Similarly, a standard ranking update can publish one policy while another fails.

Inspect the structured result before retrying.

JSON errors

When global JSON output is enabled, handled CLI errors are reported through stderr.

Partial collection results can be returned as structured JSON on stdout with a nonzero exit code.

For scripts, preserve the command's exit status when piping output.
