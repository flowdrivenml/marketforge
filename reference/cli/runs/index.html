Execution history and retained evidence

New historical operations use <operation>-<uuid> logical run IDs. The five operations are acquisition, normalize, merge, convert, and pipeline. Acquisition mapping and downloading both use acquisition-. Their action records which activity ran.

PostgreSQL stores bounded execution metadata, timestamps, ordered attempts and typed resource references. Complete reports, events, submitted jobs and pinned Engine evidence remain on disk. A logical run under data/runs/ can point to separate Engine preparation and execution directories. Engine job, publication, registered file and attempt identifiers each retain their own meaning.

Browse the selected registry

Production is the default. Add --testing to select the testing registry. Filter runs list by --operation, --action, --status, --recipe, --start or --end. Time bounds are timezone-aware ISO 8601 start-time bounds. The start is inclusive and the end is exclusive. Filters are exact. Use --limit and --offset to page the newest runs. Exchange and instrument filters require indexed associations and are not exposed by this interface.

mf --json runs list --testing --operation acquisition --action map --limit 20 | cpout
mf runs show RUN_ID --testing | cpout
mf runs report RUN_ID --testing | cpout
mf runs logs RUN_ID --testing --limit 50 | cpout

Replace RUN_ID with a recorded identifier. List and indexed show use schema version 2. Show includes a duration when the run has finished, and bounded attempt, resource and child-run lists. Report and logs use the retained sources and their original contracts. Running records have unknown liveness when no terminal evidence has been reconciled.

Attempts and recovery

Forge verifies the selected database UUID and purpose before starting expensive work. A single invocation that prepares and executes retains one logical run with references to both preparation and execution evidence. A pipeline resume keeps the original run ID and starts a new attempt. The pipeline report retains stage order and outcomes. Independently retained acquisition executions link to their owning pipeline. HTTP retries and individual Engine tasks do not create logical attempts.

The searchable state distinguishes prepared, completed, partial, failed, blocked, interrupted, cancelled, stopped, and unknown. An in-flight attempt is running. The registry retains the operation's domain status and available execution, verification and registration outcomes separately. A committed publication can still have a pending or failed registration.

PostgreSQL and the filesystem commit separately. Forge writes a bounded outcome beneath the attempt directory before finalizing the index. If index finalization fails, the outcome remains available for reconciliation. This replays only index updates and leaves processing and registration evidence intact.

Historical evidence and index maintenance

Anonymous UUIDs and recognized historical Engine execution directory IDs work for explicit inspection. Historical IDs and original report bytes are preserved. Legacy indexing requires evidence of the operation, timestamps and the exact selected registry UUID and environment. Missing, ambiguous or conflicting evidence stays available for local review.

mf runs index-legacy --dry-run --testing --limit 50 | cpout
mf runs index-legacy --apply --testing --limit 50 | cpout
mf runs reconcile --dry-run --testing --limit 50 | cpout
mf runs reconcile --apply --testing --limit 50 | cpout

Review the preview and use --offset for subsequent pages. Reconciliation checks the workspace and registry identity, attempt and retained outcome before applying metadata. A running row without a retained outcome needs review. Unindexed local evidence is reported and needs explicit review before assignment. Neither command launches processing or rewrites historical reports. Production indexing is an explicit administrative action.

See the pipeline reference for resume and the publication reference for retained Engine evidence.
