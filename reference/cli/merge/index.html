Merge commands

Prepare and run a pinned merge job and register committed output. Workflow and prerequisites · Shared CLI behavior

Depth Layout Compatibility

Order-book data has additional requirements.

A depth event may depend on a previously reconstructed book state.

For example:

Snapshot
   |
   v
Update
   |
   v
Update
   |
   v
Update

If the merger starts reading from the middle without the required initialization state, the resulting book history may not be interpretable.

Why does a snapshot matter?

A snapshot establishes a known book state.

Later incremental updates modify that state.

Without the required snapshot or another supported initialization boundary, the updates may not provide enough information to reconstruct the book.

Why does a depth publication have auxiliary files?

Normalized depth publications may contain information such as:

Artifact Purpose
Event index Connects observations to canonical row ranges.
Boundary information Records initialization and source-boundary states.
Reconstruction segments Identifies portions of the history and their ordering requirements.
Source information Preserves the relevant input and contribution details.

The merger may need this information to preserve valid depth interpretation.

What is segmented depth?

Some depth publications contain multiple reconstruction segments.

For example, a recording may require a new snapshot after a discontinuity or source transition.

These segments cannot always be treated as one uninterrupted book history.

The merge ordering must preserve the relevant segment dependencies.

This is one reason prepared merges containing segmented depth may use causal timeline ordering.

Can I merge only one depth Parquet part?

Not necessarily.

A particular depth layout may require all its primary parts or additional publication-level information.

Selecting one file without its dependencies can make reconstruction impossible.

The merger checks these requirements before processing.

Does merging repair missing order-book updates?

No.

A merge does not create missing source events or prove continuity that the source did not establish.

If a normalized depth publication contains independently initialized histories, the merged output must preserve the relevant limitations rather than present them as one verified continuous book.

What Does Merge Preparation Verify?

Before processing, Forge and Rust perform checks against the selected files and publication evidence.

These checks can include:

  • Active registered file identities.
  • File paths and checksums.
  • Owning publication manifests.
  • Publication fingerprints.
  • Stream identities.
  • Content types.
  • Instrument namespace.
  • Requested time interval.
  • Supported physical layout.
  • Required depth reconstruction information.
  • Prepared job compatibility.

These checks help prevent an invalid selection from reaching execution.

What preparation does not prove

Preparation cannot establish that every historical market event exists in the source data.

For example, two files may overlap the requested interval and pass all applicable structural checks while still containing an independently unverified historical gap.

Merge compatibility and historical completeness are different questions.

The first determines whether the files can be processed together.

The second concerns whether the source data contains the full intended market history.

Publications and Inspection

How Forge Verifies a Merge

After Rust Engine commits the merge publication, Forge verifies the result before registering it.

Why is verification necessary?

A file existing on disk does not automatically mean it is a completed, valid merge output.

For example, an interrupted process may leave incomplete artifacts.

Similarly, a publication may be inconsistent with its recorded job or source checksums.

Forge therefore checks the committed output and its retained evidence.

What does verification establish?

The supported verification includes the committed physical Parquet output and relevant byte fingerprints.

It also checks the applicable publication and input evidence required by the merge registration contract.

Does verification rerun normalization?

No.

The merge verification works with the selected normalized publications and their recorded evidence.

It does not decode the original exchange archives again.

Does verification prove historical completeness?

No.

It verifies the applicable merge output.

It does not independently establish that the source exchanges supplied every market event during the requested interval.

What Happens When a Merge Fails?

A merge can fail at different stages.

For example:

  • File selection may be ambiguous.
  • A required input may be missing.
  • Rust may reject an unsupported publication layout.
  • Processing may fail because of resource limits.
  • Publication verification may fail.
  • PostgreSQL registration may fail after Engine commits the output.

These problems require different responses.

Preparation failure

A preparation failure means Forge could not create an eligible executable job.

Inspect the preparation report.

The issue may involve missing inputs, source provenance, publication selection, or compatibility.

Execution failure

An execution failure occurs while Engine is processing the selected files.

Inspect the execution report and Rust diagnostics.

A failed job may leave temporary or incomplete output artifacts.

Do not treat them as completed datasets.

Registration failure

A registration failure can occur after Engine successfully commits a valid publication.

The output may remain available for registration-only recovery.

This is an important distinction because the merge itself may not need to be repeated.

Find Merge Execution Reports

MarketForge retains reports for managed merge operations.

A merge execution report is stored under the configured run directory.

For example:

data/runs/merge-execute-*/execution-result.json

The actual path is reported by the operation.

What does the report contain?

The report distinguishes the relevant stages:

Stage What it describes
Execution Whether Rust Engine completed the merge.
Verification Whether the committed output passed the required checks.
Registration Whether the verified output was recorded in PostgreSQL.

It can also include output file locations, registered IDs, and failure information.

Why inspect the report before retrying?

Imagine that Engine successfully processed a large dataset but PostgreSQL registration failed.

Rerunning the entire merge may be unnecessary.

The report helps determine whether the committed publication can be recovered directly.

Similarly, if Engine rejected the input layout before processing, retrying without changing the selection is unlikely to help.

Use the reported failed stage to decide what needs to be corrected.

Recover a Completed Merge Without Rerunning

MarketForge separates Engine publication from PostgreSQL registration.

This means a merge can successfully publish its files even when a later database operation fails.

For example, a power interruption could occur after the output was committed but before its registration completed.

Why is registration-only recovery useful?

Merging large datasets can require substantial processing time.

If the output already exists and remains valid, repeating the full operation may waste resources.

MarketForge therefore provides a command for verifying and registering an existing committed merge publication.

Recover from an execution intent

Use:

mf merge register \
    data/runs/MERGE_EXECUTION_ID/execution-intent.json \
    --testing

Replace the placeholder with the actual execution directory reported by your run.

The intent records information about the submitted operation and its output.

MarketForge uses that information to locate and verify eligible committed files.

Recover from a publication directory

You can also provide a committed publication directory:

mf merge register \
    data/datasets/merged/ENGINE_JOB_ID \
    --testing

Replace ENGINE_JOB_ID with the actual output identity.

Recover from a manifest

A committed manifest can also be used:

mf merge register \
    /absolute/path/to/merged-publication/manifest.json \
    --testing

Recover one primary file

If you need to register one specific committed primary file, provide its path:

mf merge register /absolute/path/to/part-000000.parquet --testing

Does recovery rerun the merger?

No.

Registration-only recovery verifies and registers existing committed output.

It does not repeat the Rust merge workload.

What does recovery verify?

The operation rechecks the relevant committed output and required input lineage.

This prevents an incomplete or inconsistent publication from being registered merely because its files exist.

What if the publication is already registered?

An identical registration retry can reuse the existing database identity.

Conflicting evidence or identity information is not silently overwritten.

What if the merge never completed publication?

Registration-only recovery cannot convert an incomplete staging directory into a valid committed publication.

If Engine failed before committing the output, investigate the failure and prepare or execute new work as appropriate.

Command Reference

Recipe Names and Paths

Managed merge recipes are stored under:

data/.config/workflows/data_engineering/merge/

You can use their names directly:

mf merge validate manual_merge

Or:

mf merge run manual_merge --testing

You can also use an explicit TOML path for supported recipe actions other than new.

For example:

mf merge validate ./my-merge.toml

And:

mf merge run ./my-merge.toml --testing

Why does new require a managed name?

The new command creates a recipe inside the managed merge configuration library.

It is not an arbitrary-file writing command.

This keeps managed recipe creation predictable.

What about prepared JSON?

A prepared JSON job can be submitted directly through run.

It must satisfy the current job contract, including its concrete selected-file and stream information.

For example, prepared file entries must contain the applicable stream_id, stream_rank, and content_type information required by the current contract.

They must also match active registered inputs and their pinned publications.

Older prepared submissions may need to be regenerated.

For ordinary workflows, use mf merge prepare to create the current job format.

JSON Output

Merge commands support global JSON output.

For example:

mf --json merge validate manual_merge

mf --json merge prepare manual_merge --testing

mf --json merge run manual_merge --testing

The global --json option must appear before merge.

Why use JSON?

JSON output is useful when:

  • Inspecting detailed preparation results.
  • Saving merge execution reports.
  • Working with scripts.
  • Extracting registered file IDs.
  • Investigating failures.
  • Building repeatable research workflows.

Save a merge result

For example:

mf --json merge run manual_merge --testing > merge-result.json

This saves the structured result to a local file.

Do not combine global JSON output with the interactive TUI.

Which Commands Change State?

The merge commands have different effects.

Command Uses PostgreSQL Executes merging Writes files
merge new NAME No No Creates a recipe
merge new --from-normalize Yes No Creates a recipe and may retain selection information
merge validate No No No normal processing output
merge prepare Yes No Writes a prepared job and report
merge run Yes Yes Writes a merge publication and reports
merge register Yes No Can update registration records and recovery evidence

The table describes the main effects of each operation.

For example, prepare can read and verify selected input files without executing the merge.

Similarly, register performs verification and database registration but does not rerun the Rust merger.
