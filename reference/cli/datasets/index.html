JSON results

List and find return {datasets, interval_semantics, limit, offset} in JSON mode. datasets is an array, including when no files match. limit and offset are integers. interval_semantics is descriptive text. Each array member has a numeric registry file id, numeric publication_id, text engine_dataset_id and engine_job_id, and an instrument_namespace. File fields are storage_root, storage_path, storage_format, primary_file, manifest_path, manifest_sha256, and file_sha256. operation, data_type, status and summary describe the record. Inclusive observed endpoints use nullable integer start_timestamp_ns/ end_timestamp_ns and nullable text first_observed_utc/ last_observed_utc.

Action Top-level keys
Show file, publication
Streams id, scope, streams
Schema id, columns
Head id, rows
Lineage id, file_contributions, publication_selection
Verify a primary file id, scope, status, file_sha256, entire_publication_verified

Decimal values in head JSON use strings, including nested trade and depth values. Timestamp columns remain integers. Use a parser that preserves integers beyond the IEEE-754 exact range. Read the display-independent rules in identity and provenance.

JSON dataset inspection

Most dataset commands support global JSON output.

For example:

mf --json datasets list --testing

Or:

mf --json datasets show FILE_ID --testing

The global --json option must appear before datasets.

Why use JSON?

JSON is useful when:

  • Writing scripts.
  • Extracting file IDs.
  • Inspecting complete metadata.
  • Comparing processing results.
  • Building automation around registered datasets.
  • Working with other command-line tools.

JSON previews

For datasets head, JSON output includes all stored columns by default unless you explicitly select columns.

For example:

mf --json datasets head FILE_ID \
    --testing \
    --limit 5

Exact decimal values are serialized as strings.

This helps avoid losing decimal precision through ordinary JSON number handling.

Does --wide change JSON output?

The wide and compact display modes primarily control terminal presentation.

JSON retains the underlying response structure.

For dataset previews, use --column when you want to request a smaller set of physical fields.

Does JSON ignore pagination?

No.

List, find, and coverage still use their requested file limits and offsets.

JSON does not automatically return the entire registered dataset collection.

Understanding Dataset Coverage

File-Level Contributions vs. Publication-Level Selection

This is an important distinction.

A publication may select many input files, but one individual output part may contain records from only some of them.

Example

Suppose a normalization publication uses three raw archives:

Archive A
Archive B
Archive C

The Engine produces two primary files:

Publication
    |
    +-- File 1
    |      |
    |      +-- Archive A
    |      +-- Archive B
    |
    +-- File 2
           |
           +-- Archive B
           +-- Archive C

The publication-level input selection is:

A, B, C

However, File 1 does not necessarily contain data from Archive C.

Likewise, File 2 does not necessarily contain data from Archive A.

Why not attach every source to every file?

That would incorrectly suggest that every selected source contributed records to every output part.

MarketForge therefore distinguishes:

File-level contributions

The source inputs that are proven to have contributed to the selected primary file.

Publication-level selection

The complete set of inputs selected for the overall processing publication.

Expand the publication selection

Use:

mf datasets lineage FILE_ID \
    --testing \
    --publication

This includes the shared publication-level selection information.

Why is this useful for merging?

A merged publication may select several normalized files.

However, attributing a particular merged output part to one input file can require additional evidence.

For example, if a represented stream was selected from exactly one primary input file, the contribution may be established precisely.

If several files from the same parent publication were selected, the available evidence may only support attribution to the publication as a whole.

MarketForge preserves this distinction.

It does not invent exact file-level contributions when the evidence is insufficient.

Does --publication change the dataset?

No.

It expands the lineage inspection.

The physical Parquet file remains unchanged.

Verification vs. Data Integrity

Dataset verification and processing integrity are different.

File verification

File verification answers:

"Does this file still match the registered bytes?"

For example, a SHA-256 comparison can establish that the current Parquet file matches its recorded fingerprint.

Processing integrity

Processing integrity answers different questions.

For example:

  • Were source records parsed successfully?
  • Were required order-book snapshots available?
  • Were sequence gaps detected?
  • Were timestamp regressions observed?
  • Were the applicable integrity policies satisfied?
  • Was the publication accepted with clean or degraded integrity?

These checks occur during the relevant Engine processing and publication workflow.

Historical completeness

Historical completeness is another separate question:

"Does this dataset contain every market event that should exist for the intended period?"

Neither a matching checksum nor a successful processing result automatically proves this.

A source provider may have supplied incomplete historical data.

Three different guarantees

Question Relevant evidence
Are the registered file bytes intact? Dataset verification.
Did processing satisfy its required integrity rules? Engine reports and publication evidence.
Is the historical market record complete? Source coverage evidence and applicable continuity guarantees.

These distinctions matter when using historical data for backtesting and quantitative research.

For example, a file can be perfectly intact while containing a gap inherited from the original source.

Registered Metadata Maintenance

How MarketForge Displays Datasets

The dataset CLI uses MarketForge's existing terminal theme.

It is designed to present large amounts of dataset information in a compact, readable way.

For example, the dataset browser groups files by publication and instrument rather than displaying an unstructured list of filesystem paths.

Compact and wide views

The default list uses compact file names.

For example:

mf datasets list --testing

Use:

mf datasets list --testing --wide

to display additional path information.

Precise timestamps

The default terminal view displays timestamps to whole seconds.

Use:

mf datasets list --testing --precise

for nanosecond precision.

Terminal width

The display adapts to the available terminal width.

Wide terminals may show tables.

Narrower terminals may use stacked records.

This changes the presentation, not the underlying dataset metadata.

Multi-stream labels

A file representing several instruments may be displayed under a mixed-membership heading.

This helps distinguish it from files containing only one logical stream.

Each physical file retains its registered file ID.

Tokyo Night colors

MarketForge uses its Tokyo Night-inspired terminal palette.

You can control terminal colors through the application configuration:

data/.config/forge/marketforge.toml

For example:

[presentation]
mode = "progress"
color = "auto"

Available color modes

Mode Behavior
auto Detect supported terminal color capabilities.
always Enable colors for supported interactive output.
never Disable colors.

Automatic mode respects the NO_COLOR environment variable.

Plain output

If you prefer a plain terminal view:

[presentation]
color = "never"

Redirected dataset output and global JSON use plain output.

Does silent mode hide dataset inspection?

No.

The presentation setting:

mode = "silent"

suppresses supported progress displays.

It does not prevent requested dataset inspection results from being shown.

Does color affect dataset contents?

No.

Terminal colors only change presentation.

They do not change Parquet data, timestamp precision, dataset registration, or processing integrity.

Working with Datasets in Python

Browsing Commands

List

mf datasets list --testing [FILTERS] [--wide] [--precise]

Displays registered primary files.

Find

mf datasets find --testing [FILTERS]

Searches registered files by market and content information.

Coverage

mf datasets coverage --testing [FILTERS]

Summarizes observed envelopes for the current filtered file page.

Supported filters

Option Meaning
--operation normalize|merge Processing operation.
--data-type TYPE Trade, depth, or combined content.
--status STATUS Stored file status.
--publication ID Engine publication identity.
--exchange VENUE Registered exchange code.
--instrument VALUE Exact symbol or canonical instrument ID.
--instrument-type TYPE Registered instrument type.
--market-category CATEGORY Registered market category.
--start TIMESTAMP Inclusive search start.
--end TIMESTAMP Exclusive search end.
--limit N Number of file rows per page.
--offset N Starting position within the matching file rows.

The file-page limit defaults to 50 and accepts values from 1 to 1000.

The offset defaults to zero.

File Inspection Commands

Show file details

mf datasets show FILE_ID --testing

Reads the selected file's registered metadata.

Show streams

mf datasets streams FILE_ID --testing

Displays registered stream memberships and observed intervals.

Show lineage

mf datasets lineage FILE_ID --testing
    [--publication]
    [--checksums]
    [--limit N]

Displays proven file-level contributions and the relevant publication selection.

Show schema

mf datasets schema FILE_ID --testing

Reads the selected physical Parquet schema.

Preview records

mf datasets head FILE_ID --testing
    [--limit N]
    [--column NAME ...]
    [--wide]
    [--precise]

Displays a bounded preview.

The default row limit is 10.

The accepted range is 1–1000.

Verify a file

mf datasets verify FILE_ID --testing

Checks the selected primary file and its shared manifest against registered fingerprints.

Refresh metadata

mf datasets refresh-summary FILE_ID --testing

Updates the file's derived metadata in PostgreSQL.

Migrate existing registrations

Preview legacy migration

mf datasets migrate-registration --all --testing --dry-run

Verifies eligible legacy registrations and reports the proposed file-level records without applying the registration changes.

Apply legacy migration

mf datasets migrate-registration --all --testing

Migrates eligible legacy normalization aggregates into file-level registrations.

Legacy merge aggregates currently require separate supported evidence and are reported as conflicts.

JSON Output

The global JSON option can be used with dataset inspection commands.

For example:

mf --json datasets list --testing

mf --json datasets find \
    --testing \
    --exchange bybit \
    --instrument BTCUSDT

mf --json datasets show FILE_ID --testing

mf --json datasets lineage FILE_ID --testing

Why use JSON?

JSON is useful for automated inspection and downstream processing.

For example, you can extract:

  • File IDs.
  • Physical paths.
  • Publication identities.
  • Stream memberships.
  • Observed timestamps.
  • Row counts.
  • Lineage information.

Important details

Global --json must appear before datasets.

File pagination still applies.

For head, JSON includes all stored columns by default unless an explicit column selection is supplied.

Exact decimal values are represented as strings.

Common Questions

Common Dataset Inspection Problems

No datasets are listed

Possible cause: No matching files are registered in the selected testing database.

Inspect the relevant normalization or merge result.

Check that publication registration completed.

Also verify that you are using the intended testing database.

A file ID cannot be found

Possible cause: The ID is incorrect, belongs to another registry, or refers to a legacy registration.

List the current files:

mf datasets list --testing

If the ID is from an older aggregate registration, inspect its migration status.

The dataset belongs to an unexpected publication

Possible cause: The file ID belongs to another processing run.

Inspect:

mf datasets show FILE_ID --testing

Review the Engine publication identity and source lineage.

A market search returns a mixed file

Possible cause: The selected physical Parquet file contains several registered streams.

Inspect:

mf datasets streams FILE_ID --testing

The file can legitimately represent multiple instruments.

A search by time returns a file without matching rows

Possible cause: The file's observed envelope overlaps the requested interval, but no actual event occurs inside that narrower range.

Use physical record inspection or the Python API to perform exact row-level filtering.

Coverage seems incomplete

Possible cause: The selected page does not contain every matching file.

Check the pagination information.

Continue through the remaining file pages when a complete registry-level inventory is required.

The schema command fails

Possible cause: PyArrow is missing, the file is unavailable, or the Parquet schema cannot be read.

Confirm the research dependency is installed.

Also inspect the registered file path and verification status.

A preview does not show a required column

Possible cause: The compact view hides that field.

Use:

mf datasets head FILE_ID \
    --testing \
    --wide \
    --limit 5

Or inspect the schema and request the column explicitly.

A requested column does not exist

Possible cause: The selected publication uses a different physical schema.

Inspect:

mf datasets schema FILE_ID --testing

Use the actual stored field names.

Previewed timestamps lack precision

Possible cause: The default terminal view shows whole seconds.

Use:

mf datasets head FILE_ID \
    --testing \
    --precise

Unexpected row counts

Possible cause: You are comparing different kinds of records.

For example, depth observations can produce multiple canonical price-level rows.

Inspect the publication information and relevant processing metrics.

Do not assume the number of physical Parquet rows equals the number of original source messages.

Lineage does not list every publication input as a file contribution

Possible cause: Not every selected publication input has proven contribution to the individual primary file.

Use:

mf datasets lineage FILE_ID \
    --testing \
    --publication

Review file-level contributions separately from the full publication selection.

Verification reports a checksum mismatch

Possible cause: The file or manifest differs from its registered fingerprint.

Inspect the physical file and reported path.

Do not overwrite the stored checksum to conceal the mismatch.

Investigate the original publication and recovery options.

Verification reports a missing file

Possible cause: The registered path no longer contains the expected primary file.

Check the configured data root and publication location.

Do not manually recreate an empty file under the expected name.

Refreshing a summary does not repair a damaged file

Possible cause: refresh-summary updates metadata but does not verify or rewrite the Parquet contents.

Use datasets verify for the supported physical integrity check.

Registration migration reports conflicts

Possible cause: A legacy publication cannot be verified or lacks the required supported migration evidence.

Inspect the migration report.

Legacy merge aggregates are not automatically converted through the current normalization-focused migration path.

Registration recovery fails

Possible cause: The committed publication, manifest, or required provenance does not satisfy the applicable verification contract.

Inspect the registration error.

Recovery cannot turn incomplete staging files into valid published datasets.
