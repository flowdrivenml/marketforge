Prepare and execute normalization batches and recover verified registrations. Workflow and prerequisites · Shared CLI behavior

Profile commands

Use mf normalize profiles to manage normalization definitions. The deprecated mf acquisition profiles alias still accepts the same commands and keeps JSON stdout unchanged.

A profile declares how the Engine reads and interprets a physical source format. Acquisition recipes choose sources, instruments, and time windows. Installed profiles live under data/.config/engine/normalize/profiles/, in trades/ or depth/. The profile authoring guide explains the workflow and the generated field index covers individual parameters.

Command under mf normalize profiles Output and effects
list [--type TYPE] [--exchange VENUE] [--instrument-type KIND] [--market-category CATEGORY] Compact read-only inventory. Filters combine. The Format column describes the inner record format. JSON retains complete installed definitions, paths, and fingerprints.
inspect PROFILE_ID Opens original TOML in read-only Neovim without user startup options, swap, or persistent editor state. Requires a terminal. Global --json returns the existing structural inspection and opens no editor.
show PROFILE_ID Read-only report of configured settings, mappings, path, and SHA-256. JSON uses the same result as JSON inspect.
schema [--type trades\|depth] [--field FIELD | --section SECTION] Schema-2 authoring reference. Field and section selectors are mutually exclusive. Works without an installed profile or Engine. JSON returns the versioned metadata and the selected fields.
guide trades\|depth Step-by-step source inspection, mapping, validation and installation. JSON exposes the same steps.
new PROFILE_ID Creates a commented draft using the ID’s content suffix. Leaves the required format code unset. JSON reports the path and pending validation.
edit PROFILE_ID Copies installed bytes into data/.config/engine/normalize/profile-drafts/ and opens the copy. Requires a terminal and refuses an existing draft. Checks TOML and namespace after the editor exits. The draft stays available if a check fails.
validate PROFILE_ID or validate --file PATH Stages a catalogue and runs Rust semantic compilation. JSON reports the existing structural and Engine verification result. An unsupported interpretation or failing validation returns an error.
add PROFILE_ID --from PATH or register PROFILE_ID --from PATH Verifies the venue in the selected registry, validates the candidate with Rust, and uses the conflict-safe publication path. A compatible existing fingerprint may be reused. A different interpretation under the same ID is rejected.
sample --file PATH [--member NAME] [--header | --no-header] Read-only bounded inspection of raw input for authoring. Returns structured sample evidence.

Use global --json before normalize. Draft editing has no JSON mode. The schema uses <name> for source keys and [] for array items. A concrete source key can be looked up as fields.timestamp.encoding, or use TOML-style quotes for a dotted key.

mf normalize profiles list --exchange bybit --type trades | cpout
mf normalize profiles inspect bybit.spot.spot.trades
mf normalize profiles show bybit.spot.spot.trades | cpout
mf normalize profiles schema --section normalization | cpout
mf normalize profiles schema --field fields.timestamp.encoding | cpout
mf --json normalize profiles schema --field source.format | cpout
mf normalize profiles validate bybit.spot.spot.trades | cpout

Schema browsing, list, inspect, show, edit, and sample use local data. Validation runs the managed normalizer without processing raw archives. Only add and register need the registry.

Use the Terminal Processing Interface

Normalization can involve large workloads.

During processing, you may want to monitor task progress and inspect the active operation.

MarketForge provides a terminal interface for supported Engine execution.

Run with the TUI

Use:

mf normalize run my-normalization --testing --tui

The --tui option starts the supported interactive terminal interface during processing.

This is useful when working directly in a terminal.

What does the TUI show?

Depending on the active workload and processing phase, the interface can display information about:

  • Processing jobs.
  • Source tasks.
  • Current execution phases.
  • Progress and throughput.
  • Resource activity.
  • Completed and failed work.

For example, a normalization run may spend time reading raw archives, reconstructing depth, reconciling streams, or finalizing Parquet output.

These phases do not necessarily advance at the same rate.

Why does progress sometimes appear to pause?

Historical normalization is not just a single file-reading loop.

After reading source records, Engine may still need to reconcile streams, perform integrity checks, finalize Parquet files, or validate publication information.

Therefore, a source-record counter may stop increasing while other processing work continues.

Use the available task and phase information rather than assuming that unchanged input counts mean the process has stopped.

Can I use TUI and JSON together?

No.

The interactive terminal interface and global JSON output are incompatible.

For example, do not use:

mf --json normalize run my-normalization --testing --tui

Choose either interactive monitoring or machine-readable output.

When should I use JSON?

Use JSON when you want to save the final result for scripts or later inspection.

For example:

mf --json normalize run my-normalization --testing > normalize-result.json

This avoids combining an interactive terminal display with structured output.

Inspect the Normalization Result

After a successful run, inspect the execution result before beginning research.

The result provides information about execution, verification, and registration.

What should you look for?

Confirm that:

  • The requested jobs completed as expected.
  • The relevant publications were committed.
  • Output verification succeeded.
  • The expected primary files were registered.
  • The trade and depth content types are present.
  • The integrity results are acceptable.
  • The output paths and file IDs were reported.

Save the execution result

For example:

mf --json normalize run \
    docs/content/examples/catalogue/normalization.toml \
    --testing > synthetic-result.json

This saves the structured result.

You can inspect it using a JSON viewer or a script.

Inspect registered datasets

For the synthetic AAPL example:

mf datasets list \
    --testing \
    --exchange example_exchange \
    --instrument AAPL

This searches the registered dataset collection.

The returned file IDs can be used with the dataset inspection commands.

Show one registered file

Use:

mf datasets show FILE_ID --testing

Replace FILE_ID with an actual ID returned by MarketForge.

This displays information about the selected file and its publication.

Inspect the schema

Run:

mf datasets schema FILE_ID --testing

This shows the physical columns and types of the selected Parquet file.

Preview records

Run:

mf datasets head FILE_ID --testing --limit 10 --precise

This displays a small sample of records.

The --precise option shows timestamps with their supported nanosecond precision.

For the synthetic trade example, check that the resulting record represents:

Instrument: AAPL
Side:       Buy
Price:      233.62
Quantity:   10 shares
Event time: 2024-10-28 14:30:00 UTC

Verify a registered file

You can also run:

mf datasets verify FILE_ID --testing

This checks the selected primary file and shared manifest against their registered checksums.

It does not independently reprocess every source record or verify the entire publication's historical completeness.

Inspect source lineage

Use:

mf datasets lineage FILE_ID --testing

This helps identify the source inputs associated with the registered file.

See Dataset Inspection for the complete inspection workflow.

Understand Processing and Integrity Results

A normalization result contains more than one kind of status.

This is important because successfully executing a processing job does not mean every data-quality question has been resolved.

Execution status

Execution status describes whether the requested processing jobs ran successfully.

For example, a job may complete, fail, or be interrupted.

Verification status

Verification describes whether the committed output satisfies the applicable publication and provenance checks.

A processing job should not be treated as a verified publication merely because some Parquet files exist.

Registration status

Registration describes whether the verified output was successfully recorded in PostgreSQL.

For example, Engine may commit a valid publication while a later database problem prevents registration.

The files may remain available for registration-only recovery.

Integrity status

Integrity describes the relevant data-quality and processing checks.

For example, a source may contain a tolerated anomaly that causes the resulting integrity status to be degraded.

This is different from the execution result.

Why are these statuses separate?

Consider three examples.

Example A: Clean processing

Execution:      Complete
Verification:   Verified
Registration:   Registered
Integrity:      Clean

This is an illustrative successful combination.

Example B: Completed processing with degraded integrity

Execution:      Complete
Verification:   Verified
Registration:   Registered
Integrity:      Degraded

This illustrates why a completed run and a clean integrity result are not necessarily the same thing. Such an outcome depends on the active processing policies and whether the output remains publishable.

Example C: Publication completed, registration failed

Engine output:  Committed
Verification:   Available
Registration:   Failed

In this situation, the committed output may be recoverable without rerunning the original processing.

These examples illustrate the different responsibilities. Inspect the actual run report for the precise fields and outcomes of your operation.

What Happens When Some Jobs Fail?

A normalization recipe can contain multiple jobs.

For example, you might request trades and depth together.

It is possible for one job to complete while another fails.

MarketForge provides an explicit option for handling certain partial outcomes.

Strict mode

By default, normalization uses strict execution behavior.

For example:

mf normalize run my-normalization --testing

If a submitted job fails, the strict workflow returns a nonzero result.

This prevents an incomplete multi-job operation from being presented as an ordinary complete success.

Allow partial completion

For supported cases, you can use:

mf normalize run my-normalization \
    --testing \
    --allow-partial

The flag allows MarketForge to register independently verified outputs from a partially successful operation when the applicable conditions are satisfied.

For example, imagine a run containing:

Trades Job     Complete
Depth Job      Failed

If the trade publication was committed and independently verified, the partial workflow may register that verified output while reporting the failed depth job as omitted.

What does --allow-partial actually change?

It changes the managed workflow's handling of certain multi-job execution outcomes.

It does not change Rust's normalization logic.

It also does not relax the Engine's data-integrity rules.

What does it not allow?

--allow-partial does not turn every failure into success.

In particular, it does not authorize:

  • Publishing an output that failed integrity requirements.
  • Registering unverified files.
  • Accepting an interrupted operation as complete.
  • Reporting success when no verified outputs remain.
  • Ignoring failed PostgreSQL registration.
  • Changing source ordering or reconstruction semantics.

Integrity failures, interruptions, zero verified outputs, and registration failures remain unsuccessful in both modes.

When should you use it?

Partial completion can be useful when independent jobs process different content types or selections.

For example, you may want to retain a verified trade publication even though an unrelated depth job failed.

However, always inspect the omissions before using the output.

A partial run means the original request was not fully completed.

Do not treat a partially registered result as equivalent to the complete requested dataset.

Find Execution Reports

MarketForge retains information about normalization executions.

These reports are useful when a run fails or when you need to understand how a dataset was produced.

Where are reports stored?

Normalization execution artifacts are stored under the configured data root's run directory.

For the default data root, an execution result may appear at:

data/runs/NORMALIZE_EXECUTION_ID/execution-result.json

Replace NORMALIZE_EXECUTION_ID with the actual execution identifier.

Do not construct the directory name from an assumption about the run.

Use the path reported by MarketForge.

What does the execution report contain?

The structured result describes relevant information about:

  • Submitted jobs.
  • Execution outcomes.
  • Verification results.
  • Registration results.
  • Output paths.
  • Registered file IDs.
  • Failed or omitted work.
  • Applicable processing diagnostics.

Why keep execution reports?

Suppose normalization fails after processing several files.

The report helps distinguish a failure during source decoding from a later publication or database-registration problem.

Those problems require different recovery actions.

For example:

Source-processing failure

You may need to inspect the input profile, data, or processing policies.

Registration failure

If Engine already committed a valid publication, you may be able to register it without rerunning normalization.

Should I inspect the report before retrying?

Yes.

A failed command can leave useful evidence and, in some cases, valid committed files.

Blindly rerunning the entire workload may be unnecessary.

Inspect the execution result and identify the failed stage first.

Recover a Completed Publication Without Rerunning

Normalization involves two separate final stages.

First, Engine commits the output files.

Then Forge verifies and registers them in PostgreSQL.

A problem can occur between these stages.

For example, the database connection might fail after Engine has already committed a valid dataset.

Why is registration-only recovery useful?

Imagine processing a large order-book dataset.

The normalization itself completes successfully, but PostgreSQL becomes unavailable during registration.

The committed files may already exist and be valid.

Rerunning the entire normalization could waste substantial time and resources.

MarketForge therefore provides a way to verify and register an existing committed publication without executing the processing job again.

Recover using an execution intent

The execution workflow retains an intent describing the frozen submitted work and output destinations.

Use:

mf normalize register \
    data/runs/NORMALIZE_EXECUTION_ID/execution-intent.json \
    --testing

Replace the execution ID with the actual value from your run.

MarketForge uses the retained intent to locate and verify the relevant committed outputs.

It then attempts to register the eligible files.

Recover using a publication manifest

You can also provide the path to an existing committed manifest:

mf normalize register \
    /absolute/path/to/committed-publication/manifest.json \
    --testing

MarketForge verifies the publication before registration.

Register a specific primary file

If you only need to recover one registered file, you can provide its primary Parquet path.

For example:

mf normalize register /absolute/path/to/part-000000.parquet --testing

This targets the selected primary file.

Register an entire publication

When you provide the publication directory or its manifest, the supported registration workflow considers the publication's primary files.

This is useful when an entire committed publication needs registration.

Does recovery rerun Engine?

No.

Registration-only recovery does not repeat the normalization workload.

It checks the existing committed output and its retained evidence.

What if the publication is already registered?

Registration can reuse an existing database ID when the relevant identity and evidence match.

If the submitted output conflicts with existing registered identity, content, or lineage, registration fails rather than silently overwriting the record.

What if the output is incomplete?

An incomplete staging directory is not automatically a valid publication.

Registration-only recovery requires the applicable committed output and verification evidence.

If Engine never completed publication, you may need to investigate or rerun the failed processing work.

Recovery is for verifiable committed outputs, not a way to bypass failed normalization or publication checks.

Understanding Recipe Names and Paths

Managed normalization recipes live under:

data/.config/workflows/data_engineering/normalization/

For example:

data/.config/workflows/data_engineering/normalization/my-normalization.toml

You can refer to a managed recipe by name:

mf normalize run my-normalization --testing

You can also use an explicit file path:

mf normalize run \
    docs/content/examples/catalogue/normalization.toml \
    --testing

Why use a path containing a directory?

MarketForge distinguishes named managed recipes from explicit paths.

For an explicit recipe file, use a path with a directory component.

This avoids confusing a relative filename with a managed recipe name.

What about older recipes?

MarketForge retains support for the documented legacy normalization request format under:

historical/normalization_jobs/

Existing legacy requests may remain readable through the supported compatibility path.

For new workflows, prefer the current managed normalization recipes.

Ambiguous references

Be careful when a local file and managed recipe name could refer to different inputs.

For run, an ambiguous reference can produce an error rather than silently selecting one.

Use an explicit path when you intend to submit a specific local file.

How does run distinguish JSON from TOML?

The managed command distinguishes prepared JSON content from recipe TOML.

A prepared JSON batch is submitted for execution.

A TOML recipe is resolved through preparation before execution.

Do not rename a file merely to force the command to interpret it as another contract type.

Important Normalization Options

--testing

Selects the guarded testing database.

This is required for the applicable managed preparation, execution, and registration operations.

It is not a dry-run option.

--dry-run

Available for the supported preparation and execution-planning commands.

It resolves and reports the plan without launching the workload or publishing the prepared batch and report.

It does not prevent explicit recipe creation when combined with --from-acquisition.

--from-acquisition SOURCE

Creates a normalization recipe using an existing acquisition selection.

This helps reuse the same exchange, instrument, data type, and historical interval.

The resulting normalization recipe remains a separate managed configuration.

--tui

Enables the supported interactive terminal processing interface.

It cannot be combined with global --json.

--allow-partial

Permits registration of independently verified outputs from certain partially successful multi-job executions.

It does not change Engine integrity policies or make unverified files publishable.

Global --json

Requests machine-readable results.

For example:

mf --json normalize prepare my-normalization --testing

Or:

mf --json normalize run my-normalization --testing

Global --json belongs before normalize.

Interactive recipe creation may still open an editor even when JSON output is requested for the final result.

Common Questions

Common Normalization Problems

The normalization recipe is invalid

Possible cause: The TOML file is malformed or contains unsupported fields or values.

Validate it:

mf normalize validate my-normalization

Correct the reported configuration problem before preparation.

Preparation finds no matching archives

Possible cause: The requested raw data is not registered or the selection does not match its recorded identity.

Check the acquisition recipe, registered source key, instrument, data type, and historical interval.

Inspect raw storage:

mf storage list --testing

If the files are missing, acquire or register them first.

Preparation reports missing historical specifications

Possible cause: The registered instrument does not have applicable specification evidence for the selected input period.

Inspect the catalogue:

mf catalog specs show \
    example_exchange.equity.equity.AAPL \
    --testing

Use the actual instrument reference for your request.

Resolve the historical applicability problem before executing.

Do not substitute an arbitrary current observation for verified historical rules.

The required profile is missing

Possible cause: The source format profile was not installed.

Inspect the installed profiles:

mf normalize profiles list

Validate and install the appropriate definition.

The Rust normalizer is missing

Possible cause: The managed Engine has not been built or its installation is invalid.

Inspect:

mf engine status

If necessary, rebuild:

mf engine build normalize

Preparation reports an unsupported batch

Possible cause: The prepared contract contains unsupported fields, source semantics, or version combinations.

Inspect the preparation result and Rust validation diagnostics.

Check that Forge and Engine are compatible.

Do not manually remove required prepared fields to bypass validation.

The submitted batch differs from preparation

Possible cause: The submitted request or frozen execution information no longer matches the retained preparation evidence.

Inspect the reported fingerprint mismatch.

If the underlying files, profiles, or intended request have changed, prepare a new batch.

Normalization reports invalid records

Possible cause: Source records do not satisfy the declared format or processing requirements.

For example:

  • Malformed numeric fields.
  • Incorrect timestamp encoding.
  • Unsupported side values.
  • Invalid quantities.
  • Missing required fields.

Inspect representative source records and the installed profile.

Correct the interpretation or source problem rather than blindly relaxing validation.

Trade quantities appear incorrect

Possible cause: The source quantity denomination or contract specifications are wrong.

Check the registered instrument specifications and profile quantity encoding.

For derivatives, confirm the required contract value and asset denomination.

Do not assume every exchange records quantities in base-asset units.

Trade sides are reversed

Possible cause: The profile incorrectly interprets the source-side convention.

For example, a field describing the resting order may not represent the aggressor side directly.

Consult the provider's format documentation and inspect the profile mapping.

Timestamps are incorrect

Possible cause: The source timestamp encoding does not match the profile.

Check whether the source uses seconds, milliseconds, microseconds, nanoseconds, or formatted timestamps.

Verify the resulting canonical event timestamps against known source values.

Depth reconstruction fails

Possible cause: The source is missing required snapshots, contains invalid updates, or violates its declared ordering or sequence semantics.

Inspect the depth profile and Engine diagnostics.

Do not repair stateful depth data by arbitrarily sorting updates by timestamp.

The processing job runs out of resources

Possible cause: The workload exceeds its configured memory, scratch-storage, or other resource limits.

Inspect the reported resource failure.

Review the runtime configuration and selected workload.

Resource limits should be changed deliberately, not merely increased without understanding the cause.

Engine writes files but the run fails

Possible cause: The operation failed during processing, final integrity evaluation, publication verification, or registration.

Inspect the execution report.

Do not assume that the existence of Parquet files means the publication is complete.

PostgreSQL registration fails after Engine completes

Possible cause: The output was committed, but the registry transaction did not complete.

Inspect the execution result and committed publication evidence.

If the output remains verifiable, use registration-only recovery.

A partial run contains fewer datasets than expected

Possible cause: One or more requested jobs failed and the workflow registered only the independently verified outputs.

Inspect the reported omissions.

Do not assume the partial result contains every requested instrument or data type.

Dataset inspection shows unexpected row counts

Possible cause: You are comparing different processing counters.

For example, depth source observations and canonical level rows are not equivalent.

Inspect the relevant processing metrics, event indexes, and publication information.

For trade data, also investigate rejected or suppressed records where applicable.

The output interval differs from the requested interval

Possible cause: The selected source archives extend beyond the requested recipe interval.

Inspect the raw archive bounds, selected inputs, and observed output timestamps.

Do not assume the request interval is an automatic row-level trimming operation.
