Normalization reads data/.config/engine/normalize.toml. See merge and conversion settings and pipeline inheritance for the other runtime documents. The ordering and reconciliation concepts explain choice of policy. This reference defines settings, limits, validation and retained evidence.

Runtime schema

Runtime schema version

The current runtime configuration uses:

schema_version = 1

The schema version is required.

The supported value is:

1

Why does the runtime have its own version?

The runtime configuration is independent of the other MarketForge schemas.

For example:

Artifact Schema version
Historical runtime 1
Normalization recipe 1
Normalization profile 2
Prepared normalization batch 4

These numbers do not need to match.

Each represents a different contract.

Are unknown fields allowed?

No.

The runtime loader rejects unknown configuration fields.

This includes unknown keys inside supported nested sections.

For example, inventing:

ignore_all_errors = true

does not activate an undocumented processing policy.

Why is strict validation useful?

A misspelled setting should not silently be ignored.

For example:

memory_budget_byte

should not be accepted as though it meant:

memory_budget_bytes

Strict validation makes unsupported or incorrect configuration visible.

Resource Management

Why Resource Budgets Matter

Historical market data can be extremely large.

For example, a month of detailed order-book recordings may contain millions of source messages.

A single source message can also contain hundreds or thousands of price levels.

Processing requires resources for:

  • Reading archives.
  • Decompressing files.
  • Parsing records.
  • Reconstructing order books.
  • Reconciling overlapping sources.
  • Sorting eligible trade events.
  • Writing Parquet.
  • Collecting integrity evidence.

Without resource limits, a workload could consume excessive memory or temporary storage.

MarketForge therefore uses explicit resource budgets.

Worker Count

The worker setting is:

[resources]
workers = 1

What does it control?

It controls the configured processing concurrency.

For example, a workload containing several independent source tasks may be eligible for parallel execution.

Does more workers always mean faster processing?

No.

Additional workers can increase:

  • Memory requirements.
  • Concurrent source decoding.
  • File-handle usage.
  • Parquet writer activity.
  • Scratch-storage demand.

A workload may become limited by storage throughput or resource admission rather than CPU capacity.

What happens if workers is zero?

The runtime rejects the configuration.

The worker count must be positive.

How should I choose the value?

Consider the available CPU cores, memory, and storage throughput.

For example, a large workstation may be able to support more workers than a small virtual machine.

However, the appropriate value depends on the actual workload.

Do not assume one worker corresponds directly to one CPU core or one entire source file.

Memory Budget

The memory budget is configured in bytes:

memory_budget_bytes = 1073741824

This example represents 1 GiB.

What does the budget limit?

MarketForge estimates memory requirements before admitting relevant processing work.

The budget constrains the accounted memory required by the workload.

What is included in memory accounting?

The Engine's estimate includes:

Component Why it needs memory
Source decoding Buffers for reading and decompressing input
Record parsing Temporary decoded records
Order-book reconstruction Active market state
Parquet writer Row groups and output buffers
Reconciliation Comparing and combining source histories
Source metadata Instrument and source information
Integrity observations Counters and bounded diagnostics
Failure reporting Information retained when work fails
Finalization Output completion and publication operations

What is memory admission?

Before beginning relevant work, Engine estimates the resource reservation needed for the operation.

If the reservation exceeds the configured budget, the operation can be rejected.

For example:

Required reservation: 2 GiB
Configured budget:    1 GiB

The workload cannot be admitted under that budget.

Does memory admission measure process RSS?

No.

The budget is based on accounted estimates and reservations.

It is not identical to the operating system's measured resident memory.

Does successful admission guarantee no out-of-memory condition?

No.

A successful resource estimate does not guarantee that the operating system will never encounter memory pressure.

Other processes and runtime allocations still affect system memory.

Why not set an extremely large budget?

A large budget does not create additional physical RAM.

It can allow more work to be admitted while increasing memory pressure.

Choose a budget appropriate to the machine and workload.

Scratch Storage

Some processing operations require temporary disk storage.

For example, large source reconciliation or bounded external sorting may need to spill intermediate data to disk.

The runtime uses:

scratch_path = "data/.work/normalize"
scratch_budget_bytes = 1073741824

Scratch path

The scratch path identifies the temporary processing location.

Relative paths are resolved against the MarketForge project root.

Scratch budget

The scratch budget limits the applicable accounted temporary storage.

Why use scratch storage?

Some processing tasks would require excessive memory if every intermediate record were retained in RAM.

Scratch files allow suitable intermediate data to be stored temporarily.

Is scratch the same as published output?

No.

Scratch files are internal working artifacts.

The committed dataset is published separately.

Can I use another disk?

The runtime accepts an absolute scratch path.

For example:

scratch_path = "/mnt/fast-storage/marketforge-scratch"

Use a directory backed by suitable storage.

What if the path already exists as a file?

The runtime rejects it.

An existing scratch path must be a directory.

Does the loader create the directory automatically?

The configuration loader does not create the directory merely by validating the path.

Actual processing components manage their applicable scratch operations.

Can scratch exhaustion cause processing failure?

Yes.

A workload may fail when the required temporary storage exceeds its configured budget.

This is a resource failure, not proof that the original market events were invalid.

Parquet Row-Group Target

The Parquet configuration contains:

[resources.parquet]
row_group_target_bytes = 67108864

The example represents 64 MiB.

What is a Parquet row group?

Parquet organizes columnar data into row groups.

These are physical units of data within a Parquet file.

Why does row-group size matter?

It can affect:

  • Writer buffering.
  • File layout.
  • Compression.
  • Analytical read performance.
  • Memory requirements.

Does a row group represent one historical interval?

No.

A row group is a storage structure.

It does not automatically correspond to one hour, day, instrument, or exchange.

Does changing row-group size change market events?

The setting controls physical output organization.

It does not independently redefine the source interpretation or economic meaning of records.

Parquet File Target

The file target is:

file_target_bytes = 268435456

This example represents 256 MiB.

Why configure file size?

A large historical publication may need several physical Parquet parts.

The writer can rotate output according to its supported file-target behavior.

For example:

Publication
    |
    +-- part-000000.parquet
    +-- part-000001.parquet
    +-- part-000002.parquet

Is the target an exact file-size guarantee?

No.

It is a writer target.

Actual file sizes depend on record structure, compression, row groups, and finalization behavior.

Why does file rotation matter?

Individual physical files can later be registered and inspected separately.

For example, MarketForge's dataset registry records file-level:

  • Row counts.
  • Sizes.
  • Observed intervals.
  • Stream memberships.
  • Source contributions.

Does the target change the publication identity?

No.

One publication may contain several primary files.

Their physical partitioning does not turn them into unrelated processing jobs.

Resource Validation

The runtime validates resource settings before admitting work.

For example:

  • Worker counts must be positive.
  • Memory budgets must be positive.
  • Scratch budgets must be positive.
  • Parquet targets must satisfy their supported constraints.
  • Normalization limits must be valid.
  • The scratch path must be suitable.

Merge and conversion alignment

For the supported merge and conversion runtime adapters, certain byte budgets must be exact multiples of one MiB.

These include the applicable:

memory_budget_bytes
row_group_target_bytes
file_target_bytes

Why require whole MiB values?

The merge/conversion runtime adapter converts these settings into integer MiB parameters.

A value that is not divisible by 1,048,576 cannot be represented exactly in that interface.

Example

Valid:

memory_budget_bytes = 1073741824

Invalid for the whole-MiB requirement:

memory_budget_bytes = 1000000000

The second value is not an exact whole number of MiB.

Does every Engine operation use identical resource validation?

No.

The shared runtime has operation-specific checks.

For example, a configuration may satisfy general normalization loading while a merge-specific partition or compression setting is rejected by the merge runtime loader.

Processing policies

Normalization validates resource, safety, diagnostic, integrity, reconciliation and timestamp settings. See ordering and reconciliation for the interpretation of loss and overlap.

Normalization safety limits

Why Are Safety Limits Separate from Budgets?

A memory budget controls total accounted resource usage.

However, an individual malformed or unexpectedly large source record can still create problems.

For example:

  • A CSV row may be hundreds of megabytes long.
  • A book observation may contain an unexpectedly large number of levels.
  • An XLSX workbook may contain excessive XML content.
  • A source may produce too many diagnostic entries.

MarketForge therefore uses additional normalization safety limits.

These are configured under:

[resources.normalization_limits]

Why are they useful?

They provide bounds for individual source and processing structures.

For example, the record-size limit prevents a decoder from accepting an arbitrarily large source record.

The depth-level limit constrains the supported book-level representation.

These are different from the global memory budget.

No.

Record-Size Limit

The record-size limit is:

record_bytes = 1048576

What does it protect?

It prevents the applicable source decoder from admitting records larger than the configured bound.

Why might a record be large?

For example, a JSONL depth message can contain many price levels.

Some sources may place a substantial snapshot into one line.

What happens when the limit is exceeded?

The relevant operation reports a resource-limit error.

Does increasing the limit make the record valid?

Not necessarily.

A larger limit permits more bytes to be considered.

It does not correct malformed JSON, invalid quantities, or unsupported source structure.

Depth-Level Limit

The depth-level limit is:

depth_levels = 25000

What does it control?

It constrains the number of applicable order-book levels accepted by the supported normalization scope.

Why is this useful?

Some source messages may contain unexpectedly deep snapshots.

A very large book can require substantial memory.

Does this setting truncate the output?

Do not treat it as a general truncation policy.

It is a processing safety limit.

Exceeding it can cause a failure.

Can I increase it?

Yes, within the supported resource-validation constraints.

However, the additional book state may increase memory requirements.

Workbook Limits

XLSX processing has additional limits.

These include:

workbook_bytes = 8388608
workbook_xml_bytes = 16777216
workbook_rows = 25000

Why are XLSX limits necessary?

Spreadsheet workbooks can contain compressed XML structures.

Their decoded content can be considerably larger than the original file.

What do the limits control?

Limit Purpose
workbook_bytes Workbook memory allowance
workbook_xml_bytes Decoded workbook XML allowance
workbook_rows Supported row-count bound

Does increasing these limits enable arbitrary XLSX formats?

No.

The source decoder must still support the workbook layout.

For example, the current profile schema supports a specific single-worksheet depth format.

Resource changes cannot implement unsupported workbook layouts.

Detailed Metrics and Reconciliation Limits

Two additional limits are:

metric_entries = 4096
reconciliation_bytes = 67108864

Metric entries

This limits the relevant detailed integrity observation storage.

Reconciliation bytes

This constrains memory used by the applicable reconciliation operations.

Why bound diagnostic information?

A source containing millions of anomalous records could otherwise generate an enormous amount of per-event diagnostic data.

MarketForge retains aggregate information and bounded samples rather than requiring unlimited diagnostic memory.

Does a small metric limit suppress every integrity violation?

No.

The Engine still tracks the applicable integrity counts and policy outcomes.

The limit constrains detailed observation retention.

It does not mean additional violations are accepted or forgotten.

Diagnostic Collection

What Are Runtime Diagnostics?

Runtime diagnostics provide information about processing behavior.

For example, they can help investigate:

  • Processing phases.
  • Resource utilization.
  • Workload progress.
  • Performance bottlenecks.
  • Runtime failures.

The configuration supports:

[diagnostics]
mode = "disabled"
interval_ms = 1000

Diagnostic modes

Mode Meaning
disabled Diagnostic collection disabled by default
basic Basic supported diagnostics
detailed More detailed supported diagnostics

Does detailed mode change normalized data?

The diagnostic mode controls the supported collection of runtime observations.

It does not independently change source-event semantics.

Does disabled mean no errors are reported?

No.

Required processing failures and integrity results are separate from optional diagnostic collection.

Disabling diagnostics does not disable integrity validation.

Diagnostic Sampling Interval

The setting is:

interval_ms = 1000

This represents 1,000 milliseconds.

Accepted range

The current runtime validator accepts:

100–60000 milliseconds

Why configure an interval?

Diagnostics may collect periodic runtime measurements.

A shorter interval can provide more frequent observations.

A longer interval reduces the frequency of those observations.

Does a smaller interval always improve debugging?

Not necessarily.

More frequent diagnostics can increase observation activity and retained detail.

Choose a suitable interval for the problem being investigated.

Integrity Evaluation

Why Does MarketForge Need Integrity Policies?

Historical market data can contain invalid or inconsistent records.

For example:

Trade:
Price = -100

may violate the applicable trade validity requirements.

Another source might contain an order-book update whose sequence number unexpectedly jumps.

A third may contain a malformed JSON record.

These problems are not all equivalent.

MarketForge tracks them using defined integrity categories.

What does an integrity policy decide?

It determines whether the relevant violations:

  • Cause immediate failure.
  • Can be tolerated as degraded integrity.
  • Exceed configured count or rate thresholds.
  • Exceed hourly or daily limits.

What does it not decide?

Integrity policy does not independently authorize:

  • Invalid source interpretation.
  • Unsafe order-book reconstruction.
  • Unbounded event loss.
  • Missing required metadata.
  • Resource-budget violations.
  • Invalid publication output.

Those checks remain separate.

Global Integrity Switch

The integrity policy contains:

[integrity_policy]
enabled = true

This is the ordinary enabled state.

What happens when enabled?

The configured integrity actions and thresholds are evaluated.

What if disabled?

The schema also accepts:

[integrity_policy]
enabled = false

Disabling integrity evaluation bypasses its policy decisions.

However, violations can still be recorded and the resulting integrity status can remain degraded.

Important limitation

Disabling integrity evaluation does not disable:

  • Archive validation.
  • Source parsing requirements.
  • Processing bounds.
  • Reconstruction safeguards.
  • Resource limits.
  • Publication validation.

Does disabled mean the dataset is clean?

No.

It does not prove that the source is valid or complete.

Should I disable it to make a failed job run?

Not as a general recovery method.

First determine whether the failure is caused by an integrity threshold, an invalid source format, a missing snapshot, or another independent processing requirement.

Disabling integrity evaluation does not repair any underlying source problem.

Integrity Categories

MarketForge tracks seven main integrity categories.

Category Meaning
parse_failure A source record cannot be parsed
invalid_record A parsed record violates validity requirements
sequence_gap Native sequence continuity is missing or invalid
timestamp_regression Event timestamps move backward
missing_snapshot Required order-book initialization is missing
invalid_book Reconstructed book state violates requirements
transformation_failure Source-to-canonical transformation fails

Why distinguish categories?

Different anomalies have different implications.

For example, a parse failure may affect one source record.

A missing order-book snapshot can affect the interpretation of many subsequent updates.

A timestamp regression may leave the original records intact but violate the expected ordering.

A single universal error count would not capture these differences.

Parse Failures

A parse failure occurs when a source record cannot be decoded according to the selected format.

For example:

{"price":"100","quantity":

is malformed JSON.

Why can this happen?

Possible causes include:

  • Corrupt source files.
  • Truncated records.
  • Unsupported field encodings.
  • Unexpected source-layout changes.

Does accepting a parse failure recover the record?

No.

A record that cannot be parsed does not become a valid normalized event merely because the integrity policy permits degraded acceptance.

What should I investigate?

Inspect the original source file and the installed profile.

Determine whether the problem is malformed source data or an incorrect source interpretation.

Invalid Records

An invalid record is parseable but violates the applicable validation requirements.

For example:

Price: Invalid
Quantity: Negative where unsupported

Why is this different from a parse failure?

The decoder successfully read the record's structure.

However, the decoded values do not satisfy the supported market-data rules.

Can invalid records be counted?

Yes.

The integrity system retains the relevant violation information.

Does an invalid record always require immediate failure?

That depends on the configured integrity action and independent processing constraints.

However, an integrity threshold cannot transform an invalid record into a valid canonical event.

Sequence Gaps

Some feeds include native sequence numbers.

For example:

100
101
102

A discontinuity may indicate missing updates.

For example:

100
101
105

Why is this important for depth?

Order-book reconstruction can depend on receiving every applicable update in the correct order.

If updates are missing, the resulting book state may be unreliable.

Does every source require consecutive sequences?

No.

The sequence policy depends on the installed normalization profile.

Some sources are unsequenced.

Others use ranges or bounded-observation sequence semantics.

Can integrity configuration invent sequence continuity?

No.

A sequence field's meaning is established by the source profile and actual source contract.

The runtime integrity policy evaluates the resulting violations.

Timestamp Regressions

A timestamp regression occurs when event time moves backward according to the applicable source-ordering checks.

For example:

12:00:00.100
12:00:00.200
12:00:00.150

The third event occurs earlier than the preceding high-water timestamp.

Why is this important?

Historical processing often relies on event ordering.

Timestamp regressions may indicate:

  • Out-of-order source records.
  • Recording problems.
  • Source resets.
  • Incorrect timestamp interpretation.

Are equal timestamps regressions?

No.

For example:

12:00:00.100
12:00:00.100

does not constitute a timestamp regression merely because the values are equal.

Can timestamp policy change the outcome?

Yes.

The runtime supports explicit trade and depth timestamp-processing policies.

These are explained later.

Missing Snapshots

Some order-book sources require a snapshot before applying incremental updates.

For example:

Snapshot
    |
    v
Update 1
    |
    v
Update 2

What happens without the snapshot?

The Engine may not have enough information to establish a valid initial book.

Can integrity policy ignore initialization requirements?

No.

Independent reconstruction safeguards remain mandatory.

Why?

An order-book update such as:

Delete bid at 100

does not establish the complete book state.

Publishing dependent updates without valid initialization could misrepresent the market.

Invalid Book State

An invalid-book violation means the reconstructed order book does not satisfy the applicable validity requirements.

For example, the Engine may detect state inconsistencies while applying the source operations.

Why is this different from missing snapshots?

A snapshot may be available, but subsequent updates can still produce an invalid book.

Can permissive loss settings allow an invalid book to be published?

No.

The supported reconstruction and publication checks remain independent of event-loss allowances.

Transformation Failures

A transformation failure occurs when source data cannot be converted according to the selected normalization rules.

For example, a field value may not be compatible with the declared transformation.

Possible causes

  • Wrong profile mapping.
  • Unsupported source value.
  • Invalid quantity interpretation.
  • Unexpected source format.
  • Unsupported transformation input.

Why investigate the profile?

The source may be valid under its native format but incompatible with the installed profile.

An incorrect profile can create widespread transformation failures.

Integrity Rules and Thresholds

Integrity Actions

Each integrity category has a rule.

For example:

[integrity_policy.parse_failure]
action = "fail"
max_count = 0

The supported actions are:

fail
degrade

Fail

action = "fail"

A violation is immediately fatal while integrity evaluation is enabled.

Degrade

action = "degrade"

The violation can produce a degraded integrity result, subject to the applicable limits.

Important: fail does not become permissive with a count

For example:

action = "fail"
max_count = 100

does not mean the first 100 violations are allowed.

With enabled integrity evaluation, fail rejects any occurrence.

When do thresholds matter?

Thresholds control whether violations under a degrading rule remain within the configured allowance.

They do not turn the fail action into a tolerance policy.

Integrity Rule Parameters

Each integrity category supports the following parameters.

Parameter Purpose
action fail or degrade
max_count Maximum absolute violation count
max_rate Maximum permitted violation fraction
minimum_samples Minimum observations before rate enforcement
windows.hourly Optional hourly rate rule
windows.daily Optional daily rate rule

Example rule

The following illustrates an explicitly bounded degrading policy:

[integrity_policy.parse_failure]
action = "degrade"

max_count = 10
max_rate = 0.001
minimum_samples = 1000

windows.hourly = {
    max_rate = 0.01,
    minimum_samples = 100
}

windows.daily = {
    max_rate = 0.005,
    minimum_samples = 500
}

This example is a replacement for the parse_failure section in an otherwise complete runtime configuration.

It is not a complete runtime file by itself.

Why have multiple limits?

A global violation rate may be low while one short interval contains a concentrated group of failures.

Hourly and daily rules can detect those concentrations.

Does every rule need all parameters?

No.

The applicable thresholds are optional.

However, using degrade without sufficient bounded policy configuration can be rejected.

Consult the current validator when configuring non-strict integrity behavior.

Maximum Count

For example:

max_count = 10

This limits the allowed absolute number of relevant violations under the applicable degrading rule.

Example

Suppose the permitted count is 10.

Observed violations:

8

remain within the count limit.

Observed violations:

11

exceed it.

Is the threshold inclusive?

Yes.

An observation count equal to the configured maximum is within the limit.

Does max count apply to arbitrary event loss?

No.

Integrity violation counts and processing-event exclusion allowances are separate.

For example, a trade overlap policy has its own max_excluded_events setting.

Do not confuse these controls.

Maximum Rate

The rule can also specify:

max_rate = 0.001

Rates are fractions, not percentages.

Examples

Value Percentage
0 0%
0.0001 0.01%
0.001 0.1%
0.01 1%
0.1 10%
1 100%

Why use a rate?

An absolute count can have different significance depending on the number of observations.

For example:

10 failures in 100 records

is different from:

10 failures in 10 million records

Rate-based checks account for the eligible observation denominator.

Are rates rounded to percentages before comparison?

No.

The evaluator uses decimal arithmetic for the applicable rate checks.

The configured rate is a fraction.

What if the observed rate equals the limit?

Equality is permitted.

The rule fails when the applicable observed rate exceeds the limit.

Minimum Samples

A rate rule can specify:

minimum_samples = 1000

This delays rate enforcement until enough observations have been collected.

Why is this useful?

A small sample can produce an unstable rate.

For example:

1 failure
10 observations

produces a 10% rate.

However, the final workload may contain millions of observations.

A minimum-sample rule prevents the applicable rate check from making decisions before its required denominator is available.

Does minimum samples disable absolute limits?

No.

An absolute count limit can still fail before the minimum sample count is reached.

Example

max_count = 10
max_rate = 0.001
minimum_samples = 1000

If 11 violations occur before 1,000 observations, the count limit is already exceeded.

The sample floor does not authorize unlimited failures.

Hourly and Daily Integrity Windows

Integrity rules can apply rate thresholds to event-time windows.

For example:

windows.hourly = {
    max_rate = 0.01,
    minimum_samples = 100
}

Why use time windows?

A source may contain a short period with unusually many malformed records.

For example:

00:00–01:00   Clean
01:00–02:00   Many failures
02:00–03:00   Clean

The overall daily violation rate could remain small.

However, the affected hour may be unsuitable for research.

Hourly rule

Evaluates the applicable violation rate within supported hourly event-time windows.

Daily rule

Evaluates the applicable violation rate within supported daily event-time windows.

What if a record has no trustworthy timestamp?

The evaluator tracks observations that cannot be assigned to trustworthy event-time windows.

When a time-window policy requires attribution, missing trustworthy timestamps can cause policy failure.

Why not assign an arbitrary time?

Doing so would create false timing evidence.

MarketForge distinguishes unknown event-time attribution from verified timestamps.

Immediate vs. Final Integrity Evaluation

Integrity checks occur at more than one point.

During source processing

Immediately fatal categories can stop work as violations occur.

During final evaluation

The Engine evaluates the relevant:

  • Absolute counts.
  • Violation rates.
  • File-level rates.
  • Stream-level rates.
  • Hourly rates.
  • Daily rates.
  • Whole-job integrity conditions.

Why separate these stages?

Some rate calculations require a final denominator.

Rejecting based on an incomplete denominator could produce incorrect decisions.

However, an immediately fatal rule does not need to wait for the final rate calculation.

Does delayed rate evaluation mean violations are ignored?

No.

The relevant observations are retained in the aggregate integrity accounting.

They are evaluated when sufficient evidence is available.

          10:00 ─────────────────── 24:00

Between 10:00 and 12:00, both sources contain observations.

Why can this happen?

Possible reasons include:

  • Overlapping provider archives.
  • Repeated recordings.
  • Source revisions.
  • Recovery recordings.
  • Alternative archive products.
  • Partially overlapping data collection.

Why is reconciliation necessary?

Simply concatenating the files may duplicate observations.

Choosing one source arbitrarily may discard unique events.

For depth, mixing updates without matching book state can invalidate reconstruction.

MarketForge therefore implements explicit source-reconciliation policies.

Default Reconciliation Behavior

The runtime supports separate trade and depth reconciliation settings.

For example:

[reconciliation.depth]

The sections can be omitted when you want the strict defaults.

Trades and depth have different event semantics.

A trade is an execution.

A depth update can depend on a reconstructed book state.

The same overlap-handling strategy may not be appropriate for both.

Does adding [reconciliation] enable permissive behavior?

No.

The table itself does not activate relaxed processing.

The selected policy and any required loss allowances must be explicit.

Because source preference and event-loss permission are separate decisions.

Price:    80000
Quantity: 0.5
Side:     Buy

Why is identity scope important?

An exchange may use identifiers that are:

  • Globally unique.
  • Instrument-scoped.
  • Source-local.
  • Reset between sessions.
  • Unreliable.

For example, the numeric ID:

does not automatically establish global uniqueness.

Can equal timestamps prove duplicates?

No.

Two trades can share:

Timestamp
Price
Quantity
Side

without representing the same execution.

What proves equivalence?

The supported reconciliation requires reliable event identity together with matching complete contents.

What if the contents conflict?

Under strict processing, conflicting complete contents for one reliable identity cause failure.

A source-preference policy may resolve the conflict only when the applicable loss authorization permits it.

The losing observation is then conservatively accounted for.

Source-Local and Ambiguous IDs

Some source IDs are only unique within a local scope.

For example:

Archive A:
Trade ID 100

Archive B:
Trade ID 100

These may represent different trades.

Why not deduplicate them automatically?

Because the identity scope may not extend across archives.

Does a large numeric ID imply global uniqueness?

No.

Even arbitrary-length numeric identifiers do not establish an identity contract merely by their shape.

What about nonconsecutive IDs?

Reliable trade identities do not need to be consecutive to represent distinct executions.

For example:

100

9000

can represent distinct valid IDs under the appropriate source contract.

What if the native reset domain is ambiguous?

Strict processing can reject the unresolved identity relationship and report the missing evidence.

Why is this necessary?

Incorrect cross-source deduplication can permanently remove legitimate historical trades.

MarketForge requires source identity semantics rather than relying on superficial record similarity.

Verified Duplicate Suppression

Suppose two source observations are proven to represent the same trade.

The duplicates can be reconciled without treating one as lost unique market activity.

Example

Source A:
Trade 10001

Source B:
Trade 10001

If their reliable identities and complete contents agree, they represent verified duplicate evidence.

Why does this matter for completeness?

Suppressing an independently verified duplicate is different from discarding a unique trade.

For example:

Two recordings of the same execution

still represent one logical execution.

However:

Two different executions

must not be reduced to one merely because their prices or timestamps match.

How is it reported?

Verified duplicate suppression is distinguished from known-unique or unverified event exclusions.

Verified duplicate suppression does not itself degrade supplied-event completeness.

Source Preference

How Source Preference Works

When using prefer_source, the runtime can select which source has priority in an overlapping region.

The supported selection modes are:

earlier
later

Example

[reconciliation.trades]
overlap_policy = "prefer_source"

[reconciliation.trades.prefer_source]
selection = "earlier"

This example selects the earlier-coverage preference.

It does not authorize unique event loss.

What does earlier mean?

It compares actual validated source coverage starts.

What does later mean?

It prefers the source with the later validated coverage start.

Does filename order determine priority?

No.

Source preference is based on actual accepted coverage information.

What if starts are equal?

The runtime uses canonical physical path and archive-member identity as deterministic tie-breakers.

This is a reproducibility rule.

It is not a claim that the selected file is higher quality.

Source Preference Is Not Task Priority

A prepared normalization job may contain task ordering or stream ranks.

However, those are not the authority for reconciliation source preference.

Why distinguish them?

Task ordering can depend on:

  • Prepared job organization.
  • Stream ranking.
  • Source enumeration.
  • Engine scheduling.

Source preference should not change merely because worker completion order changes.

What determines ownership?

The reconciliation algorithm uses the actual validated coverage relationships and the selected preference policy.

Does processing concurrency choose the winner?

No.

Task or worker completion order does not select the preferred source.

What about complex overlaps?

The ownership sweep supports more than two sources.

For example:

Source A:
00:00 ─────────────────── 12:00

Source B:
      06:00 ─────────────────── 18:00

Source C:
           09:00 ─────────────────── 24:00

The algorithm handles nested, chained, and multiple overlapping source relationships.

It does not rely on a simplistic pairwise concatenation rule.

Trade Union and Conflict Ownership

Reliable nonconflicting trade observations can be retained together.

For example:

Source A:
Trade 100
Trade 101

Source B:
Trade 102
Trade 103

If the identities and source evidence are compatible, the logical trade union preserves the distinct executions.

What if one source contains unknown identities?

The runtime cannot prove which observations are duplicates solely from their timestamp and price.

In overlapping conflict intervals, source ownership may be required.

What happens to excluded observations?

They are counted conservatively.

Unknown uniqueness is reported as an unverified exclusion.

Why is this important?

A source-preference policy should not silently turn uncertainty into a claim of equivalence.

For example, an excluded observation might be a duplicate.

But it might also be a unique trade.

Without sufficient identity evidence, its uniqueness remains unverified.

Explicit Event-Loss Authorization

Why Event Loss Must Be Explicit

A preferred source can contain fewer observations than another source.

For example:

Source A:
Trade 1
Trade 2
Trade 3

Source B:
Trade 1
Trade 3

If Source B wins and Trade 2 is excluded, the result loses unique supplied activity.

MarketForge does not allow this silently.

Default behavior

The source-preference loss action defaults to:

on_unique_data_loss = "fail"

Meaning

Any exclusion of unique data that is not otherwise authorized causes failure.

Why is this strict?

A dataset should not appear complete when processing knowingly removed supplied market observations.

Permit Bounded Degraded Loss

The supported alternative is:

on_unique_data_loss = "mark_degraded"

This explicitly permits bounded exclusion while marking the resulting quality as degraded.

Example

The following is a policy fragment to add to a complete runtime configuration:

[reconciliation.trades]
overlap_policy = "prefer_source"

[reconciliation.trades.prefer_source]
selection = "earlier"

on_unique_data_loss = "mark_degraded"

max_excluded_events = 5
max_excluded_rate = 0.001

minimum_samples = 1000
max_excluded_interval_ms = 1000

What does this authorize?

It allows the relevant trade reconciliation to exclude a bounded number of observations under the selected preference rules.

Does it guarantee that five events will be excluded?

No.

It establishes limits.

The actual number depends on the selected source data.

Does it permit unlimited exclusion below the rate threshold?

No.

The event-count limit remains effective.

Does the resulting publication remain clean?

No.

Known-unique and unverified exclusions degrade completeness.

The quality evidence records the applicable loss.

The supported settings are:

Field Default Meaning

Required permission

mark_degraded requires:

A zero allowance is invalid for that loss action.

Why require an explicit positive count?

A rate alone could permit an unexpectedly large absolute number of excluded events in a huge dataset.

The finite count makes the maximum exposure explicit.

What if max_excluded_rate is omitted?

The configured event-count allowance still applies.

Omitting a rate does not remove the count limit.

What if minimum samples is large?

The count limit is still enforced before the rate floor is reached.

What about contiguous intervals?

The optional interval limit constrains the duration of a continuous exclusion span.

This prevents a policy from accepting one very long period of missing supplied activity merely because the total count remains within a numerical limit.

Why Loss Accounting Uses Logical Events

Order-book observations can expand into many canonical price-level rows.

For example:

One source snapshot
        |
        v
200 price-level rows

If that one snapshot is excluded, the logical loss is one source observation.

It is not automatically 200 separate source-event losses.

Why distinguish source observations from rows?

The physical Parquet representation can contain multiple rows per market event.

Counting expanded rows would make loss thresholds depend on output representation rather than supplied observations.

What does MarketForge count?

Loss allowances use logical source-event accounting under the relevant content type.

The denominator excludes verified duplicates but includes excluded and unverified logical observations.

What about parse failures?

Parse and normalization rejections are accounted for through their relevant processing and integrity categories.

They are not arbitrarily added to the source-preference event-loss denominator.

Depth Reconciliation

Why Depth Reconciliation Is Different

Trades are independent executions.

Depth updates can depend on earlier book state.

For example:

Snapshot:
Bid 100 = 10

Update:
Bid 100 = 15

Update:
Delete Bid 100

Each update changes the state established by earlier events.

Why is overlapping depth difficult?

Imagine two recordings of the same market.

Source A and Source B may contain different sequences of book updates.

Even if their timestamps overlap, their internal reconstruction histories may not be interchangeable.

What could go wrong?

Suppose you apply a delta from Source B to a book reconstructed from Source A.

The resulting state may be incorrect if the two sources do not share the required prior book state.

Why not merge individual level changes?

The runtime does not splice unrelated level-difference vectors together without matching reconstruction evidence.

Depth events are treated as atomic messages or grouped snapshots according to the applicable source contract.

For research, independently valid order-book segments can still be useful.

The alternative is:

This is more restrictive than it may appear.

What must be established?

The transition requires:

  • Matching complete book state.
  • Compatible native sequence evidence.
  • Supported source-boundary conditions.

Why is this necessary?

Two streams can contain events with matching timestamps while representing different book states.

Equal timestamps do not prove that the corresponding books are interchangeable.

What about unsequenced feeds?

Unsequenced feeds cannot invent the required native sequence evidence.

Can Source A be resumed after switching to Source B?

Only through another valid transition.

For example:

Source A → Source B → Source A

The Engine does not assume returning to an earlier source is automatically safe.

Depth reconciliation includes stronger checks than source overlap alone.

Source reconstruction

The runtime reconstructs source prefixes from scratch-backed evidence.

Selected history

The selected history is applied to a separate book state.

Validation

Complete book state is checked after every applicable event.

Why use separate reconstruction?

The Engine must establish that the selected history is valid.

It should not simply splice source updates and assume the result represents a coherent book.

What happens when reconstruction fails?

Unsafe transitions, missing initialization, or invalid source reconstruction can prevent publication.

This remains true even when the loss policy permits some excluded events.

Does a generous loss allowance override book validity?

No.

Resource limits, reconstruction validity, integrity acceptance, and publication checks are separate gates.

Some depth sources provide sequenced boundary snapshots.

These can help establish whether two histories describe equivalent state.

What does MarketForge compare?

The supported comparison uses decoded evidence such as:

  • Complete snapshot contents.
  • Timestamps.
  • Relevant sequence information.

Does JSON property order matter?

Not when comparing semantically equivalent decoded JSON object contents.

For example:

{"price":"100","quantity":"5"}

and:

{"quantity":"5","price":"100"}

have the same object properties.

Property ordering alone does not establish a different market event.

What about deltas sharing snapshot IDs?

They remain distinct where their source semantics require it.

A shared snapshot identifier does not automatically make every associated delta a duplicate.

Can a terminal snapshot be represented by the next initialization?

The supported boundary representation can use a following full initialization when it accurately represents the canonical state transition.

It does not authorize inventing an intermediate book state.

Timestamp-Regression Policies

Why Have Separate Timestamp Policies?

Timestamp regressions occur when events move backward in event time.

For example:

12:00:00.100
12:00:00.300
12:00:00.200

However, the correct response depends on the content type.

Trades

Independent trades may sometimes be reordered while preserving their identities and original timestamps.

Depth

Incremental depth updates are stateful.

Arbitrary timestamp sorting can change reconstruction behavior.

Why separate the policies?

A policy suitable for independent trades may be unsafe for order-book updates.

MarketForge therefore has separate trade and depth timestamp-regression settings.

Timestamp Configuration Structure

The runtime supports:

[timestamp_regression.trades]
policy = "strict"

[timestamp_regression.depth]
policy = "strict"

These are the default behaviors.

Trade policies

Supported values:

strict
preserve
reorder
discard

Depth policies

Supported values:

strict
preserve
snapshot_recovery

Why are the lists different?

Depth cannot be handled as a collection of independent trades.

Its reconstruction depends on valid source ordering and state transitions.

What Counts as a Regression?

The Engine uses the relevant high-water timestamp when evaluating regressions.

Example

Consider:

100
95
90

If the high-water timestamp is 100, both later observations remain below that high-water mark.

The regression bound is not reset simply because the immediately preceding timestamp was 95.

Why is this important?

Otherwise, a source could move progressively backward through several small steps without exceeding a per-step threshold.

The high-water comparison prevents that form of cumulative backward movement from evading the configured bound.

Equal timestamps

Equal timestamps are not regressions.

Source domains

Raw-source ordering evidence is evaluated within the appropriate concrete source and native reset domain.

Independent sources are not automatically treated as one native sequence.

Snapshot resets

Validated native snapshot resets can establish a new applicable domain.

Timestamp precision

Arithmetic is checked using canonical nanosecond precision.

The original event and system timestamps are not clamped, shifted, or rewritten by these policies.

Trade Timestamp Handling

Strict Trade Timestamp Policy

The default is:

[timestamp_regression.trades]
policy = "strict"

What does strict mean?

The Engine rejects applicable timestamp regressions under the strict processing contract.

Does setting a positive bound make strict permissive?

No.

For example:

policy = "strict"
max_regression_ms = 100

does not authorize regressions.

Strict remains strict.

Preserve Trade Source Order

The preserve policy retains the original native source order.

For example:

[timestamp_regression.trades]
policy = "preserve"
max_regression_ms = 100

What does preserve do?

It retains:

  • Original source order.
  • Original event timestamps.
  • Original record ordinals.

Does it sort trades chronologically?

No.

Does it change timestamps?

No.

Does the regression bound still matter?

Yes.

The permissive policy remains subject to its configured processing limits and independent integrity requirements.

Why use preserve?

It can be useful when the source's native order is significant and the policy explicitly permits the bounded regression behavior.

However, the resulting physical ordering must be understood by downstream consumers.

Reorder Independent Trades

The reorder policy permits supported deterministic chronological ordering of independent trade executions.

For example:

[timestamp_regression.trades]
policy = "reorder"

max_regression_ms = 100
max_reorder_window_ms = 100

This is a policy fragment for an otherwise complete runtime file.

What does it do?

After the applicable identity reconciliation, the Engine can order independent executions chronologically.

Does it modify event timestamps?

No.

The original timestamps remain unchanged.

How are equal-time trades ordered?

The supported deterministic ordering uses:

  • Exact numeric trade IDs where applicable.
  • Source positions as final tie-breakers.

Does it use floating-point trade IDs?

No.

Exact numeric identities are retained for the applicable ordering logic.

Is reordering in memory unbounded?

No.

The implementation uses admitted bounded external runs and scratch storage.

It does not allocate an unlimited in-memory time-window buffer.

What happens if scratch is insufficient?

The operation can fail because of resource exhaustion.

Reorder Bounds

Trade reordering requires:

max_regression_ms > 0

and:

max_reorder_window_ms > 0

The reorder window must also satisfy:

max_reorder_window_ms >= max_regression_ms

Why require both?

One bound constrains the permitted regression.

The other constrains the supported reordering operation.

Example

Valid:

max_regression_ms = 100
max_reorder_window_ms = 200

Invalid:

max_regression_ms = 200
max_reorder_window_ms = 100

The reorder window is smaller than the regression bound.

Does a large window guarantee success?

No.

Resource constraints and independent integrity rules still apply.

Why is this a lossy policy?

Because it can remove supplied observations from the published result.

What is required?

The policy requires:

No.

A positive finite event-count allowance is required.

Does discard remove arbitrary bad records?

No.

The policy applies to eligible regressing survivors under the supported processing contract.

It cannot mask unrelated parsing, identity, or overlap failures.

What about verified duplicates?

A raw regression associated with a verified duplicate may be resolved during identity reconciliation.

However, a fatal raw integrity rule can still fail the job.

Does discarding affect completeness?

Yes.

Excluding unique or unverified observations degrades the published completeness evidence.

Loss Accounting and Completeness

Why Event Accounting Matters

Historical processing can transform one source observation into several canonical rows.

For example:

One depth snapshot
        |
        v
100 bid levels
100 ask levels
        |
        v
200 canonical rows

If that snapshot is excluded, MarketForge must account for one lost logical source observation.

It should not confuse that with 200 separate market messages.

Why distinguish events and rows?

Because physical representation and logical source activity are different.

For example:

  • One trade usually corresponds to one canonical trade event.
  • One depth observation may expand into many level rows.
  • One verified duplicate may be suppressed without losing unique market activity.

The processing-quality system accounts for these differences.

Loss Denominator

The supported event-loss denominator is based on accepted logical source observations, excluding verified duplicates.

It includes relevant excluded and unverified observations.

What does it exclude?

The denominator does not treat expanded price-level rows as separate logical events.

Parse and normalization rejections are accounted for through their corresponding processing and integrity categories rather than being silently treated as accepted source observations.

Why does this matter?

Suppose one depth observation expands into 500 canonical rows.

A loss policy should not become 500 times stricter merely because the source observation contains many levels.

Does verified deduplication degrade completeness?

No.

A verified duplicate represents repeated evidence of the same logical event.

Suppressing it does not remove unique market activity.

What does degrade completeness?

Known-unique or unverified exclusions.

Those represent supplied observations that were not preserved in the committed logical output.

Job-Wide vs. Stream-Wide Limits

The documented source-preference and timestamp-loss allowances apply job-wide per relevant content type.

Example

Suppose the trade job contains three streams.

BTCUSDT
ETHUSDT
SOLUSDT

The configured maximum excluded-event count is not automatically reset for every stream.

The job-wide allowance constrains the applicable total.

Why?

Otherwise, a policy intended to permit only a small amount of loss could permit that amount independently for every instrument.

The total loss could become much larger than expected.

Are stream metrics still available?

Yes.

The processing report retains applicable source, task, and stream totals.

However, the main loss allowances are enforced at the documented job-wide scope.

Why track spans?

A small number of missing events spread across a large dataset may have a different implication from a concentrated period of missing observations.

Do different loss reasons start separate spans?

Not automatically.

The documented accounting continues contiguous loss spans across reasons and verified duplicates until an observation is actually retained.

Why?

A sequence of excluded observations remains an uninterrupted absence from the published logical history even when individual exclusions have different reasons.

What does the interval limit control?

The optional:

max_excluded_interval_ms = ...

constrains the maximum contiguous excluded span under the applicable source/stream accounting.

Scratch Representation

Why Does MarketForge Have Scratch Formats?

During historical processing, the Engine may need temporary representations of records.

For example:

  • Source reconciliation.
  • Bounded trade reordering.
  • Detailed integrity processing.
  • Intermediate event storage.

These temporary artifacts are not the same as committed Parquet output.

Why use separate scratch formats?

Different internal representations can have different processing and storage characteristics.

The runtime provides explicit options for those temporary records.

Scratch Format

The supported setting is:

scratch_format = "json"

Accepted values are:

Value Meaning
json JSON scratch representation
typed_trades Typed trade scratch representation
typed_events Typed event scratch representation, including supported depth scratch records

The default is:

json

Why use typed representations?

The Engine can use specialized internal structures for supported processing paths.

For example, typed scratch records may avoid some costs associated with repeatedly representing structured events as generic JSON.

Does typed_events change canonical publication schemas?

No.

Scratch representation is internal working storage.

The committed output still uses the supported Parquet and manifest formats.

Does every scratch format support every source?

Use only combinations supported by the current processing implementation.

A scratch setting does not add unsupported normalization decoders.

Scratch Codec

The codec setting is:

scratch_codec = "zlib"

Accepted values are:

zlib
uncompressed

The default is:

zlib

Zlib

Uses the supported compressed scratch representation.

Uncompressed

Uses the corresponding uncompressed scratch representation.

Why provide both?

Compression can reduce temporary storage requirements.

However, it can also introduce compression and decompression work.

The appropriate choice depends on the workload and storage environment.

Does changing the codec change normalized values?

No.

The codec controls internal scratch-file representation.

It does not independently redefine source values or canonical market semantics.

Merge runtime settings

Normalization merge fan-in

The runtime supports:

merge_fan_in = 8

The default is 8.

The current validator accepts:

2–64

What does fan-in control?

It constrains the relevant merge/reconciliation fan-in behavior.

Why limit fan-in?

Processing too many intermediate streams or files at once can increase resource pressure.

Fan-in provides a bounded processing parameter.

Does increasing fan-in always improve performance?

No.

The effect depends on the actual workload, memory budget, and storage throughput.

Is merge fan-in the same as stream rank?

No.

Stream rank describes an ordering identity.

Merge fan-in is a runtime processing parameter.

Merge and conversion runtime

Merge reads data/.config/engine/merge.toml. Conversion preparation reads data/.config/engine/convert.toml. Both use the shared Rust resource and Parquet types and reject unknown fields. The sample is a bounded starting point. Resource and Parquet fields without defaults are required. The merge-only partitioning table is optional and defaults to four partitions per worker.

schema_version = 1

[resources]
workers = 2
memory_limit_mb = 512
max_open_files = 64

[parquet]
row_group_target_mb = 16
file_target_mb = 64
compression_level = 3

# Omit this table for convert.toml.
[partitioning]
partitions_per_worker = 4
Field Type, units, range Effect
schema_version Integer, exactly 1 Runtime document schema
resources.workers Positive integer Worker ceiling. Actual admission depends on available resources and the workload.
resources.memory_limit_mb Positive integer MiB, must fit in unsigned 64-bit bytes Budget for admitted work and writer buffers.
resources.max_open_files Positive integer, file handles, default 64 File-handle ceiling. Conversion estimates participating source and reference handles before proceeding.
parquet.row_group_target_mb Positive integer MiB, at most the file target Target size for buffered row groups. Conversion checks the target multiplied by workers against its memory limit.
parquet.file_target_mb Integer MiB, at least the row-group target, must fit in unsigned 64-bit bytes File rotation size target.
parquet.compression_level Integer 1–22, default 3 Zstandard level applied to Parquet output.
partitioning.partitions_per_worker Positive integer, merge only, default 4 Timeline partition target. Multiplication by workers must fit in the platform size type.

The direct Rust merge command accepts --config PATH, relative to its --project-root. Forge records the original path and checksums the retained runtime file, then uses that copy for prepared-job execution. The merge monitor and merge-runtime.json show effective settings.

Conversion clamps each recipe resource request to the corresponding runtime ceiling. It transfers the clamped values and Parquet settings into prepared jobs, where the Rust converter reads them. The direct converter can lower the prepared worker count with --workers. Physical input, reference, file-handle and writer-memory prerequisites are checked separately from runtime TOML validation.

Parquet compression

parquet.compression_level controls the supported Zstandard compression level for merge output.

Does a higher number always improve compression?

The exact outcome depends on the data and compression implementation.

Higher levels can require more computational work.

Does compression change market-data meaning?

No.

Compression affects physical storage representation.

It does not intentionally change the canonical event values.

Is this the same as scratch codec?

No.

Merge Parquet compression and internal scratch compression are separate settings.

For example:

scratch_codec = "zlib"

does not mean the final merged Parquet output uses zlib.

Pipeline runtime

data/.config/engine/pipeline.toml has a required integer schema_version = 1. It accepts optional [normalize] and [merge] tables with the same nested fields as their operation documents, excluding the operation schema version. For example:

schema_version = 1

[normalize.resources]
workers = 2

[merge.parquet]
compression_level = 5

Each operation TOML is independently validated, then each override is applied recursively to its own stage. Unspecified fields inherit the operation file and its Rust defaults. Rust validates the resulting TOML before processing. Acquire uses Forge HTTP settings and the workflow request. The pipeline executes acquire, normalize and merge.

For a new run, Forge retains the effective TOMLs, their checksums, the source TOML hashes, compiled settings, profile source files and executable hashes. Resume uses the retained files. A prior pipeline snapshot with a shared general.toml remains readable through its retained report and executables.
