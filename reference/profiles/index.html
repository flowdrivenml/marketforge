Historical normalization profile schema

Installed profiles use schema_version = 2 and kind = "profile". The Engine compiles their physical and semantic mappings into its internal reader and normalization representation. Look up identity and installation, the schema discriminator, and the format or mapping sections in the page outline. For source inspection, editing, validation and sample execution, use the profile guides.

Use the generated field index for canonical parameter paths, types and conditions, and the profile CLI reference for inventory, editor and validation commands. The index and structured schema share one artifact. Regenerate with python engine/scripts/generate_profile_schema.py and check it with the same command plus --check after Rust profile changes.

Profile identity and installation

Profile naming convention

Every normalization profile has a unique ID consisting of exactly four components:

exchange.instrument_type.market_category.data_type

For example:

bybit.spot.spot.trades
binance.perpetual.linear.trades
binance.perpetual.inverse.depth
okx.future.inverse.depth

Understanding the components

Component Example Meaning
Exchange bybit Execution venue.
Instrument type perpetual Financial product type.
Market category linear Market or contract category.
Data type trades Source content interpretation.

Supported data-type suffixes

The final component must be:

trades
depth

For example:

bybit.perpetual.linear.trades
bybit.perpetual.linear.depth

Why use depth instead of order_book_l2?

Different MarketForge interfaces use different names for the same broad content family.

Context Value
Acquisition request order_book_l2
Normalization recipe order_book_l2
Profile ID depth
Rust normalization target l2_snapshot or l2_update

Use the exact value required by each interface.

Are additional ID components allowed?

No.

For example:

binance.spot.spot.trades.v2

is invalid.

So is:

binance.spot.spot.trades.custom

The profile ID must contain exactly four components.

Instrument and Market Compatibility

The profile identity must use a supported instrument-type and market-category combination.

Instrument type Valid market category
spot spot
perpetual linear, inverse
future linear, inverse
option option
equity equity

Why are these restrictions necessary?

A profile must identify the type of market data it interprets.

For example:

Perpetual / Linear

and:

Perpetual / Inverse

can use different contract conventions.

Similarly:

Equity / Equity

is not interchangeable with:

Spot / Spot

Native cryptocurrency exchanges

MarketForge's native acquisition infrastructure includes:

bybit
binance
okx
bitget
gateio

External execution venues

For externally supplied recordings, use the actual execution venue registered in the catalogue.

For example, an AAPL recording can use an equity venue identity rather than the name of the data vendor.

The provider and execution venue are separate concepts.

Does accepting an identity mean the decoder exists?

No.

A valid market identity is necessary, but the actual source layout must also be supported by the Rust compiler and runtime.

Profile Filenames

The filename must match the declared profile ID exactly.

For example:

binance.spot.spot.trades.toml

The corresponding metadata must include:

id = "binance.spot.spot.trades"
exchange = "binance"
instrument_type = "spot"
market_category = "spot"

Why require an exact filename?

The profile catalogue resolves definitions using their declared identities.

An inconsistent filename could make discovery and installation ambiguous.

Can I rename a profile to create a new variant?

Not by adding another ID component.

For example:

binance.spot.spot.trades.custom.toml

does not establish a supported independent profile identity.

The current catalogue uses one interpretation per four-component ID.

Profile Catalogue Directories

Installed profiles are stored under:

data/.config/engine/normalize/profiles/

The relevant directories are:

data/.config/engine/normalize/profiles/
├── trades/
└── depth/

For example:

data/.config/engine/normalize/profiles/trades/binance.spot.spot.trades.toml

and:

data/.config/engine/normalize/profiles/depth/bybit.spot.spot.depth.toml

Discovery reads the direct children of trades/ and depth/ in deterministic order. The filename must be the lowercase exchange.instrument_type.market_category.kind.toml ID. The final component agrees with the directory. Temporary files, backup suffixes and unrelated TOMLs are excluded. A recognized candidate with invalid TOML, a contradictory namespace or an unsupported schema fails validation.

The normalization binary resolves --profiles-root relative to its project root. Its default is data/.config/engine/normalize/, the parent of profiles/. The library's cached default catalogue also accepts an absolute MARKETFORGE_HISTORICAL_CONFIG or its legacy environment alias MARKETFORGE_HISTORICAL_FORMATS. Forge passes the appropriate workspace or retained snapshot root to the binary.

mf acquisition profiles list --type trades
mf acquisition profiles validate bybit.spot.spot.depth

Why separate trades and depth?

Trade records and order-book events require different processing rules.

Separating the installed definitions makes their content type explicit.

Where should I create new profiles?

Prepare new definitions in a separate working directory.

For example:

research/profiles/
├── binance.spot.spot.trades.toml
└── bybit.spot.spot.depth.toml

This is an illustrative authoring location.

Validate the candidate before installing it into the managed profile catalogue.

File requirements

Candidate profile files must:

  • Be regular files.
  • Not be symbolic links.
  • Stay within the supported file-size limit.
  • Match the declared profile identity.

The current maximum profile size is:

1 MiB

One Interpretation per Profile ID

MarketForge does not provide a general-purpose namespace for competing interpretations under one profile identity.

For example, suppose the catalogue already contains:

binance.spot.spot.trades

That profile describes one compiled source interpretation.

You cannot install a conflicting definition under the same ID and expect the old one to remain independently selectable.

What happens during installation?

The installation service compares the candidate's compiled interpretation with the installed definition.

There are two important outcomes.

Equivalent interpretation

The existing installed profile can be reused without replacing its original bytes.

Conflicting interpretation

Installation is rejected.

Why enforce this?

Imagine that the installed profile maps:

B → buy

but a new candidate maps:

B → sell

These interpretations are incompatible.

Silently replacing the profile could change the meaning of historical processing results.

Does changing the format code bypass this?

No.

The profile ID still identifies the same market and content type.

A different format code does not automatically authorize a competing installed interpretation.

How should incompatible source variants be handled?

Use the supported source-specific variant mechanism where one exists.

For example, Gate.io depth has explicit feed variants.

Do not invent arbitrary additional ID components or overwrite managed catalogue files.

Profile Structure

The Three Main Sections

A schema-2 profile contains identity metadata followed by three main sections.

Section Purpose
[source] Physical source format, packaging, ordering, and source contracts.
[fields.<name>] Raw field types, names, positions, and encodings.
[normalization] Mappings and rules that produce canonical market events.

The overall structure is:

Profile
  |
  +-- Identity
  |
  +-- Source
  |
  +-- Fields
  |
  +-- Normalization

Identity

Format Codes

Format codes identify the source format interpretation.

The supported naming convention uses an exchange-specific prefix, a content-type letter, and a positive number.

Native exchange prefixes

Exchange Trade code Depth code

OKX OKX-T<number> OKX-B<number>

For example:

BINANCE-T1

The letter identifies the content type.

T = Trades

Number requirements

The number must be positive.

It cannot begin with zero.

BINANCE-T1

Gate.io prefix

GATE

GATEIO

Does a valid format code mean the source is supported?

No.

A code can satisfy the naming convention without corresponding to a real implemented decoder.

Use the code associated with the actual source format.

A syntactically valid code does not prove compatibility with an exchange archive.

How Normalization Mappings Reference Fields

Schema-2 profiles use named raw fields.

For example:

[fields.price]
type = "decimal"

A normalization mapping references the field:

[normalization.price]
field = "price"

Why use field names?

This separates the raw source layout from the canonical target.

For example, the original source may call its price field:

px

The profile can declare:

[fields.px]
type = "decimal"

[normalization.price]
field = "px"

The canonical target remains a price.

Important schema distinction

User-authored schema-2 profiles use:

field = "price"

Do not copy internal resolved-job representations that use generated source mappings or raw_schema structures.

Those belong to the compiler's internal representation.

Describing the Physical Source

The [source] Section

The source section explains how the historical data is packaged and organized.

For example:

[source]
container = "plain"
format = "csv"
record_format = "rows"
header = true
ordering = "chronological"
granularity = "daily"

This describes a plain CSV file containing chronological rows with a header.

Why is this information necessary?

Rust needs to know how to open and decode the source before applying normalization mappings.

For example, a ZIP archive containing CSV records needs different file-handling behavior from a plain JSONL file.

The source section describes those physical requirements.

Source Containers

The container field describes the outer packaging.

Supported values are:

Container Meaning
plain Uncompressed source file.
gzip Gzip-compressed source.
zip ZIP archive container.
tar_gzip Gzip-compressed TAR archive.

Plain CSV

For example:

[source]
container = "plain"
format = "csv"

Gzip-compressed CSV

[source]
container = "gzip"
format = "csv"

ZIP containing CSV

[source]
container = "zip"
format = "csv"

Why are container and format separate?

The container describes how the records are packaged.

The format describes how individual records are represented after opening the package.

For example:

ZIP Archive
     |
     v
CSV Member
     |
     v
CSV Records

The physical container is ZIP.

The record format is CSV.

Does ZIP imply support for arbitrary members?

No.

Archive-member selection and layout support depend on the corresponding source and processing contract.

Do not assume every arbitrary ZIP structure is executable merely because container = "zip" is accepted.

Source Record Formats

The format field supports:

csv
jsonl
xlsx

CSV

Comma-separated values.

For example:

timestamp,price,quantity
1767225600000,100,0.5

JSONL

One JSON value per line.

For example:

{"timestamp":1767225600000,"price":"100","quantity":"0.5"}

XLSX

An Excel workbook.

The current XLSX decoder supports a specific fixed layout rather than arbitrary spreadsheets.

Important implementation distinction

A supported format string does not mean every possible layout of that format can be processed.

For example:

  • Trades support the implemented CSV and JSONL paths.
  • Depth supports specific JSONL, positional CSV, and fixed XLSX paths.
  • Arbitrary headered CSV depth layouts are not automatically supported.
  • Arbitrary JSON arrays embedded inside CSV cells are not automatically supported.
  • XLSX does not provide a general-purpose spreadsheet decoder.

Start from an existing compatible profile when working with specialized layouts.

Record Formats

The record_format field describes the organization of records.

Supported values include:

Value Intended representation
rows Ordinary tabular records.
events Event-oriented records.
snapshot_rows Rows representing snapshots.
book_rows Rows associated with book-level observations.

Trade profiles

Trade profiles require:

record_format = "rows"

Depth profiles

Depth profiles use the applicable supported record format:

events
snapshot_rows
book_rows

Why distinguish these?

A trade record usually represents one execution.

An order-book source may represent individual updates, complete observations, or rows that must be assembled into a snapshot.

These layouts require different processing behavior.

Does record_format alone enable a decoder?

No.

The selected format, record layout, field mappings, and normalization rules must form a combination supported by the Rust runtime.

CSV Headers

For CSV and XLSX source declarations, header is required.

For example:

header = true

or:

header = false

Headered CSV

A headered CSV contains column names:

timestamp,price,quantity,side
1767225600000,100,0.5,buy

The trade profile's field references must match the actual header names.

Headerless CSV

A headerless CSV contains values immediately:

1767225600000,100,0.5,buy

The profile must identify columns by their supported positional declarations.

Does header = true support every CSV layout?

No.

In particular, arbitrary headered depth CSV is not enabled simply by setting this flag.

The actual depth decoder path must support the source layout.

Source Ordering

The ordering field describes the source's record-ordering contract.

Supported declarations include:

chronological
timestamp_sortable

The following alias is also accepted:

not_chronological

It represents the sortable declaration.

Chronological ordering

Use:

ordering = "chronological"

when the source order is the order that must be preserved.

Timestamp-sortable ordering

Use:

ordering = "timestamp_sortable"

only when the source has a supported sorting path.

Why does this matter for depth?

Order-book updates are stateful.

For example:

1. Initialize book
2. Add bid
3. Modify bid
4. Delete bid

Changing the order can change the reconstructed book state.

A timestamp alone may not establish the correct event order when messages have equal timestamps or source-specific sequence semantics.

Can Engine sort arbitrary depth input?

No.

The current runtime rejects timestamp sorting for ordinary stateful depth input.

The supported workbook snapshot path has separate sorting behavior.

Should I use not_chronological for an unordered feed?

Only when the corresponding decoder actually supports the required sorting behavior.

Declaring a source sortable does not create an arbitrary sorting implementation.

Source Granularity

The granularity field supports:

daily
hourly
monthly

For example:

granularity = "daily"

What does granularity describe?

It describes the relevant source archive organization.

For example:

  • One archive per day.
  • One archive per hour.
  • One archive per month.

Why is this useful?

Historical providers use different archive calendars and packaging conventions.

The profile needs to describe the source format consistently with the corresponding registered archive information.

Does granularity determine the number of records?

No.

A daily archive may contain thousands or millions of events.

The granularity describes archive organization, not event frequency.

Declaring Raw Fields

The [fields] Section

The fields section describes the source values available to the normalizer.

Each field is declared using its own TOML table.

For example:

[fields.price]
type = "decimal"

Another field might be:

[fields.timestamp]
type = "integer"
encoding = "unix_milliseconds"

Why declare raw fields?

The Rust compiler needs to know which source fields exist and how their values should be interpreted.

For example, a timestamp field requires more than its position.

The compiler must know whether the number represents seconds, milliseconds, microseconds, or nanoseconds.

Field names are source-specific

The profile can use names such as:

price
px
quantity
size
ts
timestamp

The normalization mapping then identifies which raw field supplies the canonical value.

Positional CSV Fields

Headerless CSV requires explicit field positions.

For example:

10001,100,0.5

A profile can declare:

[fields.id]
type = "integer"
position = 1

[fields.price]
type = "decimal"
position = 2

[fields.qty]
type = "decimal"
position = 3

Important: positions are 1-based

The first column is:

position = 1

not zero.

Positions must be unique

Two fields cannot claim the same positional column.

Positions must be contiguous

For a three-column file, the declared positions must cover:

1, 2, 3

A declaration using:

1, 3, 5

is invalid.

Why declare unused columns?

For headerless CSV, every physical column must be represented when positional declarations are used.

For example:

id,ignored,price,quantity

If the file has four physical columns, the positional field declarations must account for all four.

A column does not need to be mapped to canonical output merely because it is declared.

Does TOML field order matter?

No.

Writing [fields.price] before [fields.id] does not establish the physical CSV order.

Use explicit position values.

Can I mix positioned and unpositioned fields?

Not under the described positional contract.

If any declared field uses a position, all declared fields must have positions covering the complete contiguous range.

Supported Raw Field Types

The current schema accepts these type names:

decimal
integer
string
array
boolean
integer/string
uuid/string
integer/bool
string/integer
signed_integer
signed_decimal

Why are there several numeric types?

Sources can represent numeric values differently.

For example:

{"quantity": 10}

uses a JSON number.

Another source may use:

{"quantity": "10"}

which is a string.

A combined type declaration can describe an appropriate supported source representation.

Signed values

Some feeds encode information using signed numbers.

For example:

+10
-10

A signed quantity may represent an amount and an operation or side.

The source field type must reflect the actual representation.

Does declaring a field type create arbitrary transformations?

No.

A field type describes how the source value is represented.

It does not automatically enable arithmetic formulas, custom parsers, or arbitrary expression evaluation.

Only the transformations supported by the relevant Rust decoder are available.

Additional Field Metadata

Besides type, the schema supports field metadata keys such as:

encoding
position
precision
fractional_digits
observed_effective_precision
values
level_format
ordering
decode
update_precision
snapshot_precision
level_fields

Why are these fields optional?

Different source formats need different metadata.

For example, a timestamp field may require:

encoding = "unix_nanoseconds"

An array of order-book levels may require:

level_format = ["price", "quantity"]

A source precision declaration may use supported precision metadata.

Does every field support every property?

No.

The keys must be used according to the relevant source decoder and semantic compiler.

For example, adding:

decode = "json"

does not make arbitrary JSON arrays embedded in CSV cells executable.

Does values create event filters?

No.

A field's descriptive values metadata does not replace an executable event_filter.

For depth rules, event selection must use the supported normalization-rule filtering contract.

Nested JSON Fields

Some JSONL sources contain nested objects.

For example:

{
  "data": {
    "ts": 1767225600000
  }
}

The relevant field is:

data.ts

In TOML, declare the dotted name using a quoted table key:

[fields."data.ts"]
type = "integer"
encoding = "unix_milliseconds"

Then reference it:

[normalization.event_timestamp]
field = "data.ts"

Why quote the field name?

Without quotes, TOML interprets dots as table nesting.

The quoted declaration makes:

data.ts

one raw field name in the profile.

Is this a general JSONPath implementation?

No.

The supported depth JSON reader resolves simple dotted object paths.

It does not provide:

  • JSONPath wildcards.
  • Arbitrary array-index expressions.
  • Computed selectors.
  • General JSON queries.

Use the source paths supported by the relevant decoder.

Timestamp Encoding

Why Timestamp Units Matter

Financial market data often uses integer timestamps.

However, different sources use different units.

For example:

1767225600

may represent Unix seconds.

1767225600000

may represent Unix milliseconds.

1767225600000000

may represent Unix microseconds.

1767225600000000000

may represent Unix nanoseconds.

All four can describe the same instant.

If Rust interprets the wrong unit, the resulting event time will be incorrect.

Why is this dangerous?

The resulting timestamp may still be a valid integer.

However, it may represent an entirely different date or overflow the supported range.

Incorrect timestamps can affect:

  • Event ordering.
  • Historical intervals.
  • Trade and depth alignment.
  • Stream reconciliation.
  • Market replay.
  • Backtesting.

Timestamp encoding must therefore be explicit.

Supported Timestamp Encodings

The schema supports:

Encoding Source representation
unix_seconds Seconds since the Unix epoch.
unix_milliseconds Integer milliseconds.
unix_microseconds Integer microseconds.
unix_nanoseconds Integer nanoseconds.
iso8601_nanoseconds Timezone-qualified ISO 8601 string with up to nine fractional digits.

Unix milliseconds

For example:

[fields.timestamp]
type = "integer"
encoding = "unix_milliseconds"

Unix nanoseconds

[fields.timestamp]
type = "integer"
encoding = "unix_nanoseconds"

ISO 8601

For example:

[fields.timestamp]
type = "string"
encoding = "iso8601_nanoseconds"

The source value must include an explicit UTC offset or Z.

Fractional seconds

The unix_seconds encoding supports fractional seconds when their value can be represented exactly in nanoseconds.

What does Rust produce?

The normalization engine converts supported source timestamps into canonical nanosecond values.

This provides a consistent timestamp representation across different source formats.

Where Timestamp Encoding Belongs

Timestamp encoding is declared on the raw field.

For example:

[fields.time]
type = "integer"
encoding = "unix_milliseconds"

[normalization.event_timestamp]
field = "time"

Why not declare it inside normalization?

The schema-2 compiler derives the timestamp encoding from the referenced raw field.

Do not add:

timestamp_encoding = "unix_milliseconds"

to [normalization].

That is not the supported schema-2 authoring pattern.

Event and receive timestamps

Some sources contain both an exchange event timestamp and a receive timestamp.

If ISO 8601 encoding is used for either mapped timestamp, the current contract requires ISO 8601 encoding for both mapped timestamp fields.

Can I infer the timestamp unit from the exchange name?

No.

Different archive products from the same exchange may use different timestamp encodings.

Use the actual source-format specification and representative records.

Quantity Encoding

Why Quantity Units Matter

Consider a trade containing:

Price:    80,000
Quantity: 100

The quantity could represent:

  • 100 BTC.
  • 100 USDT.
  • 100 contracts.

These interpretations are economically different.

A profile must explicitly declare the raw quantity denomination.

Supported encodings

Encoding Meaning
base Quantity is expressed in base-asset units.
quote Quantity is expressed in quote-asset units.
contracts Quantity counts derivative contracts.

Example

[normalization]
target = "trade"
quantity_encoding = "base"

This tells Rust that the source trade quantity is denominated in base units.

Base and Quote Quantities

Suppose a trade has:

Price:    100
Quantity: 0.5 base units

Its quote quantity is:

100 × 0.5 = 50 quote units

Base quantity

For example:

quantity_encoding = "base"

The source quantity represents base units.

Quote quantity

For example:

quantity_encoding = "quote"

The source quantity represents quote units.

Why does Engine need to know?

For trades, the supported normalization can derive the corresponding base or quote quantity using the execution price.

The correct direction depends on the source denomination.

Does the profile need to specify a custom formula?

No.

The supported quantity normalization handles the declared encoding according to its fixed interpretation rules.

The profile does not provide a general-purpose arithmetic expression language.

Contract Quantities

Derivative sources may express quantities as contract counts.

For example:

quantity_encoding = "contracts"

Why is contract normalization different?

Suppose a source reports:

Quantity: 100 contracts

Without a contract multiplier, the economic quantity is unknown.

Required instrument metadata

Contract normalization requires authoritative instrument information, including:

  • Positive contract value.
  • Contract-value denomination.
  • Applicable instrument identity.
  • Relevant historical specifications.

Where is this information supplied?

Through the instrument catalogue and concrete processing job.

It should not be invented inside a reusable format profile.

Why not hardcode one multiplier?

Different contracts may have different values.

For example, two futures contracts can share a source layout while using different contract multipliers.

The profile can describe their common field format.

The catalogue describes each contract's economic properties.

Spot restrictions

Spot profiles cannot use:

quantity_encoding = "contracts"

This is rejected by the supported schema.

Trade-Side Transformations

Why Trade-Side Transformations Matter

Different sources represent buy and sell information differently.

For example:

buy / sell

or:

B / S

or:

true / false

Some sources encode side through the sign of a quantity.

A profile must explicitly describe how its native values map to canonical sides.

Supported canonical values

The relevant side mappings use:

buy
sell
unknown

An unknown side should only be used when it reflects the actual source semantics.

It is not a general replacement for unrecognized values.

Case-Folding Text Sides

For a source already containing buy/sell text:

[normalization.side]
field = "side"
transform = "casefold"

The current implementation accepts the documented forms:

buy
Buy
BUY

sell
Sell
SELL

Does casefold trim whitespace?

Do not depend on that behavior.

For example:

" buy "

is not automatically guaranteed to be accepted.

Does it support arbitrary mixed-case strings?

No.

Use the explicitly supported vocabulary.

When should I use it?

Use casefold when the source already represents the canonical buy/sell concept using one of the supported text forms.

For coded or Boolean fields, use an explicit mapping.

Map Coded Sides

Suppose a source uses:

B
S

You can declare an explicit mapping.

For example:

[normalization.side]
field = "side"
transform = "map"

[normalization.side.values]
b = "buy"
s = "sell"

Why use lowercase keys?

The compiler requires mapping keys to use the supported lowercase representation.

What if the source contains an unmapped value?

An absent or unmapped source side is invalid.

For example, if the source contains:

N

but the profile only defines B and S, do not assume the compiler will silently interpret N as unknown.

If the source legitimately supports an unknown aggressor-side value, declare its supported mapping explicitly.

Why not default every unexpected value to unknown?

Because unexpected values may indicate a source-format problem.

For example, a new side code could have a meaning not represented by the existing profile.

Silently accepting it would hide that incompatibility.

Boolean Side Mappings

Some sources represent trade-side information through Boolean fields.

For example:

true
false

The synthetic trade example uses:

[normalization.side]
field = "is_buyer_maker"
transform = "map"

[normalization.side.values]
true = "sell"
false = "buy"

Why is this mapping source-specific?

A Boolean field can represent different concepts.

For example, a provider may report whether the buyer was the maker.

Another source may use a field describing whether the aggressor was the buyer.

Those fields require different interpretations.

Do not use this mapping unless it matches the actual source contract.

Signed Quantity Transformations

Some feeds encode trade direction using the sign of a quantity.

For example:

+10 → Buy
-10 → Sell

In this situation, the source quantity contains two pieces of information:

  1. Trade magnitude.
  2. Trade direction.

MarketForge supports separating them through two mappings.

Quantity magnitude

[normalization.quantity]
field = "size"
transform = "abs"

This takes the magnitude of the original signed value.

Side from sign

[normalization.side]
field = "size"
transform = "sign_to_side"
positive = "buy"
negative = "sell"

Why use the same source field twice?

Both mappings read the original raw value.

For example:

size = -10

produces:

Quantity magnitude = 10
Side = Sell

What about zero?

A zero value has no positive or negative sign.

Therefore, zero cannot establish a trade side through this transformation alone.

Can I write arbitrary arithmetic expressions?

No.

The current transformation vocabulary is fixed.

The profile does not support arbitrary:

  • Multiplication formulas.
  • Custom functions.
  • Default-value expressions.
  • User-defined transformations.

Use only supported transformations.

Optional Trade Flags and Identifiers

Optional RPI Flag

Some trade sources provide information about retail price improvement or a related source-specific flag.

The supported optional normalization field is:

optional.is_rpi

Boolean-like source field

For example:

[normalization.optional.is_rpi]
field = "RPI"
transform = "bool"

Equality-based source code

If the source uses an integer code:

[normalization.optional.is_rpi]
field = "source"
transform = "equals"
value = 1

Why use explicit transformations?

Different sources represent optional flags differently.

For example:

true / false

is not identical to:

1 / 0

under every possible source interpretation.

The profile must use the supported transformation matching the actual field semantics.

Does the source field need to be declared?

Yes.

For example:

[fields.RPI]
type = "boolean"

must exist when the mapping references RPI.

A normalization mapping cannot reference an undeclared field.

Trade IDs and Identity Scope

Many exchanges provide native trade identifiers.

For example:

Trade ID: 10001

However, the presence of a trade ID does not establish how unique that identifier is.

Why does uniqueness matter?

Imagine two historical archive files both contain:

Trade ID 10001

Are these the same execution?

Not necessarily.

The source may reset identifiers between files.

The IDs may only be unique within one instrument.

Or the provider may use an identifier that does not reliably represent one execution.

Mapping versus scope

The field mapping identifies where the trade ID appears.

For example:

[normalization.trade_id]
field = "id"

The identity scope describes where that identifier is trustworthy.

These are different responsibilities.

Supported Trade ID Scopes

The source section supports several trade identity contracts.

Scope Meaning Reset domain
global IDs have the declared global uniqueness contract. Omit
instrument_scoped IDs are scoped to a concrete instrument and declared reset domain. Required
ordered_run IDs are meaningful within a checked, non-reset run of one concrete stream. Required
source_local IDs are local to a source and do not establish cross-source uniqueness. Omit
unreliable IDs cannot be trusted as reliable event identities. Omit

Global identity

For example:

trade_id_scope = "global"

Only use this when the source actually guarantees the relevant global uniqueness contract.

Instrument-scoped identity

trade_id_scope = "instrument_scoped"
trade_id_reset_domain = "instrument_lifetime"

The reset-domain value is illustrative and must be supported by the actual source semantics.

Ordered-run identity

An ordered-run identity describes IDs that are reliable within a checked sequence of one concrete stream.

The applicable reset domain must be explicitly supplied.

Source-local identity

trade_id_scope = "source_local"

This does not establish uniqueness across unrelated source files.

Unreliable identity

trade_id_scope = "unreliable"

Use this when source IDs cannot be trusted as reliable event identities.

Trade ID Validation Rules

The scope declaration must satisfy its supported contract.

Explicit ID mapping

An explicit native trade identity contract requires the corresponding:

[normalization.trade_id]
field = "id"

mapping.

Reset-domain requirements

A reset domain is required for:

instrument_scoped
ordered_run

It must be omitted for:

global
source_local
unreliable

A reset domain without the corresponding scope is invalid.

Why not assume equal records are duplicates?

Two trades can have:

Same timestamp
Same price
Same quantity

without representing the same execution.

Similarly, equal native trade IDs do not establish cross-source identity unless the declared source contract supports that conclusion.

Why is this important for reconciliation?

Trade reconciliation may need to determine whether source observations represent the same event.

Unreliable identity assumptions can cause legitimate trades to be removed or unrelated events to be combined.

Declare only the identity guarantees actually established by the source.

Depth Normalization Rules

Shared Mappings and Operation Rules

Depth profiles can declare mappings shared by all supported operations.

For example:

[normalization]
quantity_encoding = "base"

[normalization.event_timestamp]
field = "timestamp"

[normalization.bids]
field = "bids"

[normalization.asks]
field = "asks"

These mappings apply to the profile's normalization rules.

Rule-specific configuration

Each operation is declared using:

[[normalization.rules]]

For example:

[[normalization.rules]]
target = "l2_snapshot"

or:

[[normalization.rules]]
target = "l2_update"

Why separate common mappings from rules?

Both snapshots and updates may use the same source timestamp and bid/ask fields.

There is no need to repeat identical mappings inside every rule.

However, their operation semantics differ.

Can rules override common mappings?

No.

A rule cannot override a mapping already declared in the common normalization section.

This restriction applies even when the repeated value is identical.

Why?

Allowing ambiguous overrides could make it unclear which mapping the compiler should use.

The current schema requires one unambiguous interpretation.

Single Target vs. Multiple Rules

A normalization profile must use one supported normalization structure.

Single target

For example:

[normalization]
target = "l2_snapshot"
quantity_encoding = "base"

This is a fragment illustrating the target declaration.

A complete profile still needs the appropriate fields and snapshot semantics.

Multiple rules

Alternatively:

[[normalization.rules]]
target = "l2_snapshot"

[[normalization.rules]]
target = "l2_update"

This is also only a structural fragment.

The corresponding filters and operation settings are still required.

Can I use both?

No.

Do not declare both:

normalization.target

and:

normalization.rules

in the same profile.

Can I repeat a target?

No.

For example, two separate rules both targeting:

l2_snapshot

are rejected.

The current catalogue does not allow several snapshot rules distinguished only by different event filters.

What about the TOML location?

Use:

[[normalization.rules]]

Do not use a top-level:

[[rules]]

array.

That is not the schema-2 authoring structure.

Event Filters

For JSON/event depth processing, the compiler needs to know which rule applies to each source record.

For example:

{"type":"snapshot"}

should select the snapshot rule.

Meanwhile:

{"type":"delta"}

should select the update rule.

Equality filter

Use:

[normalization.rules.event_filter]
field = "type"
equals = "snapshot"

This matches the exact string:

snapshot

Set-membership filter

Use:

[normalization.rules.event_filter]
field = "type"
in = ["delta", "update"]

This matches either of the listed strings.

Important rules

A filter must reference a declared raw source field.

It must use exactly one supported filter form:

equals

or:

in

The filter values are strings.

Matching is exact.

Every Event Must Match Exactly One Rule

For JSON/event depth profiles, every record must match exactly one normalization rule.

Valid example

type = snapshot → Snapshot rule

type = delta    → Update rule

Each record has one matching rule.

Invalid: no matching rule

Suppose the source contains:

{"type":"reset"}

but the profile only supports snapshot and delta.

The record matches no rule.

This is an error.

Invalid: multiple matching rules

Suppose two rules both accept:

delta

The record matches more than one rule.

This is also an error.

Does rule order resolve ambiguity?

No.

The rule list does not use first-match precedence.

A record matching multiple rules is rejected rather than assigned to whichever rule appears first.

Why is this important?

Order-book operations have different effects.

A snapshot may replace the current book state.

An incremental update modifies existing state.

Ambiguous event classification could corrupt reconstruction.

Use disjoint filters that cover the actual intended source records.

Order-Book Level Layouts

Two Ways to Represent Depth Levels

Supported depth profiles can describe levels through:

  1. Bid and ask arrays.
  2. Scalar price, quantity, and side mappings.

These are different physical representations.

Array-based source

For example:

{
  "bids": [["99", "2"]],
  "asks": [["101", "3"]]
}

Scalar source

For example:

timestamp,side,price,quantity
1767225600000,bid,99,2

The latter is an illustrative physical record.

Actual scalar source processing requires a compatible implemented decoder and operation rules.

Mapping requirements

A depth mapping must provide either:

Both bids and asks

or:

Price, quantity, and side

Do not mix incomplete fragments from both approaches and expect the compiler to infer missing semantics.

Positional Array Levels

A common depth format stores each level as:

[price, quantity]

For example:

["99", "2"]

The profile can declare:

[fields.bids]
type = "array"
level_format = ["price", "quantity"]

The same applies to asks.

Why declare level order?

Different providers may use different array element positions.

For example, one source may store:

[price, quantity]

while another could use a different supported layout.

The profile identifies the meaning of each element.

Supported positional layouts

The current compiler supports:

level_format = ["price", "quantity"]

and:

level_format = ["price", "quantity", "order_count"]

What is order count?

Some depth sources include the number of orders represented at a price level.

For example:

["99", "2", 4]

This could describe:

Price: 99
Quantity: 2
Order count: 4

when that interpretation is established by the source.

Does the profile need explicit array indexes?

No.

The compiler derives the supported extraction indexes from level_format.

Object-Based Depth Levels

Some JSON sources represent each level as an object.

For example:

{
  "p": "99",
  "q": "2"
}

The profile can declare the property names.

[fields.bids]
type = "array"

[fields.bids.level_fields]
price = "p"
quantity = "q"

[normalization.bids]
field = "bids"

Why use level_fields?

The source uses named properties rather than positional array elements.

The mapping explains which property supplies each canonical level value.

Required fields

The supported object-level declaration requires:

price
quantity

It can also include:

order_count

What about asks?

Provide the corresponding ask declaration.

For example:

[fields.asks]
type = "array"

[fields.asks.level_fields]
price = "p"
quantity = "q"

[normalization.asks]
field = "asks"

What if both sides come from one shared array?

The supported mapping contract may require separate level-field declarations under each normalization side.

Use the structure expected by the source-specific decoder.

Do not assume that one shared field declaration automatically establishes the interpretation of both sides.

Snapshot and update semantics

What Is an Order-Book Snapshot?

A snapshot represents an observed order-book state.

For example:

Bids:
99 → 2
98 → 1

Asks:
101 → 3
102 → 4

This provides a starting state for supported order-book reconstruction.

Why does a snapshot matter?

Incremental updates often require a known prior book state.

For example:

Delete bid at 99

only makes sense in the context of an existing book.

Without the required initialization, the reconstructed state may be unreliable.

Does every snapshot contain the full order book?

No.

A provider may publish a bounded top-N observation rather than every available price level.

The profile must describe the actual source semantics.

Supported Snapshot Types

The current schema supports several snapshot types.

Type Meaning
single_event A complete snapshot represented by one event.
single_row A supported snapshot represented by one row.
group_rows A snapshot assembled from several rows.
bounded_observation A top-N state represented by one chronological JSONL message.

Single event

For example:

[normalization.rules.snapshot]
type = "single_event"

This is used by the complete synthetic JSONL example.

Single row

[normalization.rules.snapshot]
type = "single_row"

Use this only with a compatible supported row layout.

Grouped rows

[normalization.rules.snapshot]
type = "group_rows"
group_by = "timestamp"

This groups several source rows into one snapshot according to the declared raw field.

Why is group_by necessary?

The Engine needs to know which rows belong to the same observation.

For example, several levels may share one timestamp.

The group field must be declared in [fields].

Bounded Observations

Some providers publish one top-N order-book observation per message.

For example, a source might record only the best ten bids and ten asks.

This is different from a complete full-depth book snapshot.

Supported representation

The corresponding snapshot type is:

type = "bounded_observation"

Required depth information

The configured levels_per_side must match:

source.maximum_depth_per_side

Why require agreement?

The compiler needs a consistent description of the source's bounded depth.

For example, a top-ten observation should not silently be interpreted as a top-twenty observation.

Why is bounded depth important?

A bounded observation cannot establish liquidity outside its recorded levels.

For example, a top-ten book does not describe the entire market depth.

Downstream research should preserve that limitation.

Sequence behavior

For the supported bounded-observation path, a mapped sequence_start can use:

sequence_order = "nondecreasing"

This allows repeated sequence values and forward jumps while rejecting decreases, according to the supported bounded-observation rules.

Do not confuse this with ordinary consecutive incremental-update sequencing.

Does this apply to every depth source?

No.

Bounded-observation behavior belongs to the specific supported decoder and snapshot contract.

Use the appropriate existing profile as a reference.

Incremental Update Semantics

Why Updates Need Explicit Semantics

An incremental order-book update describes a change to the current book.

However, the numerical meaning of an update can differ by provider.

For example:

Price: 99
Quantity: 5

could mean:

Absolute update

Set the quantity at price 99 to 5.

Or:

Relative update

Increase the quantity at price 99 by 5.

These are very different operations.

The profile must declare the correct interpretation.

Absolute Level Updates

The synthetic depth profile uses:

[normalization.rules.update_semantics]
type = "absolute_level"
zero_quantity = "delete"
nonzero_quantity = "set"

What does this mean?

A nonzero quantity replaces the current quantity at the price level.

For example:

Existing:
Price 99 → Quantity 2

Update:
Price 99 → Quantity 5

The resulting quantity is:

5

not:

7

Zero quantity

Under the declared rule:

zero_quantity = "delete"

a zero quantity removes the corresponding price level.

For example:

Price 99 → Quantity 0

deletes that level.

Why is this explicit?

The semantics must match the actual source.

Do not assume every exchange uses zero in the same way without checking its format contract.

Relative Level Updates

Some sources express the amount by which a level changes.

For example:

Existing quantity: 10

Update: +3

Result: 13

Or:

Existing quantity: 10

Update: -3

Result: 7

The supported scalar CSV relative-update path can use:

[normalization.rules.update_semantics]
type = "relative_level"

action_source = "action"
add_action = "add"
subtract_action = "subtract"

emit = "resulting_absolute_level"

zero_result = "delete"
nonzero_result = "set"

Action source

action_source = "action"

identifies the raw field describing the update operation.

That field must be declared under [fields].

Add action

add_action = "add"

identifies the source value representing an addition.

Subtract action

subtract_action = "subtract"

identifies the source value representing a subtraction.

Output behavior

emit = "resulting_absolute_level"

requests the supported resulting absolute level representation.

Why distinguish zero and nonzero results?

A relative update can reduce the quantity to zero.

The profile must describe how that resulting state should be emitted.

Does this support arbitrary JSON relative updates?

No.

Relative updates are not generally implemented for array-based JSON events.

Use an existing supported scalar profile for the applicable path.

Sequence Numbers

Why Are Sequence Numbers Important?

Some order-book feeds include sequence numbers.

These can help establish the intended order of source updates.

For example:

Update 100
Update 101
Update 102

This appears to be a consecutive sequence.

However, other sources may use ranges or allow repeated sequence values.

Why not assume every counter is consecutive?

Because different feeds assign different meanings to their sequence fields.

For example, one counter might identify:

  • Individual messages.
  • Exchange update groups.
  • Source batches.
  • Snapshot generations.
  • Ranges of underlying updates.

A numeric field is not automatically a consecutive event counter.

The profile must reflect the source's actual contract.

Supported Sequence Policies

The runtime derives its sequence policy from the declared mappings.

sequence_start sequence_count Interpretation
Absent Absent Unsequenced.
Present Absent Consecutive sequence.
Present Present Ranged sequence.
Absent Present Invalid configuration.

Unsequenced source

If neither mapping is declared, the source is treated as unsequenced under this contract.

Consecutive source

If sequence_start is mapped without sequence_count, the runtime uses the corresponding consecutive-sequence policy.

Ranged source

If both mappings are present, the runtime uses the corresponding ranged-sequence policy.

Invalid combination

Declaring sequence_count without sequence_start is invalid.

Consecutive Sequence Mapping

For a source with a supported consecutive sequence:

[normalization.sequence_start]
field = "update_id"

The raw field must also be declared.

For example:

[fields.update_id]
type = "integer"

Why does this change runtime behavior?

The Engine can use the declared sequence information when evaluating continuity.

For example, an unexpected sequence gap may be relevant to reconstruction integrity.

Does a gap always mean missing market data?

The meaning depends on the source's documented sequence domain.

Do not declare consecutive sequencing unless the source actually guarantees that relationship.

Ranged Sequence Mapping

Some sources represent several updates using one sequence range.

For example:

[normalization.sequence_start]
field = "begin_id"

[normalization.sequence_count]
field = "merged_count"

The relevant raw fields must also be declared.

Why include a count?

The count helps describe the range of native updates represented by a source record.

Does every source use the same range convention?

No.

Use the actual source semantics.

The field names and values must correspond to the supported decoder's interpretation.

Can one depth task mix sequence policies?

No.

All rules in one depth task must imply the same sequence policy.

For example, you cannot freely combine one unsequenced rule with another requiring consecutive sequences under the same task contract.

Why Empty Sequence Mappings Are Dangerous

Do not add a mapping merely as a placeholder.

For example, do not declare:

[normalization.sequence_start]

unless the field mapping and its semantics are actually required and supported.

Why?

The presence of a sequence mapping changes the runtime's policy selection.

It is not simply documentation.

For example:

No sequence mapping

and:

Sequence mapping present

can lead to different Engine behavior.

What if the source has a counter but its meaning is unknown?

Do not invent a continuity guarantee.

Investigate the source documentation.

A wrong sequence policy can reject valid data or incorrectly accept invalid reconstruction.

Additional Book Metadata

What Is normalization.book?

The schema supports optional book-related metadata under:

normalization.book

This section uses a restricted supported vocabulary.

Why is it separate?

Some sources require additional book-level interpretation information.

However, this metadata is not a replacement for the executable normalization mappings.

Important limitations

Optional book metadata does not:

  • Replace sequence_start.
  • Replace sequence_count.
  • Create arbitrary depth truncation.
  • Enable unsupported reconstruction behavior.
  • Allow custom book-processing expressions.

How should I author it?

Start from an existing compatible profile.

Preserve the actual supported field names and values.

Validate the completed definition through the production compiler.

Do not invent new metadata keys merely because they seem useful for order-book processing.

Mixed-Instrument Sources

Why Can One Source Contain Several Instruments?

Some historical archives contain records for multiple contracts.

For example, an OKX futures-family archive may contain several dated futures.

A source record may therefore include its own native instrument identifier.

Example

{
  "data": {
    "s": "BTC-USD-261225"
  }
}

The native symbol identifies the concrete instrument represented by the record.

Why does this matter?

A family-level archive path may identify:

BTC-USD

while individual records identify specific contracts.

MarketForge needs the concrete instrument identity to apply the correct specifications.

Map Native Instrument Identity

A supported profile can expose the native instrument field.

For example:

[fields."data.s"]
type = "string"

[normalization.instrument]
field = "data.s"
lookup = "catalog"

What does this do?

It tells the supported decoder where to obtain the native instrument identity.

The lookup connects that value to the instrument definitions available through the processing contract.

Does lookup = "catalog" contact the exchange?

No.

It does not fetch missing instrument specifications from a remote provider.

The concrete instruments and their historical economic information must already be available to the job.

What if an instrument cannot be resolved?

The corresponding processing path may reject or filter records according to its supported identity and selection rules.

Do not assume that every native symbol can be mapped automatically.

Mixed-Instrument Format Limitations

The current runtime supports specific mixed-instrument identity paths.

JSONL

Supported JSONL trade and depth readers can use the appropriate native instrument mapping.

For example:

[normalization.instrument]
field = "data.s"
lookup = "catalog"

when the source layout and decoder support that path.

CSV

Family routing supports specific CSV identity paths.

Trade CSV identity extraction has its own supported header-recognition behavior.

Do not assume every CSV column named symbol is automatically suitable.

XLSX

The current runtime rejects mixed-instrument XLSX family routing.

Why is this important?

A profile declaration cannot add a new decoder implementation.

The Rust Engine must actually support the source format and identity-routing mechanism.

A valid instrument identity declaration alone is insufficient.

XLSX Profiles

Why Is XLSX Support Specialized?

Some historical providers distribute data in spreadsheet workbooks.

For example, a depth recording might contain one row per snapshot, with bid and ask information stored in worksheet cells.

MarketForge supports a specific XLSX normalization path.

However, this is not a general-purpose spreadsheet processing engine.

Current requirements

The supported XLSX layout requires:

  • One worksheet.
  • Headers.
  • Exact supported field names.
  • Unix-second timestamps.
  • Supported ascending timestamp sorting.

Required field names

The fixed layout uses:

timestamp
asks
bids

These names must match the supported workbook contract.

Why does this matter?

An arbitrary workbook containing similar information under different sheet names or columns is not automatically compatible.

The current decoder supports a defined structure.

XLSX Ordering

The supported workbook path uses:

[normalization.input_ordering]
order = "ascending"
sort_by = "timestamp"

Why is sorting needed?

Some workbook recordings may not be stored in chronological order.

The supported path can apply its defined ascending timestamp ordering.

Does this allow arbitrary sorting for every source?

No.

The workbook sorting path has its own implementation constraints.

It does not enable general timestamp sorting for stateful incremental depth feeds.

Timestamp encoding

The supported XLSX layout uses:

encoding = "unix_seconds"

for its timestamp field.

Worksheet count

The source declaration requires:

workbook_sheets = 1

Where should I start?

Use the existing compatible workbook profile as the starting point.

Do not assume that changing field names or adding declarations enables arbitrary XLSX layouts.

Gate.io Feed Variants

Why Does Gate.io Need Feed Variants?

Gate.io supports distinct historical depth feeds.

For example:

Incremental Depth
Snapshot Depth

These formats can use different source layouts and reconstruction semantics.

The profile catalogue therefore supports explicit Gate.io depth feed variants.

Why not install two unrelated profiles?

The current profile identity contains only:

exchange.instrument_type.market_category.data_type

It does not provide a general fifth component for arbitrary feed variants.

Gate.io uses a supported explicit feed-selection mechanism instead.

Variant Structure

Gate.io depth profiles can contain:

feeds.snapshot
feeds.incremental

Each variant provides its own complete declarations.

Conceptually:

Gate.io Depth Profile
        |
        +-- Top-Level Definition
        |      |
        |      +-- source
        |      +-- fields
        |      +-- normalization
        |
        +-- Snapshot Variant
        |      |
        |      +-- source
        |      +-- fields
        |      +-- normalization
        |
        +-- Incremental Variant
               |
               +-- source
               +-- fields
               +-- normalization

Why must variants be complete?

Variant definitions are not partial overlays.

For example, a snapshot variant cannot omit an essential source declaration and expect it to be inherited automatically from the top-level default.

Each variant supplies its own complete interpretation.

Does the top-level profile still need its own sections?

Yes.

The top-level profile must still contain its required source, fields, and normalization declarations.

Can other exchanges use arbitrary variants?

No.

The current feed-variant mechanism is a supported Gate.io depth feature.

Do not assume that adding:

feeds.custom

to another exchange profile creates a valid selectable format.

How is the feed selected?

The corresponding supported source selection can declare the intended Gate.io feed.

For example, acquisition configuration supports:

[requests.source_options]
feed = "snapshot"

or:

[requests.source_options]
feed = "incremental"

The selected feed must match the source archive and its installed interpretation.
