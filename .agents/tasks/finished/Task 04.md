**Project:** MarketForge

**Status:** Approved for implementation  
**Dependencies:** Task 01 — Shared Historical Runtime Configuration; Task 02 — Production V3 Batch Loading and Unified Normalization Profiles; Task 03 — Shared Normalization Test Infrastructure and Persistent Outputs  
**Next task:** Source-Error Handling and Timestamp-Ordering Enforcement

## 1. Objective

Correct the historical normalization engine's integrity observation accounting and time-window attribution so that configured integrity thresholds are evaluated using accurate, meaningful data.

The current engine already contains substantial integrity-policy infrastructure, including:

- Integrity categories.
- Eligible observation counters.
- Violation counters.
- Global integrity statistics.
- Source-file integrity statistics.
- Stream-scoped integrity statistics where supported.
- Hourly and daily integrity windows.
- Count thresholds.
- Rate thresholds.
- Minimum-sample requirements.
- Failure and degradation actions.

However, previous code inspection identified gaps between the integrity evaluator and the observations supplied by processing workers.

**The objective is to make the existing integrity guarantees accurate without redesigning the integrity-policy system.**

This task focuses on two problems:

1. Incorrect or incomplete eligible-observation accounting.
2. Missing or misleading timestamp attribution for integrity failures.

Do not implement the other correctness fixes during this task.

Complete only Task 04.

# 4. Define Eligible Observation Semantics

The integrity model calculates rates using:

```text
violation_rate = violations / eligible_observations
```

This is only meaningful when the denominator represents the population actually eligible for the corresponding integrity check.

### Example

Suppose a source contains:

```text
999 successfully parsed records
1 malformed record
```

The correct parsing observation accounting is:

```text
eligible_observations = 1000
violations = 1
violation_rate = 0.001
```

The following is incorrect:

```text
eligible_observations = 1
violations = 1
violation_rate = 1.0
```

It is also incorrect to report:

```text
eligible_observations = 999
violations = 1
```

because the failed parsing attempt belongs to the eligible population.

### Required Semantics

An eligible observation represents an actual attempt to perform the corresponding integrity check.

A successful observation represents an applicable check that passed.

A violated observation represents an applicable check that failed.

Do not count checks that were never reached.

For example:

```text
Record read
    │
    ▼
JSON parsing succeeds
    │
    ▼
Quantity transformation fails
```

This record should contribute:

```text
ParseFailure:
    eligible += 1
    violations += 0

TransformationFailure:
    eligible += 1
    violations += 1
```

It must not disappear from the parsing denominator simply because normalization ultimately failed.

### Category-Specific Eligibility

Do not assume every integrity category uses the same denominator.

The correct observation unit depends on the corresponding check.

Examples:

| Integrity category | Eligibility principle |
|---|---|
| `parse_failure` | An applicable parsing attempt |
| `invalid_record` | A record reaching the relevant validation stage |
| `transformation_failure` | An applicable normalization/transformation attempt |
| `sequence_gap` | A source event for which the declared sequence-continuity check is applicable |
| `timestamp_regression` | A timestamp comparison that is actually applicable under the ordering contract |
| `missing_snapshot` | A depth event or state transition where initialization requirements can be checked |
| `invalid_book` | An applicable order-book state validation |

These are conceptual rules.

Inspect the existing definitions and processing stages before finalizing their exact counting semantics.

Do not introduce artificial successful observations for checks that the engine never performed.

### Deliverable

Establish a clear, documented eligibility definition for every integrity category currently supported by the normalization engine.

Prefer concise Rust documentation close to the relevant types or accounting functions.

Do not introduce a separate configuration file solely for these definitions.

# 6. Correct Depth Integrity Accounting

Depth processing is more complex because one source event may produce multiple canonical level updates.

The engine must distinguish:

```text
Physical source records
Accepted source events
Canonical level updates
Integrity observations
```

These are separate quantities.

### Example

One valid depth snapshot may produce:

```text
1 accepted source event
500 canonical level rows
```

This must not automatically produce 500 successful source-message parsing observations.

The correct number of parsing observations depends on the physical source format.

### Required Behavior

Inspect and correct observation accounting for the supported depth input paths.

These may include:

```text
JSONL depth
CSV depth
XLSX depth
```

Use the actual supported production formats.

### JSONL Depth

A complete JSONL message represents a parsing attempt.

Record successful parsing observations when parsing succeeds.

Record violations when parsing fails.

Preserve the distinction between parsing, normalization, and depth reconstruction checks.

Do not count one source event multiple times merely because it produces many canonical levels.

### CSV Depth

Some CSV depth formats contain scalar rows that are assembled into one logical snapshot.

For example:

```text
100 source rows
        │
        ▼
1 assembled depth snapshot
        │
        ▼
100 canonical levels
```

A row-level parsing check and an assembled-snapshot validation do not necessarily share the same denominator.

Define their eligibility separately.

Do not count the assembled snapshot as 100 independent sequence-continuity checks unless that is genuinely what the source semantics require.

### XLSX Depth

Apply the same principle to XLSX processing.

If the decoder produces one logical source event per worksheet row, account for that event appropriately.

Do not assume every XLSX row represents one canonical level.

Do not modify the XLSX decoder's layout behavior during this task.

### No-Change Events

A valid depth event may produce zero canonical level changes.

For example:

```text
Source event accepted
Book state unchanged
Canonical levels emitted = 0
```

The event must still contribute to applicable integrity observations.

Do not use emitted canonical level count to decide whether the source event was checked.

### Missing Snapshots and Sequence Checks

Only record successful observations for checks that genuinely occurred.

For example, do not increment successful `sequence_gap` observations for an unsequenced feed merely because its events were accepted.

Likewise, do not record successful snapshot checks for unrelated trade events.

### Preserve Reconstruction Semantics

Do not change:

- Snapshot initialization.
- Snapshot replacement.
- Absolute updates.
- Relative updates.
- Sequence validation.
- Synchronization invalidation.
- Recovery behavior.
- Boundary tracking.
- Source-event indexing.
- Canonical level emission.

This task changes integrity observation accounting, not depth reconstruction algorithms.

# 7. Avoid Duplicate Integrity Observations

Integrity statistics may be collected at several levels:

```text
Task
    │
    ▼
Job
    │
    ▼
Dataset
```

The same observation must not be counted multiple times during aggregation.

### Required Rule

**Record an observation once at the stage where the check occurs.**

Then aggregate recorded observations.

Do not generate another successful or failed observation during job finalization.

Do not recount a task's observations when combining task results.

### Aggregation Invariants

For each category and applicable scope:

```text
eligible_total = sum(eligible_per_task)

violations_total = sum(violations_per_task)
```

where the tasks represent disjoint observations.

Aggregation must not lose observations or duplicate previously aggregated values.

Use checked arithmetic.

### Parallel Execution

The result must not depend on worker completion order.

For an equivalent workload and integrity policy:

```text
workers = 1
```

and:

```text
workers = 4
```

must produce equivalent applicable integrity observation totals.

Do not introduce shared mutable counters into worker hot paths when existing task-local accumulation and controlled aggregation are sufficient.

### Source Boundaries

Preserve source-specific attribution when tasks are combined into job-level statistics.

Do not collapse all task observations into one anonymous global counter before producing required source-level diagnostics.

# 8. Time-Window Attribution

The engine supports hourly and daily integrity windows.

These windows require trustworthy event timestamps.

### Existing Concern

The reviewed trade failure helper recorded integrity errors with:

```rust
event_timestamp_ns: None
```

The scoped integrity collector only populated hourly and daily windows when a timestamp was supplied.

This can exclude rejected records from the corresponding time-window statistics.

### Required Correction

When a rejected record has a trustworthy parsed event timestamp, preserve it.

Pass the timestamp into the integrity diagnostic and observation collector.

For example:

```text
Record received
    │
    ▼
Event timestamp parsed successfully
    │
    ▼
Price transformation fails
    │
    ▼
Integrity violation
    │
    ├── Global scope
    ├── Source-file scope
    ├── Stream scope, if established
    ├── Correct hourly window
    └── Correct daily window
```

The failure must contribute to the appropriate time windows.

### Timestamp Extraction

Reuse the existing timestamp parsing and normalization infrastructure.

Do not implement a separate, inconsistent timestamp parser merely for diagnostics.

Where possible, preserve a validated timestamp obtained before a later transformation fails.

Do not reparse the entire source record unnecessarily if an earlier stage already produced a trustworthy timestamp.

### Trustworthiness

Only assign a timestamp when it has been successfully interpreted under the applicable source configuration.

Do not fabricate timestamps.

Do not infer event time from:

- Processing wall-clock time.
- File modification time.
- Archive filename alone.
- Previous record timestamp.
- Next record timestamp.
- Current hour or date.

The timestamp must represent the rejected event itself.

# 9. Failures Without Trustworthy Timestamps

Some records are malformed before an event timestamp can be established.

For example:

```json
{
  "timestamp": "invalid",
  "price": "100.0"
}
```

Such a record cannot truthfully be assigned to a specific hourly or daily event-time window.

### Required Behavior

The failure must still contribute to applicable non-windowed integrity statistics.

For example:

```text
Global:
    violation recorded

Source file:
    violation recorded

Event-time window:
    unavailable
```

Do not silently discard the violation.

Do not assign an arbitrary timestamp.

### Explicit Unattributed Accounting

Introduce the smallest necessary mechanism to distinguish failures that cannot be attributed to an event-time window.

Conceptually:

```text
attributed_violations
unattributed_violations
```

These are illustrative names.

Inspect the existing metrics model before introducing new fields.

If an existing mechanism already provides equivalent information, reuse it.

### Window-Policy Guarantees

A window-based integrity policy must not claim complete verification when relevant violations could not be assigned to windows.

Determine the existing behavior and implement a conservative, explicit handling rule.

The preferred principle is:

**Do not report a window as fully validated when relevant observations are missing event-time attribution.**

If the existing policy system cannot truthfully evaluate the requested window guarantee, produce an explicit unsupported or indeterminate-policy failure rather than silently reporting success.

Do not invent a timestamp or silently drop the observation.

Do not change count or global-rate policy semantics merely to address missing window attribution.

### Compatibility

If persisted integrity metrics require additional fields:

- Keep the change minimal.
- Use the existing serialization conventions.
- Preserve existing fields.
- Update affected tests.
- Follow established protocol-versioning rules.
- Document any compatibility impact.

Do not redesign the complete metrics report.

# 10. Preserve Window Boundary Semantics

Inspect the existing implementation of hourly and daily windows.

Preserve its established UTC epoch-based boundary calculation.

### Example

A record with:

```text
2026-11-06T12:59:59.999999999Z
```

belongs to the hour beginning:

```text
2026-11-06T12:00:00Z
```

A record with:

```text
2026-11-06T13:00:00Z
```

belongs to the next hourly window.

Do not assign windows using local system timezone.

Do not use the developer's timezone.

Do not round timestamps before determining the correct window unless the existing contract explicitly requires it.

### Timestamp Units

Canonical event timestamps use nanoseconds.

Do not confuse:

```text
seconds
milliseconds
microseconds
nanoseconds
```

Reuse the production timestamp normalization logic.

### Negative Timestamps

Where supported by the current timestamp model, preserve correct epoch-based window behavior for negative timestamps.

Do not introduce incorrect integer division or modulo behavior around dates before the Unix epoch.

Use the existing window calculation if it already handles these cases correctly.


```toml

```

and hourly or daily thresholds.

### Preserve Existing Actions

Do not change the semantics of:

```text

```

In particular, preserve existing immediate-failure behavior.

If `action = "fail"` currently fails on the first applicable violation, it must continue doing so.

Do not reinterpret `max_count = 1000` as permission to accept 1,000 failures.

### Corrected Observations May Change Outcomes

Correcting denominator accounting may change rate-based policy evaluations.

For example:

```text
Previously:
    eligible = 1
    violations = 1
    rate = 100%

Corrected:
    eligible = 1000
    violations = 1
    rate = 0.1%
```

This is an intended correctness consequence.

It is not permission to weaken thresholds.

The policy evaluator should use the corrected observations without changing its unrelated rules.

### Immediate Versus Final Evaluation

Inspect how immediate worker-level enforcement and final job-level evaluation interact.

Ensure:

- Immediate failure remains immediate where required.
- Deferred thresholds use complete accumulated observations.
- Task aggregation does not double-count.
- Failed tasks preserve available diagnostics.
- A completed dataset has passed all required evaluations.

Do not silently disable checks inside workers unless the established architecture deliberately defers them to the correct job-level evaluation.

Do not change the failure boundary merely to simplify accounting.

# 12. Metrics and Counter Consistency

The engine already tracks processing counters.

Examples include:

```text
records_read
records_matched
records_processed
records_rejected
events_normalized
events_written
```

These counters must remain meaningful.

### Important Distinction

Integrity observation counts are not substitutes for processing counters.

For example:

```text
records_read = 1000
```

does not imply:

```text
parse_failure.eligible = 1000
```

unless every read record was subject to that exact parsing check.

Similarly:

```text
events_written = 500000
```

does not imply 500,000 depth source events were processed.

### Required Behavior

Ensure integrity accounting and processing counters remain internally consistent.

Do not require them to be numerically identical when their definitions differ.

Do not manipulate processing counters to obtain the desired integrity rate.

Preserve checked arithmetic and existing overflow protections.

### Error Paths

When an operation fails after some observations have been recorded, preserve the available integrity metrics.

Do not silently reset them because the job did not complete.

Do not report partial canonical output as a committed dataset.

# 13. Reusable Integrity Observation Helpers

Inspect existing helper functions before introducing new ones.

It may be useful to centralize repeated operations such as:

```text
record successful observation
record violated observation
record observation with timestamp
record observation without timestamp
```

However, avoid an overly generic framework.

### Design Principles

- Keep the API strongly typed.
- Preserve category-specific eligibility.
- Preserve source scope.
- Preserve optional event-time attribution.
- Make duplicate observations difficult to introduce.
- Use checked arithmetic.
- Keep processing hot paths efficient.

Do not force all categories through a helper that assumes every check occurs once per source record.

The calling processing stage must still decide whether the check was applicable.

### Performance

Avoid unnecessary allocations for every successful record.

Do not create full diagnostic messages for successful observations.

Prefer efficient counter updates.

Do not add expensive synchronization to ordinary task-local processing.

This task must not create substantial avoidable overhead in the normalization hot path.

Do not run performance benchmarks to verify this task.
