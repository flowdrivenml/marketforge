## 1. Purpose

The Connection Manager owns the physical transport infrastructure of MarketForge Live.

It establishes, maintains, pools, monitors, and terminates exchange connections while providing reliable transport services to the Subscription Manager.

The Connection Manager is **exchange-protocol-aware but market-data-agnostic**.

Its responsibilities include:

- Establishing and terminating physical WebSocket connections.
- Pooling connections across compatible subscriptions.
- Enforcing connection-level resource constraints.
- Managing heartbeat and connection liveness.
- Detecting transport failures and silent connections.
- Coordinating reconnection with exponential backoff and jitter.
- Maintaining connection identities and generations.
- Routing inbound frames to protocol dispatchers.
- Serializing outbound transport operations.
- Enforcing connection-attempt rate limits.
- Managing transport-level backpressure.
- Supporting graceful shutdown and deterministic cleanup.
- Exposing connection health and operational diagnostics.

The Connection Manager does not normalize market data, reconstruct order books, or manage logical stream identities.

Its primary objective is to provide **fault-tolerant, reusable physical connectivity without introducing unnecessary exchange-specific implementations**.

## 2. Architectural Boundaries

The Connection Manager operates between the Subscription Manager and exchange protocol adapters.

### 2.1 Component Responsibilities

| Component | Responsibility |
|---|---|
| Stream Registry | Logical stream identity, desired state, lifecycle |
| Subscription Manager | Native subscription assignment, admission, acknowledgements |
| Connection Manager | Physical connections, pooling, transport lifecycle |
| Transport Adapter | WebSocket operations and frame handling |
| Exchange Protocol Adapter | Exchange-specific message encoding and interpretation |
| Rate Limiter | Connection and request budget enforcement |
| Stream Processor | Market-data decoding, normalization, integrity |
| Recovery Coordinator | Trade recovery and L2 resynchronization |
| Metrics Registry | Connection health and performance measurements |

The Connection Manager owns physical connectivity but delegates exchange-specific protocol semantics to compiled adapters.

### 2.2 Dependency Model

    Stream Registry
           |
           v
    Subscription Manager
           |
           v
     Connection Manager
           |
           +------------------+
           |                  |
           v                  v
    Transport Adapter    Rate Limiter
           |
           v
    Exchange WebSocket
           |
           v
    Inbound Frame Dispatcher
           |
           v
    Exchange Protocol Adapter
           |
           v
    Subscription / Stream Routing

This diagram represents the principal control and data boundaries.

Actual inbound frame delivery must not pass through the Stream Registry.

### 2.3 Ownership Rules

The Connection Manager exclusively owns:

- Physical socket handles.
- Connection establishment and termination.
- Connection lifecycle state.
- Connection generations.
- Transport reader and writer tasks.
- Heartbeat scheduling.
- Transport-level timeouts.
- Connection-level outbound queues.
- Reconnection scheduling.
- Connection resource accounting.

The Subscription Manager exclusively owns native subscription assignments and their lifecycle.

The Connection Manager must not independently decide which logical streams should be restored after reconnection.

Instead, it reports connection availability and failures to the Subscription Manager, which reconciles subscriptions against the Stream Registry's desired state.

### 2.4 Design Constraints

- Rust-only runtime implementation.
- Asynchronous, nonblocking transport operations.
- No exchange-specific connection manager implementations.
- No direct PostgreSQL dependencies.
- No direct TUI dependencies.
- No market-data normalization inside transport tasks.
- No REST snapshot or trade-recovery logic inside the Connection Manager.
- No network I/O while holding global registry locks.
- No unbounded inbound or outbound queues.
- No silent frame loss under backpressure.
- No automatic assumption that a connected socket represents a healthy market-data stream.
- No reuse of obsolete connection generations.
- No reconnection attempts that bypass exchange rate limits.

Transport failures must remain isolated from unrelated physical connections wherever possible.

## 3. Transport Abstraction

MarketForge Live initially supports WebSocket transport.

The architecture must permit additional transport implementations without modifying connection lifecycle semantics.

### 3.1 Transport Interface

The transport abstraction exposes the following conceptual operations:

    Connect
    Send
    Receive
    Close
    InspectState

Transport implementations return structured results rather than exchange-specific errors.

The interface must support:

- Text frames.
- Binary frames.
- WebSocket ping frames.
- WebSocket pong frames.
- Close frames.
- Transport errors.
- Connection closure.
- Configurable handshake headers.

The transport adapter is responsible for preserving frame payloads and transport ordering.

### 3.2 TransportFrame

The internal transport representation contains:

| Field | Purpose |
|---|---|
| connection_id | Physical connection identity |
| connection_generation | Connection incarnation |
| frame_type | Text, Binary, Ping, Pong, Close |
| payload | Original frame bytes |
| received_at | Local receipt timestamp |
| sequence | Connection-local receive ordering |

Frame payloads remain unnormalized.

JSON decoding and exchange-specific message classification occur downstream.

### 3.3 Transport Requirements

Each connection is created from a compiled `ConnectionRequirements` definition.

Relevant fields:

| Field | Purpose |
|---|---|
| exchange | Exchange identity |
| endpoint | Resolved WebSocket URL |
| protocol_version | Exchange API generation |
| authentication | Authentication requirements |
| headers | Required handshake headers |
| heartbeat | Compiled heartbeat strategy |
| compression | Supported compression configuration |
| connection_class | Optional operational isolation |
| transport_limits | Frame and queue constraints |

Connection requirements are immutable for one physical connection generation.

Changes affecting handshake properties require connection replacement.

### 3.4 Handshake Requirements

Handshake configuration must be validated before connection establishment.

For example, Gate.io Futures requires:

    X-Gate-Size-Decimal: 1

This header preserves fractional contract quantities.

Connections must not be shared when their required handshake properties differ.

A stream requiring unsupported transport capabilities must fail admission before activation.

### 3.5 Transport Error Classification

Transport errors are normalized into a shared classification.

| Error | Initial handling |
|---|---|
| DNS resolution failure | Retry with backoff |
| Connection timeout | Retry with backoff |
| Connection refused | Retry according to policy |
| Connection reset | Reconnect |
| Unexpected EOF | Reconnect |
| TLS handshake failure | Classify as transient or configuration failure |
| Invalid endpoint | Fail configuration |
| Unsupported transport capability | Fail configuration |
| Protocol close frame | Interpret close reason and policy |
| Frame-size violation | Reject frame and evaluate connection validity |
| Outbound queue saturation | Apply backpressure policy |
| Inbound queue saturation | Apply lossless overflow policy or terminate connection |

Retryable errors must not cause unlimited immediate reconnection attempts.

Permanent configuration failures must not enter endless retry loops.

## 4. Connection Identity

Each physical connection has a stable identity within its lifetime and a monotonically increasing generation across replacements.

Connection identity must remain independent of logical source-stream identity.

### 4.1 ConnectionDescriptor

Immutable connection definition.

| Field | Type | Purpose |
|---|---|---|
| connection_id | ConnectionId | Logical connection identity |
| pool_key | ConnectionPoolKey | Connection compatibility identity |
| exchange | ExchangeId | Exchange identifier |
| endpoint | EndpointId | Resolved WebSocket endpoint |
| protocol_version | ProtocolVersion | Exchange API generation |
| authentication | AuthenticationContext | Authentication requirements |
| transport_requirements | TransportRequirements | Headers, compression, TLS |
| heartbeat_policy | HeartbeatPolicy | Compiled heartbeat configuration |
| connection_class | ConnectionClass | Optional isolation category |
| created_at | Timestamp | Descriptor creation time |

`ConnectionDescriptor` is immutable.

Changes to endpoint, authentication, handshake requirements, or transport capabilities require connection replacement.

### 4.2 ConnectionRuntime

Mutable operational state.

| Field | Type | Purpose |
|---|---|---|
| connection_id | ConnectionId | Logical connection identity |
| generation | u64 | Current physical connection incarnation |
| state | ConnectionState | Observed lifecycle |
| assigned_subscriptions | u32 | Current subscription allocation |
| last_received_at | Option<Timestamp> | Last inbound frame |
| last_sent_at | Option<Timestamp> | Last outbound frame |
| last_pong_at | Option<Timestamp> | Last heartbeat response |
| reconnect_attempts | u32 | Consecutive recovery attempts |
| last_error | Option<TransportError> | Latest transport failure |
| connected_at | Option<Timestamp> | Current connection establishment |
| state_changed_at | Timestamp | Latest lifecycle transition |

Connection metrics such as throughput, RTT, and queue utilization belong to the Metrics Registry.

The Connection Manager maintains only the operational state required for lifecycle decisions.

### 4.3 Connection Generations

A connection generation identifies one physical socket incarnation.

    ConnectionId = 12
    Generation = 1 → Initial socket
    Generation = 2 → First replacement
    Generation = 3 → Second replacement

Every inbound frame, outbound operation, and connection event carries its generation.

Events from obsolete generations must never modify current connection state or enter active stream processing.

Generation counters must not wrap or be reused during a runtime lifetime.

## 5. Connection Pooling

Connection pooling allows multiple compatible subscriptions to share one physical WebSocket connection.

Pooling reduces connection overhead, exchange connection-limit consumption, and unnecessary reconnection activity.

### 5.1 ConnectionPoolKey

A connection pool is identified by transport compatibility rather than market category alone.

Conceptually:

    ConnectionPoolKey {
        exchange
        endpoint
        protocol_version
        authentication_context
        handshake_requirements
        heartbeat_compatibility
        connection_class
    }

All fields affecting physical connection compatibility must participate in pool selection.

Two connections with different required handshake headers or authentication contexts must not be considered interchangeable.

### 5.2 Pooling Examples

**OKX**

Compatible Spot, Linear, and Inverse subscriptions may share the same public WebSocket connection.

    OKX Public Pool
           |
           +-- Spot L2
           +-- Linear L2
           +-- Inverse L2

Business-channel subscriptions use their corresponding business endpoint.

**Bitget**

UTA V3 uses a shared public endpoint.

    Bitget Public Pool
           |
           +-- spot
           +-- usdt-futures
           +-- usdc-futures
           +-- coin-futures

Native instrument categories remain part of subscription identity, not necessarily connection identity.

**Binance**

Spot, USD-M Futures, and COIN-M Futures use separate endpoints and therefore separate pools.

**Gate.io**

Spot and Futures use different endpoints.

Futures connections are additionally separated by settlement route.

    Gate Futures
         |
         +-- USDT Pool
         +-- USD1 Pool
         +-- BTC Pool

### 5.3 Connection Selection

When a subscription requires connectivity:

    Resolve ConnectionPoolKey
              |
              v
    Locate Compatible Pool
              |
              v
    Inspect Available Connections
              |
         +----+----+
         |         |
         v         v
      Capacity   No Capacity
         |         |
         v         v
      Assign    Request New
                Connection

Connection selection considers:

- Current connection health.
- Subscription capacity.
- Outbound queue utilization.
- Exchange connection limits.
- Connection isolation policies.
- Existing resource reservations.

The Connection Manager must not inspect or modify logical stream definitions.

### 5.4 Capacity Accounting

Connection capacity includes both confirmed assignments and pending reservations.

    AvailableCapacity =
        MaximumCapacity
        - ActiveAssignments
        - PendingReservations

Reservations must be acquired atomically.

This prevents concurrent admission requests from exceeding the same connection's capacity.

Reservations are released when:

- Subscription admission is cancelled.
- Connection establishment fails.
- Assignment fails.
- Subscription is removed.
- The connection becomes unavailable.

Capacity must not be released twice.

### 5.5 Connection Sharing Constraints

A connection may be shared only when:

- Endpoint and protocol versions match.
- Authentication contexts are compatible.
- Required handshake headers match.
- Heartbeat requirements can be satisfied.
- Subscription capacity is available.
- Operational isolation policies permit sharing.

Connection sharing must not allow one stream to modify transport properties required by another.

## 6. Connection Lifecycle State Machine

The Connection Manager maintains an explicit physical connection lifecycle.

### 6.1 ConnectionState

The Connection Manager uses the authoritative `ConnectionState`
contract defined in Document 02, Section 7.3.

```rust
pub enum ConnectionState {
    Created,
    PendingAdmission,
    Resolving,
    Connecting,
    Handshaking,
    Connected,
    Reconnecting,
    Closing,
    Closed,
    Failed,
}
```

| State | Meaning |
|---|---|
| `Created` | Connection descriptor registered |
| `PendingAdmission` | Waiting for connection-attempt capacity or rate-limit admission |
| `Resolving` | DNS or endpoint resolution in progress |
| `Connecting` | TCP connection establishment in progress |
| `Handshaking` | Required TLS and WebSocket negotiation in progress |
| `Connected` | Physical transport established and operational |
| `Reconnecting` | Transport recovery scheduled or underway |
| `Closing` | Intentional connection shutdown in progress |
| `Closed` | Physical connection terminated |
| `Failed` | Nonrecoverable connection condition requiring correction or intervention |

The Connection Manager is authoritative for these lifecycle
transitions.

Connection lifecycle must remain independent of:

- Logical source-stream lifecycle.
- Native subscription lifecycle.
- Market-data integrity.
- Recovery-operation status.
- Historical coverage.
- Health assessment.

`Connected` means the physical transport is available.

It does not imply successful native subscription activation,
valid market data, or acquisition readiness.

#### Connection Health

Connection health is an independent operational assessment.

A physically connected transport may have degraded health
without changing its lifecycle state.

For example:

    ConnectionState:  Connected
    ConnectionHealth: Degraded

`Degraded` is not a `ConnectionState` variant.

Health classification and evaluation are defined in
Section 15 of this document.

The health subsystem must not maintain a second,
competing physical connection lifecycle state machine.

#### Connection Failure

A recoverable unexpected disconnection is represented
through `ConnectionState::Reconnecting`.

The Connection Supervisor coordinates recovery and
establishes a new connection generation when appropriate.

Intentional termination is represented through
`Closing` and `Closed`.

Terminal configuration or transport incompatibility
is represented through `Failed`.

Connection failure must not automatically invalidate
the logical source-stream runtime.

The affected source streams may remain
`StreamLifecycle::Active` while connection,
subscription, and integrity recovery proceeds.

All connection operations must preserve the
generation-fencing and resource-ownership guarantees
specified in this document.
### 6.2 Initial Connection

    Created
       |
       v
    PendingAdmission
       |
       v
    Resolving
       |
       v
    Connecting
       |
       v
    Handshaking
       |
       v
    Connected

Each stage has a bounded timeout.

The Connection Manager allocates a new `ConnectionGeneration`
before beginning each physical connection attempt.

The generation identifies the attempt throughout endpoint
resolution, TCP connection establishment, TLS negotiation,
and WebSocket handshaking.

Successful WebSocket negotiation transitions the current
generation to `ConnectionState::Connected`; it does not
allocate the generation at that point.

Failed, cancelled, timed-out, or superseded attempts retain
their original generation identity for diagnostic reporting
and stale-completion rejection.

A newer connection attempt must not reuse the generation
of an earlier attempt.

The Connection Manager then notifies the Subscription Manager that the connection is available.

### 6.3 Transport Failure

    Connected
       |
       v
    Transport Failure
       |
       v
    Reconnecting
       |
       v
    Backoff / Admission
       |
       v
    Resolving
       |
       v
    Connecting
       |
       v
    Handshaking
       |
       v
    Connected

A failed generation must be fenced before a replacement becomes authoritative.

Reader, writer, and heartbeat tasks belonging to the failed generation must be cancelled or terminated.

### 6.4 Connection Health Degradation

Connection health degradation is independent of
`ConnectionState`.

A physical connection may remain
`ConnectionState::Connected` while its operational
measurements indicate reduced transport health.

Examples include:

- Elevated heartbeat RTT.
- Repeated delayed heartbeat responses.
- Sustained outbound queue congestion.
- Abnormal transport latency.
- Repeated transient frame-processing errors.

These conditions contribute to the independent
connection-health assessment defined in Section 15.

They must not introduce a `ConnectionState::Degraded`
variant.

Health degradation does not automatically imply
physical disconnection.

The configured health and escalation policies determine
whether the Connection Manager should:

- Continue monitoring the existing connection.
- Apply additional diagnostics.
- Escalate the operational incident.
- Initiate controlled connection replacement.

A replacement initiated because of degraded health
must follow the ordinary connection lifecycle and
generation-fencing rules.

Market-data silence alone must not establish transport
failure without considering the exchange's heartbeat
and channel-specific activity semantics.

Connection health must not be used as a substitute
for native subscription readiness or market-data integrity.

### 6.5 Terminal States

`Closed` represents intentional or completed termination.

`Failed` represents a nonrecoverable condition requiring configuration correction or explicit intervention.

Examples:

- Invalid endpoint configuration.
- Unsupported handshake requirements.
- Permanent authentication rejection.
- Unsupported transport protocol.

Transient network failures must not enter `Failed` merely because several retries have occurred.

Repeated failures may trigger escalation or longer backoff according to policy.

## 7. Connection Task Architecture

Each physical WebSocket connection is managed by a small set of asynchronous Rust tasks.

The Connection Manager coordinates these tasks but does not perform market-data normalization or subscription-specific processing.

### 7.1 Task Structure

A connection generation contains:

- Reader task.
- Writer task.
- Heartbeat controller.
- Connection supervisor.
- Bounded inbound and outbound queues.

Conceptually:

    Connection Supervisor
              |
      +-------+-------+
      |       |       |
      v       v       v
    Reader  Writer  Heartbeat
      |       ^       |
      v       |       |
    Inbound Outbound  |
    Queue   Queue <---+
      |       ^
      v       |
    Frame     |
    Router    |
      |       |
      v       |
    Protocol Adapter

The supervisor owns task cancellation and connection lifecycle transitions.

Reader and writer tasks operate on the same physical WebSocket generation.

### 7.2 Task Ownership

| Task | Responsibility |
|---|---|
| Connection Supervisor | Lifecycle, task supervision, cancellation, recovery |
| Reader | Receive WebSocket frames |
| Writer | Serialize outbound frames |
| Heartbeat Controller | Schedule and validate heartbeats |
| Frame Router | Dispatch received frames |
| Protocol Adapter | Interpret exchange-specific messages |

Tasks must not independently initiate reconnection.

A task detecting a fatal condition reports it to the Connection Supervisor.

The supervisor performs the authoritative lifecycle transition.

### 7.3 Task Failure Propagation

A fatal reader or writer failure invalidates the current physical connection generation.

    Reader / Writer Failure
              |
              v
       Connection Supervisor
              |
              v
       Fence Generation
              |
              v
       Cancel Remaining Tasks
              |
              v
       Notify Subscription Manager
              |
              v
       Schedule Reconnection

All tasks must terminate when their connection generation is invalidated.

Detached tasks from obsolete generations are prohibited.

## 8. Reader Task

The Reader Task owns inbound WebSocket frame acquisition.

It must preserve frame ordering and detect transport failures without performing exchange-specific normalization.

### 8.1 Reader Responsibilities

- Receive WebSocket frames.
- Record local receipt timestamps.
- Preserve inbound frame ordering.
- Distinguish text, binary, control, and close frames.
- Enforce configured frame-size limits.
- Forward market-data frames to the inbound pipeline.
- Route transport-level control frames appropriately.
- Detect connection closure.
- Report fatal transport errors.
- Respect connection-generation cancellation.

The Reader Task must not:

- Parse canonical trades.
- Apply L2 updates.
- Execute REST recovery.
- Query instrument metadata.
- Write market data to PostgreSQL.
- Modify Stream Registry state.

### 8.2 Inbound Frame Processing

    WebSocket Frame
          |
          v
    Validate Generation
          |
          v
    Record Receipt Timestamp
          |
          v
    Validate Frame Size
          |
          v
    Classify Frame Type
          |
          +---- Control Frame
          |          |
          |          v
          |    Transport Handler
          |
          +---- Data Frame
                     |
                     v
               Inbound Queue
                     |
                     v
                Frame Router

The Reader Task must not silently discard frames when downstream processing becomes slower than network reception.

### 8.3 Receipt Timestamps

Each received data frame receives a local monotonic receipt timestamp for latency measurements.

A corresponding wall-clock timestamp may be recorded for diagnostics and canonical event provenance.

The system must distinguish:

| Timestamp | Purpose |
|---|---|
| Exchange event timestamp | Native market-data event time |
| Local receipt timestamp | Time the frame entered MarketForge |
| Processing timestamp | Time normalization or processing occurred |
| Publication timestamp | Time canonical output was published |

The Reader Task assigns only transport receipt information.

Exchange event timestamps are extracted downstream.

### 8.4 Frame Ordering

Frames received through one physical WebSocket connection must retain their original transport order.

The Reader Task assigns a connection-local receive sequence:

    ReceiveSequence = 1, 2, 3, ...

This sequence is scoped to:

    ConnectionId
    ConnectionGeneration

It is not an exchange-native market-data sequence identifier.

It must not be used to infer missing exchange events.

### 8.5 Reader Failure Conditions

Fatal conditions include:

- Unexpected WebSocket closure.
- Connection reset.
- Unrecoverable transport error.
- Invalid connection generation.
- Unsupported frame representation.
- Frame exceeding configured safety limits.
- Inbound queue overflow that cannot be handled losslessly.

The Reader Task reports the failure and terminates.

The Connection Supervisor determines the recovery action.

## 9. Writer Task

The Writer Task is the exclusive owner of outbound WebSocket frame transmission.

All subscription commands, unsubscription commands, application heartbeats, and other protocol messages pass through it.

### 9.1 Writer Responsibilities

- Serialize outbound WebSocket operations.
- Preserve required command ordering.
- Enforce connection-local sending constraints.
- Respect exchange rate-limit permits.
- Send protocol and application heartbeat messages.
- Detect write failures.
- Reject obsolete-generation operations.
- Report transmission outcomes.
- Support graceful connection closure.

Only one task may write to a physical WebSocket connection at a time.

### 9.2 Outbound Commands

Conceptual command types:

    Subscribe
    Unsubscribe
    ApplicationPing
    WebSocketPing
    WebSocketPong
    ProtocolMessage
    Close

Every outbound operation carries:

    ConnectionId
    ConnectionGeneration
    OperationId
    Payload
    Priority
    Deadline

Subscription-specific commands additionally carry their subscription generation.

### 9.3 Outbound Queue

The outbound queue is bounded.

It must support:

- Normal subscription commands.
- Unsubscription commands.
- Heartbeat traffic.
- Connection shutdown commands.
- Exchange-specific control messages.

Queue admission must account for memory limits and command deadlines.

Expired commands must not be transmitted.

### 9.4 Outbound Priorities

Suggested priority classes:

| Priority | Operations |
|---|---|
| Critical | Protocol-required Pong, connection shutdown |
| High | Heartbeats, urgent connection control |
| Normal | Subscribe, unsubscribe |
| Low | Optional diagnostics |

Priority scheduling must not violate protocol-required ordering.

It must also avoid indefinitely starving normal subscription operations.

### 9.5 Writer Failure

A failed write may leave the native operation outcome ambiguous.

For example:

    Subscribe Command
           |
           v
    Socket Write Attempt
           |
           v
    Connection Failure

The exchange may have received the command even if the local write operation failed.

The Writer Task reports the failure.

The Subscription Manager resolves the operation through acknowledgement handling, connection replacement, or another protocol-supported reconciliation mechanism.

The Writer Task must not independently retry subscription commands.

## 10. Inbound Frame Routing

Inbound routing separates transport acquisition from exchange-specific message interpretation.

### 10.1 Routing Pipeline

    Reader Task
         |
         v
    Inbound Frame Queue
         |
         v
    Frame Router
         |
         v
    Exchange Protocol Adapter
         |
         +---- Subscription Acknowledgement
         |
         +---- Subscription Error
         |
         +---- Heartbeat Response
         |
         +---- Exchange System Event
         |
         +---- Market-Data Message
                         |
                         v
                  Stream Dispatcher
                         |
                         v
                  Stream Processor

The Connection Manager owns the transport pipeline.

The Exchange Protocol Adapter classifies messages using the compiled exchange profile.

The Stream Dispatcher resolves market-data messages to their logical source streams.

### 10.2 Routing Identity

Market-data routing uses exchange-native identifiers.

Depending on the exchange, these may include:

- Native channel.
- Instrument symbol.
- Native market category.
- Subscription topic.
- Connection endpoint.
- Channel parameters.

The routing table maps:

    NativeSubscriptionKey
              |
              v
           StreamId
              |
              v
    SubscriptionGeneration

Messages must be rejected or quarantined when their native identity cannot be resolved safely.

### 10.3 Routing Generation Validation

Before delivering a market-data message:

1. Validate the physical connection generation.
2. Resolve the native subscription identity.
3. Validate the active subscription generation.
4. Confirm that the stream remains eligible to receive data.
5. Forward the message to the assigned processor.

Messages belonging to obsolete generations must never enter current processing state.

This is particularly important for L2 streams because stale deltas could corrupt a newly synchronized book.

### 10.4 Unknown Messages

Unknown messages are not automatically fatal transport errors.

They may represent:

- Newly introduced exchange fields.
- Unsupported channels.
- System notifications.
- Unexpected subscription responses.
- Malformed protocol messages.

The Protocol Adapter classifies the condition.

Repeated unknown or malformed messages may trigger stream invalidation or connection escalation according to policy.

## 11. Backpressure and Queue Management

MarketForge Live prioritizes lossless acquisition and explicit integrity guarantees.

Backpressure must therefore be treated as a correctness concern, not merely a performance optimization.

### 11.1 Bounded Queues

All transport queues must have explicit capacity limits.

Relevant queues include:

| Queue | Producer | Consumer |
|---|---|---|
| Inbound frames | Reader | Frame Router |
| Outbound commands | Subscription Manager / Heartbeat | Writer |
| Routed stream messages | Frame Router | Stream Processor |
| Connection events | Supervisor | Control-plane consumers |

Unbounded queues are prohibited.

Queue capacities are configured according to expected throughput, message size, and available memory.

### 11.2 Inbound Backpressure

When downstream processing cannot keep up:

    Incoming Frames
          |
          v
    Inbound Queue Filling
          |
          v
    Backpressure Threshold
          |
          v
    Apply Flow-Control Policy

The initial policy is:

    Block → Buffer → Escalate

Blocking a bounded queue can propagate pressure to the WebSocket reader and ultimately to the TCP receive buffer.

However, TCP flow control does not guarantee that an exchange will retain every market-data event indefinitely.

Therefore, blocking alone must not be considered a complete lossless-delivery guarantee.

### 11.3 Overflow Policy

MarketForge must never silently discard market-data frames.

When the inbound pipeline cannot maintain capacity:

- Record the overload condition.
- Preserve already accepted frames according to queue ownership.
- Stop claiming uninterrupted acquisition.
- Invalidate affected integrity guarantees when continuity cannot be established.
- Trigger controlled recovery or connection replacement.
- Report any unrecoverable coverage gap.

For trades, recovery may use exchange-supported historical endpoints.

For L2, recovery generally requires a new synchronized snapshot.

A new snapshot restores current book validity but does not reconstruct all missed depth updates.

### 11.4 Disk Spill

Optional disk-backed buffering may be introduced when memory capacity is insufficient.

Disk spill must provide:

- Bounded storage allocation.
- Explicit ordering guarantees.
- Generation-aware records.
- Crash-safe segment handling.
- Backpressure when disk capacity is exhausted.
- Deterministic replay into the processing pipeline.

Disk spill is not automatically enabled merely because a queue is full.

Its use must be explicitly configured and tested.

### 11.5 Per-Stream Isolation

A shared connection may carry several streams with different message rates.

Example:

    Shared WebSocket
          |
          +-- BTCUSDT Trades
          |
          +-- ETHUSDT Trades
          |
          +-- BTCUSDT L2

A slow consumer must not silently cause unrelated streams to lose data.

The routing layer should support bounded per-stream queues and independent processing tasks.

However, because all streams share one physical reader, sustained overload in one stream may still affect the connection.

The Connection Manager should expose congestion information so the Subscription Manager can consider redistributing subscriptions across compatible connections.

### 11.6 Backpressure Metrics

The Metrics Registry should expose:

| Metric | Description |
|---|---|
| inbound_queue_depth | Current inbound queue occupancy |
| outbound_queue_depth | Current outbound queue occupancy |
| inbound_queue_capacity | Configured queue capacity |
| outbound_queue_capacity | Configured queue capacity |
| queue_wait_duration | Time spent waiting for capacity |
| frame_dispatch_latency | Receipt-to-dispatch delay |
| backpressure_events_total | Number of backpressure incidents |
| queue_overflow_events_total | Number of capacity failures |
| connection_overload_total | Connections affected by sustained overload |

Metrics must distinguish temporary congestion from confirmed data loss.

## 12. Heartbeat Management

The Connection Manager supports multiple heartbeat strategies through a shared, configurable heartbeat controller.

Heartbeat behavior is defined by the compiled exchange profile.

The implementation must not introduce separate heartbeat managers for Binance, Bybit, OKX, Bitget, or Gate.io.

### 12.1 Responsibilities

The Heartbeat Controller is responsible for:

- Scheduling heartbeat requests.
- Monitoring heartbeat responses.
- Measuring heartbeat round-trip time.
- Detecting missed heartbeat deadlines.
- Maintaining transport-level liveness information.
- Reporting heartbeat failures to the Connection Supervisor.
- Respecting exchange-specific heartbeat requirements.
- Preventing obsolete heartbeat operations from affecting newer connection generations.

Heartbeat management must remain independent of market-data normalization and subscription lifecycle state.

### 12.2 Supported Heartbeat Strategies

MarketForge initially supports:

| Strategy | Description |
|---|---|
| WebSocket control frames | Protocol-level Ping/Pong |
| Text ping/pong | Literal text messages such as `ping` and `pong` |
| JSON application heartbeat | Exchange-specific JSON heartbeat messages |
| Inactivity-triggered | Send heartbeat after a configured idle period |
| Periodic | Send heartbeat at fixed intervals |
| Server-driven | Respond to exchange-initiated heartbeat requests |

A connection may require more than one heartbeat mechanism.

For example, an exchange may use WebSocket control frames while also supporting optional application-level heartbeats.

The compiled configuration determines which mechanisms are active.

### 12.3 Exchange Heartbeat Profiles

The initial exchange configurations define the following general behavior:

| Exchange | Heartbeat approach |
|---|---|
| Binance | WebSocket protocol-level Ping/Pong |
| Bybit | Exchange-defined JSON application heartbeat |
| OKX | Text `ping` / `pong`, inactivity-triggered |
| Bitget | Text `ping` / `pong`, periodic |
| Gate.io | WebSocket control frames, optional application heartbeat |

Exact intervals, timeout values, and response semantics are obtained from the selected exchange profile.

The Connection Manager must not hardcode these values.

## 13. Heartbeat Controller

Each physical connection generation owns one Heartbeat Controller.

The controller operates independently of the Reader and Writer tasks but communicates through their established interfaces.

### 13.1 Heartbeat State

Conceptual heartbeat state:

    HeartbeatState {
        connection_id
        connection_generation
        strategy
        last_request_at
        last_response_at
        pending_request
        consecutive_failures
        current_rtt
    }

The controller must not retain heartbeat state across physical connection generations.

A newly established connection starts with a fresh heartbeat state.

### 13.2 Heartbeat Scheduling

Heartbeat scheduling supports two primary modes.

**Periodic mode**

    Connection Established
             |
             v
       Start Interval Timer
             |
             v
       Send Heartbeat
             |
             v
       Await Response
             |
             v
       Record Result
             |
             v
       Schedule Next Heartbeat

Periodic scheduling is appropriate when the exchange requires heartbeat requests at regular intervals.

**Inactivity-triggered mode**

    Connection Established
             |
             v
       Monitor Activity
             |
             v
       Inactivity Threshold
             |
             v
       Send Heartbeat
             |
             v
       Await Response
             |
             v
       Resume Monitoring

The definition of activity must be explicit.

Depending on the exchange protocol, activity may mean:

- Any inbound WebSocket frame.
- Any inbound application message.
- Any outbound message.
- A successfully received heartbeat response.

The scheduler must not assume these definitions are interchangeable.

### 13.3 Heartbeat Request Identity

Where the protocol supports correlation identifiers, each heartbeat request receives a unique identifier.

Conceptually:

    HeartbeatRequest {
        connection_id
        connection_generation
        request_id
        sent_at
        deadline
    }

Responses must be associated with the correct pending request.

For protocols without request identifiers, the controller must enforce a safe outstanding-request policy.

The initial implementation should permit at most one outstanding heartbeat request per heartbeat mechanism unless the protocol explicitly supports concurrent correlation.

### 13.4 Heartbeat Response Processing

    Heartbeat Response
           |
           v
    Validate Connection Generation
           |
           v
    Match Pending Request
           |
           v
    Calculate RTT
           |
           v
    Update Heartbeat State
           |
           v
    Report Health Measurement

Unexpected, duplicate, or obsolete heartbeat responses must not modify current heartbeat state.

They may be recorded as protocol diagnostics.

### 13.5 Heartbeat Round-Trip Time

Heartbeat RTT is calculated using a monotonic clock.

    RTT = response_received_at - request_sent_at

Wall-clock timestamps must not be used for elapsed-time measurement because system-clock adjustments can distort the result.

The Metrics Registry may maintain:

- Latest RTT.
- Minimum RTT.
- Maximum RTT.
- Rolling average RTT.
- RTT distribution.
- Consecutive heartbeat failures.

Heartbeat RTT measures connection responsiveness.

It does not directly measure exchange market-data latency.

## 14. Connection Liveness Detection

A physically connected WebSocket does not necessarily represent a healthy transport.

The Connection Manager must detect connections that remain open but no longer respond correctly.

### 14.1 Liveness Signals

Connection liveness is evaluated using:

| Signal | Meaning |
|---|---|
| Successful heartbeat response | Transport or application responsiveness |
| Recent inbound frames | Evidence of inbound activity |
| Successful outbound writes | Local transport accepted outbound data |
| WebSocket close frame | Explicit connection termination |
| Reader failure | Inbound transport failure |
| Writer failure | Outbound transport failure |
| Heartbeat timeout | Missing expected response |
| Exchange system notification | Exchange-defined operational condition |

No individual signal is sufficient to establish every aspect of connection health.

For example, successful outbound writes do not prove that the exchange is receiving or processing messages.

### 14.2 Silent Connections

A silent connection is one that remains physically established but stops producing expected activity.

Possible causes include:

- Network path failure.
- Exchange infrastructure problems.
- Stalled WebSocket processing.
- Missing heartbeat responses.
- Transport-level deadlock.
- Application-level processing failure.

The Connection Manager must distinguish transport silence from legitimate market-data inactivity.

A low-volume trading instrument may produce no trades for an extended period while its WebSocket connection remains healthy.

Therefore:

    No Market Data != Dead Connection

Market-data freshness is evaluated by the Stream Processor and Metrics Registry.

Transport liveness is evaluated by the Connection Manager.

### 14.3 Heartbeat Timeout

When a heartbeat response is not received before its deadline:

    Heartbeat Deadline Exceeded
               |
               v
       Record Timeout
               |
               v
       Evaluate Failure Policy
               |
          +----+----+
          |         |
          v         v
       Retry     Escalate
          |         |
          v         v
       Monitor   Supervisor
                    |
                    v
              Reconnection

The selected action depends on exchange requirements and configured failure thresholds.

A heartbeat timeout must never be silently ignored.

### 14.4 Consecutive Failures

The heartbeat policy may define a maximum number of consecutive failures before connection replacement.

Conceptually:

    consecutive_failures >= failure_threshold
                      |
                      v
              Connection Unhealthy
                      |
                      v
              Notify Supervisor

Successful heartbeat responses reset the consecutive-failure counter.

The failure threshold is a MarketForge operational setting, not necessarily an exchange-defined limit.

### 14.5 Half-Open Connections

A half-open connection may occur when one endpoint loses connectivity without the other immediately detecting it.

WebSocket heartbeat mechanisms help identify these conditions.

The Connection Manager must not rely exclusively on TCP connection state.

A connection that repeatedly fails heartbeat validation must be replaced according to its configured recovery policy.

## 15. Connection Health

Connection health is separate from lifecycle state.

A connection may remain in `Connected` while exhibiting degraded operational characteristics.

### 15.1 Health Classification

Supported health classifications:

    Healthy
    Degraded
    Unhealthy
    Unknown

| Health | Meaning |
|---|---|
| Healthy | Required liveness checks succeed |
| Degraded | Transport remains operational but health thresholds are exceeded |
| Unhealthy | Required liveness guarantees are not satisfied |
| Unknown | Insufficient evidence to establish current health |

Health classification is derived from observable signals.

It must not be manually modified by stream processors.

### 15.2 Health Evaluation

Health evaluation may consider:

- Heartbeat success rate.
- Consecutive heartbeat failures.
- Heartbeat RTT.
- Time since last successful heartbeat.
- Reader and writer task status.
- Inbound queue utilization.
- Outbound queue utilization.
- Transport error frequency.
- Connection age.
- Reconnection frequency.

Thresholds are configurable.

A connection should not be classified as unhealthy solely because its market-data throughput is low.

### 15.3 Degradation Policy

When degradation is detected:

    Health Threshold Exceeded
              |
              v
         Mark Degraded
              |
              v
       Publish Health Event
              |
              v
       Evaluate Escalation
              |
         +----+----+
         |         |
         v         v
      Continue   Replace
      Monitoring Connection

Temporary degradation does not automatically require reconnection.

Unnecessary reconnections can introduce trade coverage gaps and force L2 resynchronization.

The Connection Manager should avoid replacing connections for isolated latency spikes.

### 15.4 Health Recovery

A degraded connection may return to healthy status when its measurements recover.

Recovery thresholds should support hysteresis.

For example:

    Degraded threshold: RTT > configured upper bound

    Recovery threshold: RTT < configured lower bound

Using different thresholds prevents rapid oscillation between `Healthy` and `Degraded`.

The exact thresholds belong to runtime configuration.

## 16. Heartbeat and Transport Failure Coordination

The Heartbeat Controller detects liveness failures.

The Connection Supervisor owns the resulting lifecycle decisions.

### 16.1 Failure Escalation

    Heartbeat Controller
             |
             v
       Liveness Failure
             |
             v
      Connection Supervisor
             |
             v
       Validate Generation
             |
             v
       Fence Connection
             |
             v
       Cancel Connection Tasks
             |
             v
       Notify Subscription Manager
             |
             v
       Schedule Recovery

The Heartbeat Controller must not independently open replacement sockets.

This prevents multiple components from initiating competing reconnection attempts.

### 16.2 Generation Safety

Every heartbeat event carries:

    ConnectionId
    ConnectionGeneration

A heartbeat timeout from an obsolete generation must not terminate a newer connection.

Example:

    Generation 4: Heartbeat timeout scheduled
    Generation 4: Connection replaced
    Generation 5: Connected
    Generation 4: Timeout callback executes

The timeout callback must be rejected because generation 4 is obsolete.

### 16.3 Shutdown Behavior

During graceful connection shutdown:

- Stop scheduling new heartbeat requests.
- Cancel pending heartbeat deadlines.
- Prevent heartbeat commands from entering the outbound queue.
- Allow required WebSocket close-handshake operations.
- Terminate the Heartbeat Controller.
- Release heartbeat-related resources.

Shutdown must not be misclassified as a transport failure.

### 16.4 Observability

The Metrics Registry should expose:

| Metric | Description |
|---|---|
| heartbeat_requests_total | Heartbeat requests sent |
| heartbeat_responses_total | Valid heartbeat responses |
| heartbeat_timeouts_total | Missed heartbeat deadlines |
| heartbeat_failures_consecutive | Current consecutive failures |
| heartbeat_rtt | Measured heartbeat round-trip time |
| last_heartbeat_success | Timestamp of last successful response |
| connection_health | Current health classification |
| connection_degraded_total | Degradation transitions |
| connection_unhealthy_total | Unhealthy transitions |

Metrics should be available through the runtime API and TUI without requiring Prometheus or Grafana.

Operational heartbeat failures may additionally be written to local structured logs.

## 17. Reconnection Management

The Connection Manager is responsible for restoring physical connectivity after recoverable transport failures.

Reconnection must be automatic, rate-limit-aware, generation-safe, and coordinated with the Subscription Manager.

The Connection Manager restores the physical transport.

The Subscription Manager restores native subscriptions.

The Recovery Coordinator restores market-data integrity.

These responsibilities must remain separate.

### 17.1 Reconnection Triggers

Reconnection may be triggered by:

| Trigger | Required behavior |
|---|---|
| Unexpected WebSocket closure | Reconnect |
| Connection reset | Reconnect |
| Unexpected EOF | Reconnect |
| Heartbeat failure | Replace connection |
| Connection timeout | Retry with backoff |
| DNS resolution failure | Retry with backoff |
| Temporary exchange outage | Retry with extended backoff |
| Exchange maintenance notification | Controlled connection replacement |
| Transport protocol violation | Classify and reconnect when recoverable |
| Sustained connection degradation | Replace according to health policy |
| Explicit connection restart | Controlled replacement |
| Invalid endpoint configuration | Fail configuration |
| Authentication rejection | Require credential or configuration correction |
| Unsupported transport requirements | Fail configuration |

Not every failure should trigger reconnection.

Permanent configuration errors must not enter unlimited retry loops.

### 17.2 Reconnection Sequence

    Transport Failure
           |
           v
    Validate Generation
           |
           v
    Fence Failed Connection
           |
           v
    Cancel Connection Tasks
           |
           v
    Notify Subscription Manager
           |
           v
    Classify Failure
           |
           v
    Calculate Backoff
           |
           v
    Acquire Connection Permit
           |
           v
    Establish Replacement Socket
           |
           v
    Initialize New Generation
           |
           v
    Notify Connection Available
           |
           v
    Subscription Restoration

A successful physical reconnection does not imply successful subscription restoration.

The connection enters `Connected` when its transport requirements are satisfied.

A logical source-stream runtime may remain `StreamLifecycle::Active`
throughout physical disconnection and reconnection.

Physical reconnection does not automatically restore native subscriptions,
processor integrity, or acquisition readiness.

Each affected stream regains acquisition readiness only after its
configured subscription, processor-initialization, and integrity
requirements have been satisfied.

The Connection Manager reports connection availability and generation
changes to the responsible components. It does not independently
declare logical stream activation or acquisition readiness complete.

The authoritative distinction between logical runtime lifecycle
and acquisition readiness is defined in Documents 02 and 05.

### 17.3 Single Reconnection Owner

Only the Connection Supervisor may initiate physical reconnection.

Reader, Writer, Heartbeat, and Protocol Adapter components report failures but must not independently establish replacement connections.

This prevents duplicate reconnection attempts.

For each logical connection:

    Maximum Concurrent Reconnection Attempts = 1

Concurrent failure notifications must be consolidated into the same recovery operation.

### 17.4 Generation Replacement

Before reconnecting:

- Fence the failed connection generation.
- Reject new outbound operations targeting that generation.
- Prevent obsolete inbound frames from reaching processors.
- Cancel associated heartbeat deadlines.
- Terminate reader and writer tasks.
- Release or invalidate transport resources.
- Notify the Subscription Manager of lost assignments.

The replacement connection receives a new generation.

Delayed operations from the previous generation must not affect it.

## 18. Reconnection Backoff

Reconnection attempts must use bounded exponential backoff with jitter.

This prevents aggressive retry loops and reduces synchronized reconnection storms during exchange outages.

### 18.1 Exponential Backoff

The initial policy is:

    delay = min(
        maximum_delay,
        initial_delay * multiplier ^ attempt
    )

Where:

| Parameter | Purpose |
|---|---|
| initial_delay | Starting retry delay |
| multiplier | Exponential growth factor |
| maximum_delay | Maximum calculated delay |
| attempt | Consecutive failed attempt index |

The first retry may use a short delay, but immediate unlimited retries are prohibited.

### 18.2 Jitter

Jitter introduces randomness into retry scheduling.

Supported strategies may include:

    FullJitter
    EqualJitter
    DecorrelatedJitter

The initial recommended strategy is:

    FullJitter

Conceptually:

    maximum = min(
        maximum_delay,
        initial_delay * multiplier ^ attempt
    )

    delay = random(0, maximum)

The selected jitter strategy must be configurable.

Randomization must not bypass exchange-imposed cooldown periods.

### 18.3 Backoff Configuration

Conceptual configuration:

    ReconnectionPolicy {
        initial_delay
        maximum_delay
        multiplier
        jitter_strategy
        connection_timeout
        stability_reset_interval
        maximum_concurrent_attempts
    }

The exact values belong to the Configuration System.

Exchange-specific requirements may override compatible global defaults.

### 18.4 Backoff Reset

A successful WebSocket handshake does not necessarily prove stable recovery.

For example:

    Connect
       |
       v
    Connected
       |
       v
    Disconnect after 200 ms

Immediately resetting the retry counter could produce an aggressive connection loop.

Therefore, the backoff counter should reset only after the connection remains healthy for a configured stability interval.

### 18.5 Backoff Cancellation

A scheduled reconnection must be cancelled when:

- The connection is intentionally closed.
- The owning pool is removed.
- Runtime shutdown begins.
- The connection configuration becomes invalid.
- A newer recovery generation supersedes the attempt.
- No subscriptions require the connection and the pool policy permits termination.

Cancelled attempts must release any reserved connection-attempt capacity.

## 19. Connection Rate Limiting

Connection establishment must respect exchange-defined limits.

The Connection Manager coordinates with the shared Rate Limiter before attempting network connections.

### 19.1 Rate-Limit Scopes

Different exchanges enforce limits at different scopes.

Supported scopes include:

| Scope | Description |
|---|---|
| Connection | Operations associated with one physical socket |
| Endpoint | Operations targeting a specific API endpoint |
| Exchange | Operations across an exchange's endpoints |
| IP | Operations originating from one public IP |
| Account | Operations associated with one authenticated account |
| API key | Operations associated with one credential |
| Global runtime | MarketForge-wide resource constraints |

The compiled exchange configuration determines applicable scopes.

Limits must not be independently allocated to multiple components when they share the same exchange quota.

### 19.2 Connection Attempt Admission

Before establishing a connection:

    Connection Request
           |
           v
    Resolve Applicable Limits
           |
           v
    Acquire Rate-Limit Permit
           |
       +---+---+
       |       |
       v       v
    Granted  Deferred
       |       |
       v       v
    Connect  Wait for Capacity

A deferred connection attempt must not consume network resources.

The permit acquisition mechanism must support cancellation and deadlines.

### 19.3 Shared Connection Budgets

Connection attempt limits may be shared across:

- Multiple market families.
- Multiple connection pools.
- Initial connections.
- Reconnection attempts.
- Replacement connections.

For example, when an exchange imposes an IP-wide connection-attempt limit, all applicable pools must consume the same budget.

    Exchange IP Budget
           |
       +---+---+
       |       |
       v       v
    Spot Pool  Futures Pool
       |       |
       v       v
    Connections

A per-pool limiter alone is insufficient when the exchange enforces a shared quota.

### 19.4 Rate-Limit Reservation

Rate-limit permits and connection-capacity reservations are distinct.

A connection attempt may require:

    Resource Capacity Reservation
                +
    Exchange Rate-Limit Permit

Both must be available before network establishment.

A failed connection attempt must release its resource reservation.

However, an exchange request already attempted may still count against the exchange's rate limit.

Consumed exchange permits must not be refunded merely because the connection failed.

### 19.5 Subscription Rate Limits

Subscription request limits belong to the Subscription Manager.

The Connection Manager provides the transport and serialized Writer Task.

The shared Rate Limiter enforces applicable budgets.

This prevents subscription restoration from overwhelming an exchange after reconnection.

## 20. Exchange-Imposed Cooldowns

Exchange-imposed cooldowns take precedence over ordinary reconnection backoff.

Examples include:

- HTTP 429 responses.
- Explicit retry-after instructions.
- Exchange connection throttling.
- Temporary IP restrictions.
- Maintenance windows.
- Exchange-defined connection rejection periods.

### 20.1 Cooldown Policy

When a valid exchange cooldown is identified:

    Exchange Cooldown
           |
           v
    Determine Applicable Scope
           |
           v
    Register Cooldown Deadline
           |
           v
    Suspend Affected Operations
           |
           v
    Resume After Deadline

The cooldown must be applied to the correct scope.

An IP-wide cooldown must not be treated as a single-stream delay.

### 20.2 Effective Retry Deadline

The effective retry deadline must satisfy both the ordinary backoff policy and exchange-imposed restrictions.

Conceptually:

    next_attempt_at = max(
        backoff_deadline,
        exchange_cooldown_deadline,
        rate_limit_available_at
    )

The Connection Manager must not retry before the resulting deadline.

### 20.3 Cooldown Expiration

Cooldown expiration does not guarantee immediate admission.

The operation must still satisfy:

- Current desired connection demand.
- Resource capacity.
- Rate-limit availability.
- Valid configuration.
- Runtime shutdown state.

Multiple waiting connections should not all reconnect simultaneously when a shared cooldown expires.

Jitter and shared admission control remain applicable.

## 21. Exchange Outage Handling

Exchange outages may affect multiple connections and market families simultaneously.

The Connection Manager must avoid treating every failed socket as an unrelated incident.

### 21.1 Outage Detection

Possible outage signals include:

- Repeated connection failures.
- Widespread heartbeat failures.
- Connection rejection across multiple pools.
- Exchange maintenance notifications.
- Repeated temporary server errors.
- Persistent inability to establish new connections.

The Connection Manager may aggregate these signals into an exchange-level health assessment.

However, a single connection failure must not automatically classify the entire exchange as unavailable.

### 21.2 Exchange Health

Conceptual exchange health states:

    Healthy
    Degraded
    Unavailable
    Recovering

| State | Meaning |
|---|---|
| Healthy | Exchange connectivity operates normally |
| Degraded | Elevated failures or reduced connectivity |
| Unavailable | Required connectivity cannot currently be established |
| Recovering | Connectivity is returning but stability is not established |

Exchange health is an operational assessment.

It does not replace individual connection lifecycle states.

### 21.3 Outage Backoff

During widespread failures, the runtime may increase backoff durations.

    Repeated Exchange Failures
               |
               v
       Exchange Degraded
               |
               v
       Extended Backoff
               |
               v
       Controlled Recovery Probes
               |
               v
       Connectivity Restored
               |
               v
       Gradual Subscription Restoration

The system should avoid reconnecting every affected connection immediately.

### 21.4 Recovery Probes

When an exchange is unavailable, controlled connection attempts may be used to test recovery.

Probe frequency must remain within exchange limits.

Successful probes indicate restored transport connectivity.

They do not establish:

- Subscription readiness.
- Trade coverage completeness.
- L2 synchronization.
- Recording continuity.

Those conditions are verified by their respective components.

### 21.5 Gradual Restoration

After an exchange outage:

- Restore physical connections within admission limits.
- Distribute connection attempts over time.
- Restore subscriptions through the Subscription Manager.
- Reinitialize stream processors.
- Trigger market-data recovery where required.
- Report unresolved coverage gaps.

Restoration must prioritize acquisition correctness over prematurely
reporting source-stream readiness.

A logical source-stream runtime may remain `StreamLifecycle::Active`
throughout an exchange outage and subsequent recovery.

`StreamLifecycle::Active` indicates that the logical runtime is
executing. It does not imply that the physical connection is healthy,
the native subscription is established, or market-data integrity
requirements have been satisfied.

After an exchange outage, each affected source must independently
reestablish its required acquisition-readiness conditions.

For trade streams, this includes native subscription restoration,
processor initialization, and applicable integrity validation.

For L2 streams, this additionally requires valid snapshot and
sequence synchronization before synchronized-book data may be
reported as ready.

Successful transport reconnection must not be treated as proof of
subscription restoration, acquisition readiness, or historical
coverage completeness.

The Connection Manager reports physical connectivity.

The Subscription Manager reports native subscription state.

The responsible stream processor reports data integrity.

The Recovery Coordinator reports recovery progress and outcomes.

The Stream Registry retains authority over logical stream lifecycle
and effective acquisition demand.

These independent states must be exposed without introducing
competing source-stream lifecycle transitions.

## 23. Connection Resource Management

The Connection Manager must enforce explicit resource ownership and bounded resource consumption.

Physical connections, asynchronous tasks, queues, timers, and connection reservations are finite runtime resources.

Resource management must remain independent of exchange-specific market-data processing.

### 23.1 Managed Resources

| Resource | Owner | Lifetime |
|---|---|---|
| Physical WebSocket | Connection Manager | Connection generation |
| Reader task | Connection Supervisor | Connection generation |
| Writer task | Connection Supervisor | Connection generation |
| Heartbeat controller | Connection Supervisor | Connection generation |
| Inbound queue | Connection Manager | Connection generation |
| Outbound queue | Connection Manager | Connection generation |
| Connection capacity reservation | Connection Pool | Until committed or released |
| Connection-attempt permit | Rate Limiter | According to limiter semantics |
| Subscription assignment | Subscription Manager | Subscription generation |
| Reconnection timer | Connection Supervisor | Recovery attempt |
| Transport metrics | Metrics Registry | Runtime lifetime |

Every resource must have a defined acquisition and release procedure.

Resources belonging to an obsolete connection generation must not remain active after replacement.

### 23.2 Resource Limits

The Connection Manager enforces configurable limits.

| Limit | Purpose |
|---|---|
| Maximum connections | Bound total physical connections |
| Maximum connections per exchange | Prevent exchange resource exhaustion |
| Maximum connections per endpoint | Enforce endpoint-specific constraints |
| Maximum concurrent connection attempts | Prevent connection storms |
| Maximum inbound queue capacity | Bound received-frame buffering |
| Maximum outbound queue capacity | Bound pending transport commands |
| Maximum frame size | Prevent oversized frame allocation |
| Maximum connection task count | Bound asynchronous runtime overhead |
| Maximum pending reconnections | Bound recovery scheduling |
| Maximum memory allocation | Protect runtime stability |

Limits must be validated before resource allocation.

Exchange-imposed limits and MarketForge operational limits are distinct.

The effective limit is the most restrictive applicable constraint.

### 23.3 Resource Reservations

Connection creation uses explicit resource reservations.

    Connection Requested
             |
             v
    Check Resource Capacity
             |
             v
    Reserve Connection Slot
             |
             v
    Acquire Rate-Limit Permit
             |
             v
    Establish Connection
             |
        +----+----+
        |         |
        v         v
     Success    Failure
        |         |
        v         v
     Commit    Release
    Reservation Reservation

Reservations must be released when operations fail or are cancelled.

A consumed exchange rate-limit permit must not be refunded merely because the connection attempt failed.

### 23.4 Connection Idle Policy

A physical connection may remain open after its final subscription is removed.

The pool determines whether to retain or terminate it.

Supported policies:

    CloseImmediately
    IdleTimeout
    KeepWarm

The initial recommended policy is:

    IdleTimeout

This permits short-term reuse without retaining unused connections indefinitely.

Idle connections must continue satisfying required heartbeat and health policies.

A connection cannot be considered idle while it has:

- Active subscriptions.
- Pending subscription reservations.
- Outstanding protocol operations.
- Required recovery operations.
- Other registered consumers.

### 23.5 Memory Safety

All queues and buffers must have bounded allocation policies.

The Connection Manager must avoid:

- Unbounded frame accumulation.
- Retaining obsolete generation buffers.
- Duplicating large payloads unnecessarily.
- Holding transport frames after cancellation.
- Keeping failed connection tasks alive.
- Retaining completed operation references indefinitely.

Where practical, frame payload ownership should be transferred rather than copied.

Rust ownership and reference-counting mechanisms may be used, but shared ownership must not obscure resource lifetime.

## 24. Graceful Connection Shutdown

Shutdown must terminate physical connections without creating uncontrolled subscription state or resource leaks.

### 24.1 Shutdown Modes

Supported shutdown modes:

| Mode | Semantics |
|---|---|
| Graceful | Stop admission, drain permitted work, close connections |
| Immediate | Cancel outstanding operations and terminate transports |
| Replacement | Terminate one generation and establish another |
| IdleClosure | Close an unused pooled connection |
| RuntimeShutdown | Terminate all connections as part of application shutdown |

All shutdown modes must be generation-safe.

### 24.2 Graceful Shutdown Sequence

    Shutdown Requested
             |
             v
    Stop New Connection Admission
             |
             v
    Notify Subscription Manager
             |
             v
    Fence Connection Generation
             |
             v
    Stop New Outbound Operations
             |
             v
    Resolve Pending Operations
             |
             v
    Stop Heartbeat Scheduling
             |
             v
    Send WebSocket Close Frame
             |
             v
    Await Bounded Close Handshake
             |
             v
    Cancel Reader / Writer Tasks
             |
             v
    Release Queues and Resources
             |
             v
           Closed

Shutdown must have a finite deadline.

A remote endpoint that does not complete the WebSocket close handshake must not prevent runtime termination indefinitely.

### 24.3 Subscription Coordination

The Connection Manager must notify the Subscription Manager before intentionally closing a connection containing active subscriptions.

The Subscription Manager determines whether subscriptions should:

- Be removed.
- Be migrated to another compatible connection.
- Be restored after replacement.
- Remain inactive during runtime shutdown.

The Connection Manager must not independently change logical stream desired states.

### 24.4 Pending Operations

During shutdown, pending operations must receive explicit terminal outcomes.

Possible outcomes:

    Completed
    Cancelled
    ConnectionClosed
    DeadlineExceeded

No operation may remain indefinitely pending after its owning connection has terminated.

### 24.5 Shutdown and Market-Data Integrity

Closing a connection may interrupt market-data acquisition.

The Connection Manager must report the termination boundary.

The Stream Processor and Recovery Coordinator determine whether the interruption creates:

- A trade coverage gap.
- An invalid L2 book.
- A required resynchronization.
- A recoverable historical interval.

The Connection Manager must not claim that graceful transport shutdown guarantees complete market-data coverage.

## 25. Runtime Connection Configuration Changes

Connection configuration may change while MarketForge Live is running.

Changes must be classified according to whether they affect existing physical connections.

### 25.1 Configuration Change Classes

| Change | Application |
|---|---|
| Connection health thresholds | Immediate where supported |
| Metrics collection settings | Immediate |
| Reconnection backoff settings | Subsequent recovery attempts |
| Connection admission limits | Future admission |
| Queue capacities | Connection replacement unless dynamically supported |
| Heartbeat interval | Controller reconfiguration where safe |
| WebSocket endpoint | Connection replacement |
| Handshake headers | Connection replacement |
| Authentication context | Connection replacement |
| Compression settings | Connection replacement |
| Transport protocol version | Connection replacement |

The Configuration System determines whether a change is valid.

The Connection Manager applies the required transport-level action.

### 25.2 Configuration Revisions

Each physical connection generation references the compiled configuration revision used during establishment.

Conceptually:

    ConnectionGeneration {
        connection_id
        generation
        configuration_revision
    }

A connection must not silently adopt incompatible handshake settings after establishment.

### 25.3 Controlled Connection Replacement

When a configuration change requires replacement:

    New Configuration Revision
              |
              v
    Validate Transport Requirements
              |
              v
    Reserve Replacement Capacity
              |
              v
    Establish New Connection
              |
              v
    Verify Transport Readiness
              |
              v
    Coordinate Subscription Migration
              |
              v
    Fence Old Generation
              |
              v
    Release Old Connection

This sequence is preferred when resources and exchange constraints permit overlapping connections.

Otherwise, the runtime may use a controlled stop-then-start replacement.

The selected replacement policy must be explicit.

### 25.4 Failed Configuration Replacement

If replacement fails:

- Preserve the existing connection when it remains valid.
- Report the failed revision.
- Release replacement resources.
- Avoid changing the applied configuration revision.
- Retry only when the failure is recoverable.

An invalid configuration must not unnecessarily terminate healthy connections.

## 26. Connection Observability

Connection state must be visible through the Metrics Registry, runtime API, and TUI.

MarketForge does not require Prometheus or Grafana.

### 26.1 Connection Metrics

| Metric | Description |
|---|---|
| connections_total | Total managed connections |
| connections_connected | Currently connected sockets |
| connections_reconnecting | Connections undergoing recovery |
| connections_degraded | Connections with degraded health |
| connection_attempts_total | Connection attempts |
| connection_failures_total | Failed connection attempts |
| connection_reconnects_total | Successful reconnections |
| connection_uptime_seconds | Current connection uptime |
| connection_bytes_received_total | Received transport bytes |
| connection_bytes_sent_total | Transmitted transport bytes |
| connection_frames_received_total | Received WebSocket frames |
| connection_frames_sent_total | Transmitted WebSocket frames |
| connection_heartbeat_rtt | Heartbeat round-trip time |
| connection_inbound_queue_depth | Inbound queue occupancy |
| connection_outbound_queue_depth | Outbound queue occupancy |
| connection_backpressure_total | Backpressure incidents |
| connection_last_error | Latest classified failure |
| connection_next_retry_at | Scheduled reconnection time |

Metrics must be scoped appropriately by connection, endpoint,
exchange, and runtime.

Connection lifecycle metrics and connection-health metrics describe
different operational dimensions.

In particular:

- `connections_connected` counts physical connections whose
  authoritative `ConnectionState` is `Connected`.
- `connections_reconnecting` counts physical connections whose
  authoritative `ConnectionState` is `Reconnecting`.
- `connections_degraded` counts connections classified as having
  degraded connection health. It does not count a
  `ConnectionState::Degraded` variant.
- `connection_heartbeat_rtt` describes transport responsiveness,
  not exchange market-data latency.
- `connection_last_error` and `connection_next_retry_at` expose
  diagnostic information rather than lifecycle states.

A connection may contribute to both `connections_connected`
and `connections_degraded` simultaneously.

These gauges must not be treated as mutually exclusive
lifecycle categories.

The Connection Manager owns physical connection lifecycle
and produces the corresponding authoritative observations.

The Metrics Registry owns metric aggregation and snapshot
publication.

Connection-health classification follows the HealthEvaluator
contracts defined in Document 12.

The Connection Manager may consume health assessments when
applying an approved connection-replacement or escalation policy,
but health evaluation must not independently mutate
`ConnectionState`.

Connection metrics must not be used as substitutes for
native subscription state, logical stream lifecycle,
or acquisition readiness.

The final metric names, types, and aggregation contracts
are governed by Document 12.

### 26.2 Connection Diagnostics

The Connection Manager exposes authoritative physical connection
state through read-only operational snapshots.

Connection lifecycle, connection health, and source-stream
acquisition readiness must remain distinguishable.

#### Connection Snapshot

Conceptual fields:

    ConnectionId
    ConnectionGeneration
    Exchange
    Endpoint
    ProtocolVersion
    ConnectionState
    AssignedSubscriptions
    ConnectedAt
    LastReceivedAt
    LastSentAt
    LastHeartbeatAt
    CurrentBackoff
    NextRetryAt
    LastError

`ConnectionState` uses the authoritative enum defined in
Document 02, Section 7.3.

The Connection Manager is the authoritative owner of
connection lifecycle and generation information.

#### Connection Health

The operational view may additionally include:

    ConnectionHealth
    LastHealthEvaluationAt
    HeartbeatRTT
    RecentHeartbeatFailures
    InboundQueueUtilization
    OutboundQueueUtilization

Connection health is independently evaluated using the
contracts in Section 15 and Document 12.

For example:

    ConnectionState:  Connected
    ConnectionHealth: Degraded

This is a valid operational snapshot.

`Degraded` is a health classification, not a
`ConnectionState` variant.

#### Acquisition Independence

A connection snapshot does not independently establish
whether any source stream using that connection is ready.

Multiple source streams may share one physical connection
while having different:

- Native subscription states.
- Processor initialization states.
- Market-data integrity states.
- Recovery states.
- Acquisition-readiness outcomes.

The Control API and Ratatui must obtain those observations
from their authoritative component owners.

A connected physical transport must never be presented
as proof that all associated streams are acquisition-ready.

#### Snapshot Consistency

Snapshots should include an observation timestamp and
the current connection generation.

Observations from obsolete connection generations must
not overwrite current state.

When connection and health information originate from
different components, the snapshot must not claim
atomic consistency unless that guarantee is explicitly
provided.

Missing diagnostic information must remain distinguishable
from a healthy or zero-valued observation.

Snapshots must not expose authentication secrets,
credentials, or sensitive handshake values..

### 26.3 TUI Integration

The TUI may display:

- Active connections.
- Exchange and endpoint.
- Connection health.
- Number of assigned subscriptions.
- Connection uptime.
- Heartbeat RTT.
- Inbound and outbound throughput.
- Reconnection attempts.
- Last error.
- Pending recovery.

Connection-level controls should remain minimal.

A manual connection restart must use the same lifecycle and generation-safety mechanisms as automatic recovery.

### 26.4 Local Logging

Connection lifecycle events are written to local structured logs.


Connection lifecycle events include:

    ConnectionCreated
    ConnectionAttemptStarted
    ConnectionEstablished
    ConnectionLost
    ConnectionReconnectScheduled
    ConnectionRestored
    ConnectionClosing
    ConnectionClosed
    ConnectionFailed

Connection-health events are reported separately.

For example:

    ConnectionHealthDegraded
    ConnectionHealthUnhealthy
    ConnectionHealthRecovered

These are conceptual operational-event names.

The final shared event vocabulary belongs to the
operational event and observability contracts in
Documents 02 and 12.

A health event must not be interpreted as an
authoritative `ConnectionState` transition.

A connection may experience health degradation
without disconnecting.

Connection lifecycle logs should include the
connection identity, generation, endpoint
classification, timestamps, and transition reason.

Connection-health logs should identify the affected
connection and the relevant health assessment
without claiming that the physical lifecycle changed.

Logging must not independently mutate connection
lifecycle, health, or subscription state.

Logs should include connection identity, generation, endpoint classification, timestamps, and failure reasons.

Authentication credentials, secrets, and sensitive headers must never be logged.

Operational logs are not stored in PostgreSQL.

## 27. Testing Strategy

The Connection Manager requires deterministic unit tests, asynchronous integration tests, protocol compatibility tests, and fault-injection tests.

Testing must verify not only successful connectivity but also correct behavior during failures, cancellation, reconnection, resource exhaustion, and concurrent operations.

The initial implementation should prioritize tests that establish **connection lifecycle correctness, generation safety, and resource ownership**.

### 27.1 Unit Tests

Unit tests must cover connection state transitions without requiring live exchange connectivity.

Required tests:

- Valid connection lifecycle transitions.
- Rejection of invalid state transitions.
- Connection generation increments.
- Connection pool key construction.
- Connection compatibility evaluation.
- Connection capacity reservations.
- Reservation release after failure.
- Duplicate connection creation prevention.
- Reconnection backoff calculations.
- Jitter bounds.
- Backoff reset after stable operation.
- Connection shutdown idempotency.
- Obsolete-generation event rejection.

Connection state-machine tests must use deterministic inputs.

### 27.2 Connection Pool Tests

Verify that compatible subscriptions can share physical connections.

Example:

    OKX Public Connection
             |
             +-- Spot L2
             +-- Linear L2
             +-- Inverse L2

The test must confirm that compatible subscriptions reuse an existing connection when capacity permits.

Additional tests must verify that incompatible requirements produce separate connections.

Examples include:

- Different WebSocket endpoints.
- Different authentication contexts.
- Different handshake headers.
- Different protocol versions.
- Incompatible heartbeat requirements.
- Explicit connection isolation policies.

The pool must never assign a subscription to a connection that cannot satisfy its transport requirements.

### 27.3 Capacity Tests

Verify:

- Maximum connection limits.
- Maximum connections per endpoint.
- Maximum subscriptions per connection.
- Concurrent connection reservations.
- Reservation cancellation.
- Reservation expiration.
- Capacity release after connection closure.
- Capacity release after failed establishment.
- Capacity accounting during connection replacement.

A connection pool must never exceed its effective configured capacity.

Transport integration tests exercise the Reader, Writer, Heartbeat Controller, and Connection Supervisor together.

Tests should use a local mock WebSocket server.

External exchange connectivity is not required for deterministic transport tests.

### 28.1 Reader Tests

- Receipt timestamp assignment.
- Connection-local frame ordering.

- Outbound queue capacity.
- Command deadline expiration.

### 28.3 Routing Tests

- Market-data frame classification.

- Exchange error routing.

    Exchange Outage
          |
          +-- Connection A fails

    Generation 4 connected
             |
             v

             |

## 33. Property-Based Testing

Property-based tests should explore arbitrary valid operation sequences and asynchronous completion orderings.

### 33.1 Connection Invariants

Required invariants:

    One authoritative generation per ConnectionId.

    One authoritative lifecycle state per connection.

    No obsolete generation may modify current state.

    No connection exceeds its effective capacity.

    No incompatible subscriptions share a connection.

    No physical socket has multiple independent writers.

    Every connection resource has one defined owner.

    Resource release is idempotent.

    Reconnection attempts respect rate limits.

    Shutdown eventually terminates all owned tasks.

### 33.2 Concurrency Invariants

Required invariants:

    Concurrent connection requests cannot exceed capacity.

    Duplicate failure events cannot create duplicate reconnects.

    A cancelled connection attempt cannot become authoritative.

    An obsolete heartbeat timeout cannot close a newer socket.

    Connection replacement cannot reuse an obsolete generation.

    Failed connection establishment cannot leak reservations.

    Connection shutdown cannot leave active transport tasks.

### 33.3 Model-Based Lifecycle Testing

The Connection Manager state machine should be tested against a simplified reference model.

Generate sequences containing:

    Connect
    ConnectionSucceeded
    ConnectionFailed
    HeartbeatFailed
    Reconnect
    Cancel
    Replace
    Close
    Shutdown

Compare the implementation's resulting state with the reference model.

Invalid transitions must produce explicit errors without corrupting connection state.

## 34. Implementation Acceptance Criteria

The Connection Manager is considered complete when the following requirements are satisfied.

### 34.1 Architecture

- Physical connection ownership is centralized.
- Connection lifecycle is independent of logical stream lifecycle.
- Exchange-specific protocols are implemented through adapters.
- Compatible subscriptions can share physical connections.
- Connection requirements are validated before admission.
- Transport Reader and Writer tasks have explicit ownership.
- Connection generations prevent stale operations.
- Resource allocation and release are deterministic.

### 34.2 Connectivity

- All configured exchange endpoints are supported.
- WebSocket handshake requirements are enforced.
- Text and binary frames are supported.
- Control frames are handled correctly.
- Required exchange heartbeat strategies are supported.
- Silent connection failures are detected.
- Connection closure is handled explicitly.

### 34.3 Fault Tolerance

- Transient failures trigger bounded reconnection.
- Permanent configuration failures stop automatic retries.
- Exponential backoff and jitter are supported.
- Exchange cooldowns override ordinary retry timing.
- Shared connection-attempt budgets are enforced.
- Reconnection storms are prevented.
- Obsolete connection generations are fenced.
- Subscription restoration is coordinated externally.

### 34.4 Resource Safety

- Connection and queue capacities are bounded.
- Resource reservations are atomic.
- Failed operations release resources.
- No silent market-data frame dropping occurs.
- Sustained overload produces explicit escalation.
- Graceful shutdown has a finite deadline.
- All connection tasks terminate during shutdown.

### 34.5 Observability

- Connection lifecycle events are exposed.
- Connection health is measurable.
- Heartbeat RTT is recorded.
- Queue utilization is available.
- Reconnection attempts and failures are tracked.
- Operational logs remain local.
- TUI and API can inspect connection state.
- No Prometheus or Grafana dependency is required.

### 34.6 Testing

- Unit tests pass.
- Transport integration tests pass.
- Heartbeat tests pass.
- Connection pooling tests pass.
- Rate-limit tests pass.
- Reconnection fault-injection tests pass.
- Generation-safety tests pass.

## 35. Final Architectural Contract

The Connection Manager provides reliable physical connectivity to exchange market-data endpoints.

It does not guarantee that every market-data event has been received or that an order book is synchronized.

Those guarantees belong to the Stream Processor and Recovery Coordinator.

The ownership chain is:

    Stream Registry
          |
          v
    Subscription Manager
          |
          v
    Connection Manager
          |
          v
    Exchange Transport
          |
          v
    Exchange Protocol Adapter
          |
          v
    Stream Processor
          |
          v
    Normalization and Integrity
          |
          v
    Canonical Market Events

The Connection Manager guarantees:

- Explicit physical connection ownership.
- Generation-safe transport operations.
- Bounded resource consumption.
- Exchange-compliant connection admission.
- Configurable heartbeat and liveness management.
- Controlled reconnection and backoff.
- Correct coordination with subscription restoration.
- Explicit failure and overload reporting.
- Deterministic shutdown and resource cleanup.

It does not implement exchange-specific market-data normalization, trade-history recovery, order-book reconstruction, or canonical event publication.

These responsibilities remain with their respective components.
