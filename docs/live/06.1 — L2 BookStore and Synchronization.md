## 1. Purpose

The L2 BookStore and Synchronization subsystem maintains authoritative, exchange-derived Level 2 order-book state for MarketForge Live.

It receives validated and normalized snapshots and incremental updates, reconstructs the observable order book, verifies continuity, and provides consistent book state to downstream consumers.

The subsystem must support all five initial exchanges:

- Binance
- Bybit
- OKX
- Bitget
- Gate.io

Across three market families:

- Spot
- Linear
- Inverse

The implementation must be **exchange-agnostic, configuration-driven, deterministic, fault-tolerant, and suitable for high-throughput Rust processing**.

Exchange-specific synchronization rules are supplied by the compiled depth-format specifications defined in **04 — Exchange Protocols and Connectivity**.

### 1.1 Primary Objectives

The subsystem must:

- Maintain independent order books for active L2 source streams.
- Initialize books from authoritative snapshots.
- Buffer incremental updates during synchronization.
- Validate native sequence continuity.
- Apply valid updates atomically.
- Maintain bid and ask price levels.
- Interpret absolute quantities and zero-quantity deletions.
- Track observable depth coverage.
- Preserve book-generation identity.
- Detect invalid or inconsistent book states.
- Prevent obsolete updates from corrupting newer generations.
- Support controlled resynchronization.
- Expose consistent book views.
- Coordinate canonical L2 event publication.
- Provide operational metrics and diagnostics.

The BookStore must never fabricate missing liquidity or silently repair sequence gaps.

### 1.2 Core Principle

A received L2 message is not necessarily equivalent to a valid order-book update.

MarketForge distinguishes:

    Message Received
           |
           v
    Message Structurally Valid
           |
           v
    Native Sequence Valid
           |
           v
    Book Mutation Valid
           |
           v
    Book State Committed
           |
           v
    Canonical Event Accepted

Only successfully committed updates may advance authoritative book state.

### 1.3 Scope

This document defines:

- BookStore ownership and domain models.
- In-memory bid and ask representations.
- Snapshot initialization and replacement.
- Buffered-delta synchronization.
- Native sequence validation integration.
- Atomic book mutations.
- Depth coverage and truncation.
- Book-generation fencing.
- Consistent read access.
- Publication boundaries.
- Resource limits and performance requirements.
- Fault injection and testing.

System-wide recovery orchestration remains the responsibility of **07 — Fault Tolerance and Recovery**.

## 2. Architectural Boundaries

The BookStore is a stateful processing component.

It does not own exchange connections, native subscriptions, instrument metadata acquisition, or network recovery.

### 2.1 Component Responsibilities

| Component | Responsibility |
|---|---|
| Stream Registry | Logical stream lifecycle and desired state |
| Subscription Manager | Native L2 subscription activation |
| Connection Manager | Physical WebSocket transport |
| Exchange Protocol Adapter | Native message classification |
| L2 Normalizer | Price-level extraction and economic normalization |
| Sequence Validator | Native continuity validation |
| Synchronization Coordinator | Snapshot acquisition and buffered-delta synchronization |
| BookStore | Authoritative bid/ask state and atomic mutations |
| Recovery Coordinator | Recovery scheduling and escalation |
| Publisher | Canonical L2 event distribution |
| Recording Manager | Optional market-data recording |
| Metrics Registry | Book health and processing measurements |

The BookStore does not issue REST requests.

It receives validated snapshot candidates and updates from the Synchronization Coordinator and L2 processing pipeline.

This diagram represents logical responsibilities.

For performance, validation, synchronization, and BookStore mutation may execute within the same per-stream processing task.

The implementation must preserve their semantic boundaries.

### 2.3 Ownership Rules

The BookStore exclusively owns:

- Authoritative bid price levels.
- Authoritative ask price levels.
- Current book-generation state.
- Last committed native sequence state.
- Observable depth coverage.
- Book validity status.
- Atomic mutation boundaries.

The Synchronization Coordinator owns:

- Snapshot initialization workflows.
- Buffered updates awaiting synchronization.
- Snapshot-to-delta bridging.
- Synchronization attempts.
- Synchronization deadlines.
- Initialization failure reporting.

The Recovery Coordinator owns:

- Recovery decisions.
- Retry and escalation policies.
- Recovery scheduling.
- Coordination after unrecoverable synchronization failures.

The Stream Registry owns the logical source-stream lifecycle.

These responsibilities must not be duplicated.

### 2.4 Design Constraints

- Rust-only hot-path implementation.
- No Python calls during L2 processing.
- No PostgreSQL queries during L2 processing.
- No direct TUI dependencies.
- No exchange-specific BookStore implementations.
- No floating-point representation of authoritative prices or quantities.
- No partial application of invalid updates.
- No silent sequence-gap repair.
- No publication of invalid synchronized-book state.
- No mixing of incompatible normalization revisions.
- No application of obsolete connection or subscription generations.
- No unbounded update buffering.
- No assumption that limited-depth books represent complete market depth.
- No implicit reconstruction of missed historical L2 events.

A failed synchronization attempt must not corrupt an existing valid book generation.

## 3. BookStore Domain Models

The BookStore maintains one authoritative book state for each active L2 source stream.

### 3.1 Book Identity

A book is identified by its logical source-stream identity.

Conceptually:

    BookId = StreamId

The BookStore must not use a physical WebSocket connection as its primary identity.

Multiple books may share one connection.

A book must remain logically identifiable across reconnections and resynchronization attempts.

### 3.2 BookDescriptor

Immutable book definition.

| Field | Type | Purpose |
|---|---|---|
| book_id | BookId | Stable logical book identity |
| stream_id | StreamId | Owning L2 source stream |
| instrument_id | InstrumentId | Canonical instrument |
| exchange | ExchangeId | Exchange identity |
| market | MarketCategory | Spot, Linear, Inverse |
| native_channel | String | Exchange L2 channel |
| channel_parameters | ChannelParameters | Depth, frequency, variants |
| format_id | FormatId | Compiled L2 format |
| configuration_revision | RevisionId | Effective processing configuration |

The descriptor remains immutable for one subscription definition.

Changing the instrument or native subscription identity requires controlled stream replacement.

### 3.3 BookRuntime

Mutable authoritative book state.

Conceptually:

    BookRuntime {
        book_id
        stream_id

        connection_generation
        subscription_generation
        book_generation

        metadata_revision
        configuration_revision

        lifecycle_state
        validity_state

        bids
        asks

        sequence_state
        depth_coverage

        last_event_timestamp
        last_update_received_at
        last_committed_at
    }

This structure is illustrative.

The implementation must reuse canonical identifiers and numerical types defined in **02 — Domain Models and Contracts**.

### 3.4 Book Lifecycle

The BookStore maintains a state independent of the Stream Registry lifecycle.

Supported states:

    Uninitialized
    Synchronizing
    Synchronized
    Invalid
    Replacing
    Closed

| State | Meaning |
|---|---|
| Uninitialized | Book exists but has no authoritative state |
| Synchronizing | Snapshot/delta initialization underway |
| Synchronized | Current book generation satisfies continuity requirements |
| Invalid | Book state cannot be trusted |
| Replacing | New authoritative state being prepared |
| Closed | Book resources released |

The Stream Registry may report an L2 stream as `Synchronizing` while the BookStore initializes.

An L2 stream must not be considered fully active until its required book synchronization conditions are satisfied.

### 3.5 Book Validity

Lifecycle and validity are separate concepts.

Conceptual validity classifications:

    Unknown
    Valid
    Invalid
    Stale

**Unknown**

An authoritative book baseline has not yet been established.

**Valid**

The current book generation satisfies the configured synchronization and integrity requirements.

**Invalid**

A detected failure makes the current state untrustworthy.

**Stale**

The book has not received expected updates within a configured freshness policy, but continuity has not necessarily been disproven.

Staleness alone must not be treated as confirmed sequence loss.

A low-activity instrument may legitimately produce infrequent updates.

### 3.6 Book Generations

Every authoritative initialization creates a book generation.

Conceptually:

    BookId = 15

    BookGeneration = 1
        Initial snapshot

    BookGeneration = 2
        Recovery after sequence gap

    BookGeneration = 3
        Recovery after reconnection

The BookStore must reject updates referencing obsolete generations.

A generation is associated with:

    StreamId
    ConnectionGeneration
    SubscriptionGeneration
    BookGeneration
    MetadataRevision
    ConfigurationRevision

These identities prevent updates from incompatible runtime incarnations from being combined.

### 3.7 Sequence State Ownership

The BookStore stores the last committed native sequence state.

The Sequence Validator determines whether a candidate transition is valid.

Conceptually:

    Current Book Sequence
             |
             v
    Validate Candidate Sequence
             |
             v
    Prepare Book Mutation
             |
             v
    Commit Book Mutation
             |
             v
    Advance Sequence State

The sequence must not advance before the corresponding book mutation commits.

This guarantees that book contents and sequence state describe the same accepted exchange update.

## 4. Book-Level Domain Model

An L2 order book consists of bid and ask price levels.

Each level represents aggregate resting quantity at a particular price.

### 4.1 BookLevel

Conceptual structure:

    BookLevel {
        price
        quantity
        order_count
    }

Where:

- `price` is an exact canonical decimal.
- `quantity` is an exact canonical economic quantity.
- `order_count` is optional native metadata.

The actual BookLevel type must remain compatible with the existing MarketForge BookStore and canonical domain contracts.

### 4.2 Bid and Ask State

The BookStore maintains two independent sides:

    Bids
    Asks

Bids are ordered by descending price.

Asks are ordered by ascending price.

Conceptually:

    BIDS                   ASKS

    64999.00 -> 2.5        65000.00 -> 1.8
    64998.00 -> 4.2        65001.00 -> 3.1
    64997.00 -> 1.1        65002.00 -> 2.4

The best bid is the highest bid price.

The best ask is the lowest ask price.

### 4.3 Price-Level Identity

Within one book side, a price uniquely identifies a resting-liquidity level.

Conceptually:

    LevelKey = Price

The same price may theoretically appear on both sides in malformed or crossed-book conditions.

The BookStore must not merge bid and ask levels solely because their prices match.

### 4.4 Supported Level Operations

The initial BookStore supports:

    Insert
    Replace
    Delete

**Insert**

Add a new resting price level.

**Replace**

Set the quantity of an existing level to the new absolute quantity.

**Delete**

Remove a resting price level.

The BookStore must not treat exchange-native absolute updates as additive changes.

### 4.5 Zero-Quantity Semantics

For the configured initial protocols:

    quantity = 0

means:

    Delete Level

Example:

    Existing:
        Bid 64999 -> 2.5

    Incoming:
        Bid 64999 -> 0

    Result:
        Level removed

The deletion operation is valid even if the level is already absent, provided the selected protocol and integrity policy permit idempotent deletion.

The processor must not introduce a zero-quantity resting level.

### 4.6 Native and Canonical Quantities

The BookStore must distinguish native quantity units from canonical economic quantities.

Possible native units:

    BaseAsset
    QuoteAsset
    Contracts

For contract-denominated books, normalization uses immutable instrument metadata.

Example:

    Native quantity:
        100 contracts

    Instrument contract value:
        1 USD per contract

    Price:
        65000 USD/BTC

    Derived quote quantity:
        100 USD

    Derived base quantity:
        100 / 65000 BTC

The contract value is illustrative.

The actual conversion uses the instrument catalog.

### 4.7 Quantity Storage Strategy

The initial implementation should store the canonical quantity representation required by the existing BookStore contract.

However, normalization-critical metadata changes introduce an important consideration.

If the BookStore retains only derived quantities, a contract-value change may require complete reconstruction from an authoritative snapshot.

If it retains exact native quantities, some revisions may be applied through deterministic re-normalization.

The supported strategy must be explicit.

The initial conservative policy is:

    RebuildFromAuthoritativeSnapshot

for normalization-critical metadata changes that cannot be safely applied to existing book state.

## 5. In-Memory Book Representation

The BookStore maintains an ordered representation of resting liquidity for each active L2 source stream.

The underlying data structures must support efficient:

- Price-level lookup.
- Price-level insertion.
- Absolute quantity replacement.
- Price-level deletion.
- Best bid and best ask retrieval.
- Ordered depth traversal.
- Atomic message application.
- Snapshot replacement.
- Consistent book views.

The implementation must prioritize correctness and predictable memory usage before introducing specialized optimizations.

### 5.1 BookSide

Each book contains two independently ordered sides:

    BookSide::Bid
    BookSide::Ask

Both sides use the same price-level storage abstraction.

Their traversal order differs:

    Bid: descending price
    Ask: ascending price

Conceptually:

    OrderBook {
        bids: BookSide
        asks: BookSide
    }

The BookStore must not implement separate exchange-specific bid and ask storage structures.

### 5.2 Initial Data Structure

The recommended initial representation is an ordered map keyed by exact price.

Conceptually:

    BTreeMap<Price, BookLevel>

Rust's `BTreeMap` provides:

- Deterministic key ordering.
- Efficient lookup.
- Efficient insertion and removal.
- Ordered iteration.
- No requirement for custom tree algorithms.
- Straightforward correctness testing.

The initial implementation should use one ordered map per book side.

A specialized structure may replace it later if benchmarks demonstrate a meaningful performance advantage.

### 5.3 Price Keys

Price keys must use the canonical exact-decimal representation.

Binary floating-point values must not be used as authoritative map keys.

The price representation must provide a total ordering consistent with numerical ordering.

For example:

    65000.0
    65000.00

must compare as the same economic price.

Otherwise, the BookStore could accidentally create two distinct levels for one price.

The decimal key implementation must therefore normalize comparison semantics.

### 5.4 Bid Ordering

Bid levels are ordered from highest to lowest price.

Example:

    Price       Quantity

    65000.00    1.25
    64999.00    2.50
    64998.00    4.10

The best bid is:

    max(bid_prices)

If a `BTreeMap` stores prices in ascending order, bid traversal uses reverse iteration.

The storage representation does not need a custom descending comparator.

### 5.5 Ask Ordering

Ask levels are ordered from lowest to highest price.

Example:

    Price       Quantity

    65001.00    1.80
    65002.00    3.20
    65003.00    1.15

The best ask is:

    min(ask_prices)

With ascending map storage, ask traversal uses forward iteration.

### 5.6 Best Bid and Best Ask

The BookStore must provide efficient access to:

    BestBid
    BestAsk

Conceptually:

    best_bid = highest bid price

    best_ask = lowest ask price

The best bid and best ask may be unavailable when the corresponding side is empty.

The API must represent missing levels explicitly.

It must not substitute zero prices.

### 5.7 Top-N Retrieval

The BookStore must support retrieving the best N levels from each side.

Conceptually:

    get_top_bids(N)

    get_top_asks(N)

Top-N retrieval must preserve price ordering.

The operation should avoid copying the entire book when only a small number of levels is requested.

For example:

    N = 10

should not require materializing 1,000 levels merely to return the best ten.

### 5.8 Storage Abstraction

The exact storage structure should remain behind a small internal interface.

Conceptually:

    BookSideStorage {
        insert_or_replace(price, quantity)
        remove(price)
        get(price)
        best()
        iter_best_first()
        level_count()
        clear()
    }

This permits later optimization without changing synchronization or canonical event contracts.

## 6. Price-Level Operations

The BookStore applies normalized price-level operations to its internal state.

The initial supported mutation types are:

    Insert
    Replace
    Delete

### 6.1 Insert

An insert creates a price level that does not currently exist.

Example:

    Before:

        Bid 65000 -> 2.0
        Bid 64999 -> 3.0

    Incoming:

        Bid 64998 -> 1.5

    After:

        Bid 65000 -> 2.0
        Bid 64999 -> 3.0
        Bid 64998 -> 1.5

The inserted quantity must be positive.

### 6.2 Replace

A replacement assigns a new absolute quantity to an existing level.

Example:

    Before:

        Ask 65001 -> 5.0

    Incoming:

        Ask 65001 -> 2.0

    After:

        Ask 65001 -> 2.0

The quantity is not added to the previous value.

### 6.3 Delete

A deletion removes the entire price level.

Example:

    Before:

        Bid 64999 -> 3.0

    Incoming:

        Bid 64999 -> 0

    After:

        Bid 64999 absent

Zero quantity is interpreted as deletion for the configured initial L2 protocols.

### 6.4 Upsert Semantics

For absolute-quantity delta protocols, insertion and replacement can be represented by one operation:

    SetLevel(price, quantity)

Semantics:

    quantity > 0:
        insert or replace

    quantity == 0:
        delete

This allows the generic BookStore to avoid exchange-specific mutation logic.

### 6.5 Deleting Missing Levels

An exchange may send a zero-quantity update for a price level not currently present in the local book.

This can occur legitimately when:

- The book represents only a depth-limited portion of the market.
- A price level was previously outside the observed coverage.
- The exchange publishes repeated deletions.

The initial policy should permit idempotent deletion when the selected protocol allows it.

However, deletion of an unknown level must not be used to conceal a sequence violation.

Sequence validation occurs independently.

### 6.6 Mutation Ordering

When one delta contains multiple price-level operations, the processor must preserve the ordering semantics defined by the exchange protocol.

If the protocol treats each price as one final absolute value, operations may be consolidated only when doing so preserves identical results and provenance.

If repeated levels have meaningful sequential semantics, their native order must be preserved.

The BookStore must not arbitrarily sum repeated quantities.

## 7. Atomic Book Mutations

Every accepted L2 message must produce one logically atomic state transition when the exchange protocol defines message-level atomicity.

The BookStore must never expose a partially applied update.

### 7.1 Atomicity Requirement

Given one native delta:

    Bid updates:
        65000 -> 2.5
        64999 -> 0

    Ask updates:
        65001 -> 1.0
        65002 -> 3.5

The resulting book must transition directly from:

    State N

to:

    State N+1

Consumers must not observe an intermediate state in which only the bid updates have been applied.

### 7.2 Mutation Transaction

Conceptually:

    Normalized Delta
           |
           v
    Validate Message
           |
           v
    Validate Native Sequence
           |
           v
    Prepare Mutation
           |
           v
    Apply Changes
           |
           v
    Validate Result
           |
       +---+---+
       |       |
       v       v
     Valid   Invalid
       |       |
       v       v
    Commit   Rollback
       |
       v
    Advance Sequence
       |
       v
    Publish Event

The update must not become authoritative before all required validation succeeds.

### 7.3 Atomicity Implementation

The implementation may use:

- Copy-on-write state replacement.
- A mutation journal with rollback.
- A temporary working state.
- Exclusive mutation ownership with staged validation.
- Another proven transactional strategy.

The initial implementation should favor a strategy that avoids copying the entire book for every incremental update.

For example, a mutation journal may record the previous value of each affected level.

Conceptually:

    MutationJournal {
        side
        price
        previous_value
    }

If the update fails, the journal restores the previous state.

### 7.4 Rollback Requirements

Rollback must restore:

- Bid levels.
- Ask levels.
- Level counts.
- Best bid and best ask.
- Relevant derived book metadata.
- Native sequence state.
- Book version.

The BookStore must not leave partially modified state after a failed update.

If rollback cannot be guaranteed, the book must be invalidated and replaced from an authoritative snapshot.

### 7.5 Sequence Commit Atomicity

Book mutation and native sequence advancement belong to the same logical transaction.

The following state is invalid:

    Book levels updated

    Sequence state unchanged

The following state is also invalid:

    Sequence state advanced

    Book levels unchanged

For an accepted delta, both must describe the same exchange update.

Conceptually:

    Commit {
        book_mutation
        sequence_transition
        book_version_increment
    }

All three occur atomically from the perspective of downstream readers.

### 7.6 Snapshot Atomicity

Snapshots use atomic replacement rather than incremental mutation.

The recommended procedure is:

    Build New Book
          |
          v
    Validate Snapshot
          |
          v
    Establish Sequence Baseline
          |
          v
    Assign Book Generation
          |
          v
    Atomically Replace Current Book

A malformed snapshot must not partially overwrite an existing valid book.

### 7.7 Publication Atomicity

A committed book update and its canonical L2 event must refer to the same transition.

The processing pipeline must preserve:

    Committed Book Version
             |
             v
    Canonical L2 Event
             |
             v
    Publication Queue

If publication fails after the book commits, the BookStore must not silently pretend the update was delivered.

The publisher's delivery and backpressure contract determines whether processing blocks, buffers, or escalates.

The BookStore must preserve enough transition identity to report or recover from a publication failure.

## 8. Book Versioning

The BookStore maintains a monotonically increasing local version for every committed state transition.

### 8.1 BookVersion

Conceptually:

    BookVersion = u64

The version increases after every accepted book mutation.

Example:

    Version 1:
        Initial snapshot

    Version 2:
        First delta

    Version 3:
        Second delta

This version is independent of exchange-native sequence identifiers.

### 8.2 Version Identity

A book version is identified by:

    StreamId
    BookGeneration
    BookVersion

The version must not be used as a replacement for native sequence validation.

Its purpose is to identify a locally committed book state.

### 8.3 Version Advancement

The initial policy is:

    Snapshot committed:
        book_version = 1

    Delta committed:
        book_version += 1

    New book generation:
        book_version = 1

Rejected and stale updates do not advance the book version.

A valid sequence-only message with no price-level changes may advance the version if the implementation commits an authoritative sequence transition.

That policy must be consistent with the canonical L2 event contract.

### 8.4 Version Overflow

Book versions must use checked arithmetic.

A version counter must never silently wrap.

If the implementation cannot advance the version safely, the BookStore must report a fatal state error.

## 9. Book Mutation Ownership

Each book must have one authoritative mutation owner.

This avoids conflicting updates and unnecessary locking.

### 9.1 Single-Writer Model

The recommended architecture is:

    L2 Stream Processor
            |
            v
    Book Mutation Owner
            |
            v
         BookStore
            |
       +----+----+
       |         |
       v         v
    Publisher   Readers

One processing task serializes mutations for a specific book.

Different books may be processed concurrently.

### 9.2 Concurrency Model

The BookStore should avoid global locking across all instruments.

For example:

    BTCUSDT Book Processor
              |
              v
         BTCUSDT Book

    ETHUSDT Book Processor
              |
              v
         ETHUSDT Book

Both operate independently.

A slow or heavily updated book must not block unrelated books through a shared global mutation lock.

### 9.3 Read Access

Read-only consumers may request:

- Best bid and ask.
- Top-N levels.
- Full observable depth.
- Book validity.
- Book generation.
- Book version.
- Native sequence position.
- Snapshot coverage.

Readers must observe internally consistent states.

They must not read partially applied mutations.

### 9.4 Consistent Book Views

Conceptual read result:

    BookView {
        stream_id
        book_generation
        book_version
        validity
        best_bid
        best_ask
        bids
        asks
        depth_coverage
    }

The view must represent one committed version.

For example, the bid and ask sides must not originate from different versions.

### 9.5 Read Strategies

Possible implementations include:

- Read locks around consistent snapshots.
- Immutable snapshot publication.
- Versioned copy-on-write structures.
- Actor-based query responses.

The initial implementation should favor correctness and predictable resource usage.

A specialized lock-free representation is not required unless measurements justify its complexity.

### 9.6 Read Isolation

Reading one book must not block mutation of unrelated books.

The system should avoid maintaining a single global BookStore write lock.

The registry may coordinate book identities, but individual book state should remain independently owned.

## 10. Snapshot Initialization

Snapshot initialization establishes the authoritative baseline from which an L2 order book can begin processing incremental updates.

MarketForge must support multiple initialization mechanisms without introducing exchange-specific BookStore implementations.

The initialization strategy is selected by the compiled exchange depth configuration.

### 10.1 Supported Initialization Strategies

The initial implementation supports:

    RestSnapshotWithBufferedDeltas
    WebSocketSnapshotWithDeltas
    WebSocketFullSnapshotReplacement

| Strategy | Description |
|---|---|
| RestSnapshotWithBufferedDeltas | Fetch a REST snapshot while buffering WebSocket updates |
| WebSocketSnapshotWithDeltas | Initialize directly from an authoritative WebSocket snapshot |
| WebSocketFullSnapshotReplacement | Replace the book when the exchange sends an authoritative full snapshot |

These strategies may share processing primitives but require different synchronization state machines.

### 10.2 Exchange Initialization Matrix

| Exchange | Market | Primary initialization |
|---|---|---|
| Binance | Spot | REST snapshot + buffered deltas |
| Binance | Linear | REST snapshot + buffered deltas |
| Binance | Inverse | REST snapshot + buffered deltas |
| Bybit | Spot | WebSocket snapshot |
| Bybit | Linear | WebSocket snapshot |
| Bybit | Inverse | WebSocket snapshot |
| OKX | Spot | WebSocket snapshot |
| OKX | Linear | WebSocket snapshot |
| OKX | Inverse | WebSocket snapshot |
| Bitget | Spot | WebSocket snapshot |
| Bitget | Linear | WebSocket snapshot |
| Bitget | Inverse | WebSocket snapshot |
| Gate.io | Spot | REST snapshot + buffered deltas |
| Gate.io | Linear | REST snapshot + buffered deltas |
| Gate.io | Inverse | REST snapshot + buffered deltas |

Gate.io configurations also describe WebSocket full-snapshot variants.

This matrix describes the initial configuration design.

The compiled TOML remains authoritative, and protocol compatibility must be established through recorded exchange fixtures.

### 10.3 Initialization Invariants

Before a book becomes synchronized:

- The native subscription must belong to the current subscription generation.
- Required instrument metadata must be available.
- The normalization context must be valid.
- An authoritative snapshot must be established.
- Buffered updates must satisfy native continuity rules.
- Snapshot and update generations must match.
- Every accepted mutation must be applied atomically.
- Depth coverage must be known or explicitly classified as unknown.
- The resulting book must pass applicable integrity checks.

A successful WebSocket subscription acknowledgement is not sufficient to establish L2 readiness.

## 11. Synchronization Coordinator

The Synchronization Coordinator owns the process of establishing and restoring synchronized L2 state.

It coordinates snapshot acquisition, delta buffering, sequence bridging, and initialization completion.

It does not own the physical WebSocket connection or the authoritative BookStore contents.

### 11.1 Responsibilities

The Synchronization Coordinator must:

- Select the compiled synchronization strategy.
- Establish the current synchronization attempt.
- Prepare bounded delta buffering.
- Request snapshots where required.
- Validate snapshot provenance.
- Match snapshots with buffered updates.
- Apply synchronization rules.
- Coordinate atomic snapshot installation.
- Replay valid buffered updates.
- Detect initialization gaps.
- Reject obsolete synchronization attempts.
- Report success or failure to the Stream Registry and Recovery Coordinator.

### 11.2 SynchronizationAttempt

Conceptual representation:

    SynchronizationAttempt {
        stream_id
        connection_generation
        subscription_generation
        synchronization_generation
        configuration_revision
        metadata_revision
        strategy
        started_at
        deadline
        buffered_updates
        status
    }

The exact Rust type is an implementation detail.

The synchronization generation uniquely identifies one initialization or resynchronization attempt for a logical book.

### 11.3 Synchronization States

Supported states:

    Idle
    Buffering
    AwaitingSnapshot
    Bridging
    Replaying
    Validating
    Synchronized
    Failed
    Cancelled

| State | Meaning |
|---|---|
| Idle | No synchronization attempt is active |
| Buffering | Incoming updates are being retained |
| AwaitingSnapshot | Waiting for an authoritative snapshot |
| Bridging | Matching snapshot sequence with buffered deltas |
| Replaying | Applying buffered updates in protocol order |
| Validating | Checking the reconstructed book |
| Synchronized | Valid authoritative generation established |
| Failed | Synchronization cannot be completed |
| Cancelled | Attempt superseded or explicitly stopped |

### 11.4 Attempt Identity

    SubscriptionGeneration
    SynchronizationGeneration

    BookGeneration

This rule applies even when an obsolete REST request returns a structurally valid snapshot.

### 11.5 Single Active Attempt

Only one synchronization attempt may be authoritative for a given book.

A newer attempt supersedes the previous one.

Conceptually:

    Attempt 7 started
           |

    Attempt 8 started
           |

    Attempt 7 REST response arrives
           |

    Start WebSocket Buffering

    Request REST Snapshot

- Successful response classification.

- Correct native instrument.
- Valid sequence identifier.
- Valid price-level representations.
- Compatible quantity semantics.
- Valid normalization context.
- Applicable depth coverage requirements.

### 12.5 Snapshot and Buffer Compatibility

The snapshot and buffered updates must belong to compatible protocol contexts.

The coordinator verifies:

    Same instrument
    Same native channel semantics
    Same subscription generation
    Same normalization revision
    Compatible sequence domain

An exchange REST snapshot may not expose a connection generation because REST and WebSocket use different transports.

Instead, the coordinator must associate the REST request with the current synchronization attempt and verify that the corresponding WebSocket subscription remains valid.

### 12.6 Initial Sequence Bridge

For protocols using an inclusive update range:

    snapshot_id = S

    next_required = S + 1

The first applicable buffered update must satisfy:

    U <= next_required <= u

Buffered updates with:

    u < next_required

are obsolete relative to the snapshot and may be discarded.

An update beginning after the required ID indicates that the buffer does not bridge the snapshot.

However, this specific formula is not universal.

The compiled synchronization strategy determines the correct bridge rule.

### 12.7 Buffered Update Replay

After locating a valid bridge:

- Initialize candidate book state from the snapshot.
- Apply the bridging update.
- Validate each subsequent update.
- Advance candidate sequence state.
- Continue until the buffered backlog is processed.
- Transition to live processing without introducing an ordering gap.

The replay mechanism must prevent newly arriving messages from overtaking earlier buffered updates.

### 12.8 Transition to Live Processing

Synchronization must define an atomic transition from buffered replay to normal live processing.

Conceptually:

    Buffered Updates
            |
            v
    Replay to Current Frontier
            |
            v
    Establish Live Handoff Boundary
            |
            v
    Commit Candidate Book
            |
            v
    Continue Ordered Live Updates

There must be no interval in which messages are neither buffered nor processed.

The handoff should occur through the same serialized per-book processing owner whenever possible.

## 14. Buffered Delta Management

The Synchronization Coordinator uses bounded buffers to retain updates arriving during snapshot initialization.

Buffering must preserve ordering and provide explicit failure behavior.

### 14.1 Buffer Ownership

Each synchronization attempt owns its buffered updates.

Conceptually:

    DeltaBuffer {
        synchronization_generation
        capacity
        memory_budget
        updates
        first_received_at
        last_received_at
    }

Buffers must not be shared across unrelated synchronization generations.

### 14.2 Buffer Ordering

Buffered updates preserve native arrival order.

The coordinator must not sort updates solely by event timestamp.

Sequence validation determines whether their native ordering is acceptable.

### 14.3 Buffer Capacity

Buffer capacity is bounded by configuration.

Possible constraints include:

    MaximumMessages
    MaximumBytes
    MaximumDuration

The effective limit is the first applicable bound reached.

### 14.4 Buffer Overflow

If buffering exceeds its allowed capacity:

    Buffer Limit Exceeded
             |
             v
    Mark Attempt Failed
             |
             v
    Preserve Diagnostics
             |
             v
    Release Candidate State
             |
             v
    Notify Recovery Coordinator

The system must not silently discard buffered updates and continue claiming synchronization.

A new attempt may use a different bounded policy if explicitly configured.

### 14.5 Snapshot Latency

Snapshot acquisition may take long enough for the update buffer to approach capacity.

The coordinator should measure:

- Snapshot request latency.
- Buffered update count.
- Buffered byte count.
- Maximum buffer occupancy.
- Replay duration.
- Total synchronization duration.

The Recovery Coordinator may use these measurements to adjust retry policies or escalate persistent failures.

### 14.6 Buffer Release

After successful synchronization, the temporary buffer must be released or transferred into the normal processing queue.

It must not retain obsolete messages indefinitely.

Failed and cancelled attempts must release their buffers deterministically.

## 15. Synchronization Failure Handling

Synchronization may fail even when both REST and WebSocket connectivity are operational.

### 15.1 Failure Categories

| Failure | Meaning |
|---|---|
| SnapshotTimeout | Authoritative snapshot not received in time |
| SnapshotMalformed | Snapshot cannot be decoded or normalized |
| SnapshotIncompatible | Snapshot does not match the active instrument or protocol |
| BridgeNotFound | Buffered updates do not bridge snapshot sequence |
| BufferOverflow | Updates exceed synchronization buffer capacity |
| SequenceGap | Buffered replay violates continuity |
| MetadataMismatch | Snapshot and updates use incompatible normalization contexts |
| ObsoleteAttempt | Synchronization generation superseded |
| BookValidationFailure | Candidate book violates required integrity checks |

### 15.2 Failure Semantics

A failed synchronization attempt must not modify the current authoritative book.

If no valid book exists:

    BookState = Uninitialized or Invalid

If an existing valid book remains usable under the applicable protocol and generation:

    Preserve Existing Book

A reconnect or confirmed sequence gap generally invalidates the old book regardless of whether a replacement snapshot succeeds.

### 15.3 Failure Reporting

Every failure report must identify:

    StreamId
    SubscriptionGeneration
    SynchronizationGeneration
    FailureClassification
    LastKnownSequence
    SnapshotSequence
    BufferedUpdateRange
    FailureTimestamp

The Recovery Coordinator owns retry and escalation decisions.

### 15.4 Retry Boundaries

The Synchronization Coordinator does not perform unlimited autonomous retries.

It reports failures through the defined recovery interface.

The Recovery Coordinator determines:

- Whether to retry a REST snapshot.
- Whether to resubscribe.
- Whether to replace the connection.
- Whether to increase backoff.
- Whether to escalate persistent failures.

### 15.5 Recovery Guarantees

Successful synchronization establishes:

    Valid Current Book State

It does not establish:

    Complete Historical L2 Event Coverage

Missed incremental updates remain missing even after a fresh snapshot restores current-state validity.

This distinction must be preserved in stream integrity metadata.

## 16. Exchange-Specific Synchronization Strategies

MarketForge supports multiple exchange-native L2 synchronization protocols through a common synchronization framework.

The BookStore itself remains exchange-agnostic.

Exchange-specific behavior is implemented through compiled synchronization strategies selected by the depth-format configuration.

### 16.1 Design Principle

The synchronization engine must distinguish between:

- Snapshot acquisition.
- Snapshot installation.
- Initial sequence bridging.
- Incremental sequence continuity.
- Native sequence resets.
- Stale message detection.
- Authoritative snapshot replacement.
- Book-generation transitions.

These behaviors must not be combined into one universal sequence rule.

For example:

    Binance:
        U / u update ranges

    Bybit:
        u / seq with snapshot and delta messages

    OKX:
        seqId / prevSeqId

    Bitget:
        seq / pseq

    Gate.io:
        U / u update ranges

Similar-looking identifiers do not necessarily have identical semantics.

### 16.2 SynchronizationStrategy

The Configuration Compiler resolves the selected synchronization strategy during stream initialization.

Conceptually:

    SynchronizationStrategy {
        initialization_method
        snapshot_classification
        sequence_representation
        initial_bridge_rule
        continuity_rule
        stale_update_rule
        reset_rule
        checksum_policy
        depth_coverage_policy
    }

The exact Rust representation is an implementation detail.

Each strategy must implement the required protocol rules without modifying the generic BookStore.

### 16.3 Common Interface

Conceptual operations:

    classify_message(message)

    initialize(snapshot)

    validate_initial_bridge(snapshot, update)

    validate_next_update(state, update)

    classify_reset(state, update)

    commit_sequence(state, update)

The strategy validates transitions.

The BookStore owns authoritative state mutation.

Sequence state advances only when the associated book mutation commits successfully.

### 16.4 Strategy Registry

The initial configuration set requires these strategy families:

| Strategy | Primary use |
|---|---|
| BinanceSpotDepth | Binance Spot |

## 17. Binance Synchronization

Binance Spot and Futures both support REST snapshot initialization with buffered WebSocket updates.

However, their continuous sequence-validation requirements differ.

### 17.1 Binance Spot

The Spot depth stream provides:

    U = first update ID

    u = final update ID

The REST depth snapshot provides:

    lastUpdateId

Initialization requires:

    1. Open WebSocket.
    2. Buffer depth updates.
    3. Acquire REST snapshot.
    4. Validate snapshot sequence compatibility.
    5. Discard obsolete buffered updates.
    6. Establish initial sequence bridge.
    7. Install snapshot.
    8. Replay buffered updates.
    9. Transition to live processing.

#### Snapshot Compatibility

Let:

    S = snapshot.lastUpdateId

The coordinator must retain the first buffered update identifier.

If the snapshot precedes the earliest buffered update beyond the protocol's permitted boundary, a newer snapshot is required.

The precise compatibility check must follow the selected Binance Spot protocol specification.

#### Initial Bridge

The configured range-based bridge requires the buffered stream to cover the next applicable update position.

Conceptually:

    next_required = S + 1

    U <= next_required <= u

Updates already covered by the snapshot must be discarded.

#### Continuous Validation

For the current committed update ID:

    last_applied = L

An incoming update is invalid if:

    U > L + 1

because one or more required native update positions are missing.

An update already covered by accepted state may be ignored according to the configured stale-update rule.

A valid update advances the book sequence to:

    L = u

after the corresponding price-level mutations commit.

#### Recovery

A detected gap requires:

    Invalidate Book
          |
          v
    Begin New Synchronization Attempt
          |
          v
    Buffer WebSocket Updates
          |
          v
    Acquire REST Snapshot
          |
          v
    Reconstruct New Book Generation

The previous book must not remain authoritative after confirmed continuity loss.

### 17.2 Binance Futures

Binance USD-M and COIN-M Futures use related depth protocols.

Their updates provide:

    U
    u
    pu

Where:

    U  = first update ID

    u  = final update ID

    pu = previous final update ID

Initialization uses the exchange-defined REST snapshot and buffered-update procedure.

#### Continuous Validation

The primary explicit continuity rule is:

    current.pu == previous.u

A mismatch indicates that the incoming update does not continue the previously accepted native sequence under normal protocol conditions.

The validator must not substitute Spot continuity rules for Futures when `pu` is required.

#### Shared Futures Strategy

Linear and Inverse Futures may reuse:

    BinanceFuturesDepth

while maintaining separate:

- Endpoints.
- Instrument contexts.
- Native subscriptions.
- Book generations.
- Quantity normalization strategies.

Contract economics do not alter native order-book sequence validation.

## 23. Book Integrity Validation

The BookStore must validate both individual L2 messages and the resulting authoritative order-book state.

Native sequence continuity is necessary for synchronization but does not guarantee that reconstructed book contents are economically or structurally valid.

For example, a sequence-correct update may still contain malformed prices, invalid quantities, or contradictory levels.

Book integrity validation must therefore operate at multiple stages.

### 23.1 Integrity Layers

The initial implementation distinguishes:

| Layer | Responsibility |
|---|---|
| Message integrity | Validate native message structure |
| Level integrity | Validate individual price levels |
| Sequence integrity | Validate native update continuity |
| Mutation integrity | Validate atomic book transitions |
| Structural integrity | Validate resulting bid/ask state |
| Coverage integrity | Validate observable depth assumptions |
| Generation integrity | Reject obsolete processing generations |

These checks must remain logically independent.

An exchange protocol may provide sequence guarantees without providing checksum guarantees.

Likewise, a structurally valid book does not establish complete historical update coverage.

### 23.2 Validation Order

The recommended validation sequence is:

    Native L2 Message
           |
           v
    Message Classification
           |
           v
    Structural Validation
           |
           v
    Instrument Validation
           |
           v
    Numeric Normalization
           |
           v
    Generation Validation
           |
           v
    Sequence Validation
           |
           v
    Prepare Book Mutation
           |
           v
    Validate Candidate Book
           |
           v
    Commit Mutation and Sequence
           |
           v
    Publish Canonical Event

A failed validation must not partially modify authoritative book state.

### 23.3 Book Integrity Outcomes

Supported outcomes:

    Valid
    Warning
    Stale
    Invalid
    RequiresResynchronization

| Outcome | Meaning |
|---|---|
| Valid | All required checks succeed |
| Warning | A nonfatal diagnostic condition exists |
| Stale | Update is already represented by current state |
| Invalid | Message or candidate book violates required invariants |
| RequiresResynchronization | Continuity or authoritative state cannot be trusted |

Warnings must not be silently promoted into confirmed data loss.

An invalid update must not be published as a valid canonical L2 event.

## 24. Structural Book Integrity

Structural integrity validates the relationship between price levels, quantities, and book sides.

### 24.1 Price-Level Invariants

Every stored resting level must satisfy:

    price > 0

    quantity > 0

The BookStore must never retain a zero-quantity level.

Zero quantities in incremental messages represent deletion operations.

Price and quantity values must be representable by the configured exact-decimal types.

### 24.2 Price Uniqueness

Within one side:

    One price = One resting level

The BookStore must not contain duplicate price keys.

Equivalent decimal representations must resolve to the same price.

For example:

    65000.0

and:

    65000.00

must identify the same level.

This requirement applies regardless of the exchange's native decimal formatting.

### 24.3 Bid and Ask Ordering

Bid levels must be ordered from highest to lowest price.

Ask levels must be ordered from lowest to highest price.

Conceptually:

    Bids:
        65000
        64999
        64998

    Asks:
        65001
        65002
        65003

The underlying storage structure must preserve these ordering guarantees.

### 24.4 Empty Books

An empty book side is not automatically malformed.

Whether an empty bid or ask side is acceptable depends on:

- Instrument trading status.
- Exchange protocol behavior.
- Snapshot coverage.
- Market conditions.
- Configured integrity policy.

Possible classifications:

    ValidEmptySide
    SuspiciousEmptySide
    InvalidEmptySide

The initial implementation should permit explicit empty-book states while exposing their condition to health monitoring.

It must not invent missing levels.

### 24.5 Invalid Numeric Values

The BookStore must reject:

- Zero or negative resting prices.
- Negative resting quantities.
- Unsupported decimal representations.
- Arithmetic overflow.
- Unrepresentable normalized quantities.

The processor must not silently round invalid values into acceptable ranges.

## 25. Crossed and Locked Books

A crossed book occurs when the best bid exceeds the best ask.

A locked book occurs when the best bid equals the best ask.

These conditions require careful classification.

### 25.1 Book Spread

When both sides contain at least one level:

    best_bid = highest bid price

    best_ask = lowest ask price

    spread = best_ask - best_bid

Possible conditions:

| Condition | Expression |
|---|---|
| Normal | best_bid < best_ask |
| Locked | best_bid == best_ask |
| Crossed | best_bid > best_ask |

### 25.2 Crossed Books

A crossed book may indicate:

- Invalid sequence reconstruction.
- Inconsistent snapshot and delta application.
- Malformed exchange data.
- Incorrect price normalization.
- Exchange-side transitional behavior.
- Temporarily inconsistent market-data publication.

The BookStore must detect and report crossed states.

However, **a crossed book does not automatically prove a transport sequence gap**.

The integrity policy determines whether the condition requires:

    Warning
    InvalidBook
    Resynchronization

The initial recommended policy for synchronized single-venue L2 books is conservative:

    PersistentCrossedBook -> InvalidateAndResynchronize

An immediately crossed state may also trigger invalidation when the selected protocol requires a strictly uncrossed book.

### 25.3 Recording Initialization

When recording begins after a BookStore is already
synchronized, the Live depth processor must provide
a complete authoritative initialization of the
current book state.

The Recording Manager persists this initialization
together with its book generation, event boundary,
sequence metadata, and canonical levels.

The Recording Manager must not reconstruct the book
independently.

Ordinary subsequent updates may contain only
changed levels.

A recorded L2 segment is independently
reconstructable only when its initialization and
required subsequent updates are available.

### 25.4 Validation Timing

Crossed and locked conditions are evaluated after applying the complete candidate update.

The processor must not validate intermediate states while only part of an atomic message has been applied.

Example:

    Update removes old best bid.
    Update inserts new ask.

An intermediate mutation state may temporarily appear crossed even when the final atomic book state is valid.

Only the final candidate state determines the structural integrity outcome.

### 25.5 Empty-Side Handling

Spread validation requires both sides to contain at least one level.

If either side is empty:

    spread = unavailable

The BookStore must not substitute zero values for missing best prices.

## 26. Depth Coverage and Completeness

A synchronized order book is not necessarily a complete representation of every resting order at the exchange.

MarketForge must distinguish synchronization correctness from depth completeness.

### 26.1 Coverage Dimensions

Book coverage includes:

- Native subscription depth.
- Snapshot depth.
- Number of known bid levels.
- Number of known ask levels.
- Price range represented.
- Whether deeper levels are observable.
- Whether levels may have been truncated.
- Whether the channel provides full-depth or partial-depth data.

These properties should be available through book metadata and health diagnostics.

### 26.2 Coverage Model

Conceptual representation:

    DepthCoverage {
        subscription_depth
        snapshot_depth
        known_bid_levels
        known_ask_levels
        deepest_known_bid
        deepest_known_ask
        coverage_kind
    }

Supported coverage kinds:

    FullObservableDepth
    BoundedDepth
    UnknownDepth

**FullObservableDepth**

The protocol provides all price levels within its documented observable scope.

This does not necessarily imply access to hidden liquidity or every order type.

**BoundedDepth**

The channel exposes a fixed or maximum number of levels.

**UnknownDepth**

The currently available information does not establish a reliable coverage bound.

### 26.3 Snapshot Coverage

A snapshot containing 100 levels does not necessarily prove that the exchange has only 100 levels.

For example:

    Snapshot depth = 100

means:

    Up to 100 levels per side are represented.

The BookStore must not infer that deeper prices contain zero liquidity.

### 26.4 Subscription Coverage

Different subscriptions may request different depths.

Examples:

    Top 20
    Top 50
    Top 100
    Top 400
    Top 1000

The compiled channel configuration determines the permitted values.

The BookStore records the actual selected depth.

### 26.5 Depth-Limited Streams

Depth-limited streams require explicit handling when levels enter or leave the observable range.

For example:

    Subscription depth = 20

A level previously ranked 21st may become visible after the best level disappears.

The exchange must provide sufficient information to reconstruct the new observable state.

If the protocol does not guarantee this through its update mechanism, additional snapshots may be required.

MarketForge must not assume that a locally retained top-20 book remains complete after arbitrary deletions unless the exchange's depth protocol supports that conclusion.

### 26.6 Unknown Deeper Liquidity

A depth-limited book must distinguish:

    Price level absent from observed depth

from:

    Price level known to contain zero liquidity

These conditions are not economically equivalent.

Downstream liquidity features must receive the book's coverage metadata.

### 26.7 Coverage and Feature Engineering

Depth coverage directly affects calculations such as:

- Order-book imbalance.
- Liquidity concentration.
- Cancellation intensity.
- Estimated support and resistance levels.
- Depth-weighted prices.
- Liquidity replenishment.
- Order-book pressure.

A feature calculated from 20 levels is not necessarily comparable to the same feature calculated from 1,000 levels.

MarketForge must preserve enough coverage information for downstream processors to make this distinction.

## 27. Depth Truncation and Retention

The BookStore may need to limit retained price levels to control memory consumption.

Truncation must not silently invalidate synchronization guarantees.

### 27.1 Retention Strategies

Supported conceptual strategies:

    RetainAllObservedLevels
    RetainTopN
    RetainConfiguredPriceRange

The initial recommended strategy is:

    RetainAllObservedLevels

within the exchange-provided depth scope, subject to explicit resource limits.

### 27.2 Top-N Retention

Top-N retention keeps only the best N prices on each side.

Example:

    RetainTopN = 100

The BookStore discards levels outside the best 100.

This is safe only when the selected exchange protocol provides enough information to maintain correct top-100 coverage after future updates.

Otherwise, a new snapshot may be required when retained levels are exhausted.

### 27.3 Truncation Risks

Consider:

    Book initially contains 1,000 levels.

    Local storage retains only 100.

    The best 50 levels are deleted.

Levels previously ranked 101–150 may now belong in the best 100.

If their quantities are no longer available, the BookStore cannot reconstruct the correct top 100 from retained state alone.

Therefore:

    Local Truncation
         !=
    Exchange-Defined Depth Coverage

These must be tracked separately.

### 27.4 Truncation Policies

A truncation policy must define:

- Maximum retained levels.
- Required coverage guarantees.
- Behavior when deeper levels become necessary.
- Whether recovery is required.
- Whether output coverage becomes degraded.

The BookStore must not publish a truncated book as complete without an explicit compatible protocol guarantee.

### 27.5 Memory Exhaustion

If the book exceeds its configured memory budget:

- Report resource pressure.
- Apply only supported bounded retention policies.
- Preserve sequence integrity.
- Avoid silently discarding levels.
- Invalidate or suspend the book when correctness cannot be maintained.
- Escalate to runtime resource management.

Memory pressure must not lead to fabricated book state.

## 28. Checksum Validation

Some order-book protocols provide native checksums that can verify reconstructed book contents.

Checksum validation is channel-specific and optional.

### 28.1 Checksum Strategy

Supported conceptual strategies:

    None
    ExchangeDefinedChecksum

The Configuration Compiler selects the appropriate strategy.

A checksum validator must not be enabled merely because a native field is named `checksum`.

The current protocol must explicitly define how the checksum is calculated.

### 28.2 Checksum Inputs

An exchange-defined checksum may depend on:

- The best N bid levels.
- The best N ask levels.
- A specific ordering of levels.
- Exact native price strings.
- Exact native quantity strings.
- A specified string serialization format.
- A particular checksum algorithm.

The implementation must reproduce the exchange's documented algorithm exactly.

### 28.3 Native Representation Preservation

Checksum algorithms may depend on textual representations rather than only numerical values.

For example:

    "65000.0"

and:

    "65000.00"

are numerically equivalent but have different byte representations.

If the exchange checksum uses native textual formatting, canonical decimal normalization alone may not preserve sufficient information.

The checksum subsystem must retain or reconstruct the required native representation according to the protocol.

### 28.4 Checksum Validation Boundary

Checksum verification must occur against a consistent candidate book state.

Conceptually:

    Validate Sequence
           |
           v
    Apply Candidate Mutation
           |
           v
    Construct Checksum Input
           |
           v
    Calculate Checksum
           |
           v
    Compare Native Checksum
           |
       +---+---+
       |       |
       v       v
     Match   Mismatch
       |       |
       v       v
    Commit   Invalidate

A checksum mismatch must not leave partially committed book state.

### 28.5 Checksum Mismatch

A mismatch indicates that the reconstructed state does not satisfy the exchange's checksum contract.

Possible causes:

- Missing updates.
- Incorrect message ordering.
- Incorrect level extraction.
- Incorrect quantity interpretation.
- Incorrect checksum serialization.
- Exchange-side protocol anomalies.

The initial policy is:

    ChecksumMismatch -> InvalidateAndResynchronize

The error must include sufficient diagnostics to identify the affected stream and sequence boundary.

### 28.6 Deprecated Checksums

A deprecated checksum field must not be treated as an active integrity mechanism.

For the current initial configuration scope:

| Exchange | Checksum policy |
|---|---|
| Binance | No native checksum validation |
| Bybit | No native checksum validation for selected normal L2 feeds |
| OKX | Disabled for the selected JSON channels following deprecation |
| Bitget | Disabled following V3 checksum removal |
| Gate.io | No native checksum validation for selected JSON channels |

The compiler must verify the configured checksum policy against the selected protocol revision.

Future channels may define new checksum mechanisms.

### 28.7 Integrity Without Checksums

When no active checksum is available, MarketForge relies on:

- Native sequence validation.
- Snapshot correctness.
- Structural book validation.
- Generation fencing.
- Message decoding validation.
- Optional comparison against independent snapshots.

These mechanisms reduce the risk of corrupted book state but do not provide the same guarantee as a valid exchange-defined checksum.

The runtime must not claim checksum-verified integrity when checksum validation is unavailable.

## 29. Book Publication Guarantees

The BookStore publishes authoritative state transitions only after successful validation and commit.

Publication must preserve the relationship between native messages, committed book state, and canonical output events.

### 29.1 Publication Boundary

The required sequence is:

    Validate Native Message
             |
             v
    Validate Sequence
             |
             v
    Prepare Book Mutation
             |
             v
    Validate Candidate State
             |
             v
    Commit Book and Sequence
             |
             v
    Construct Canonical L2 Event
             |
             v
    Submit to Publisher

A rejected update must not produce a normal canonical L2 event.

### 29.2 Canonical Event Correspondence

Every published canonical L2 update must identify the committed transition it represents.

Conceptually:

    StreamId
    BookGeneration
    BookVersion
    NativeSequence
    EventTimestamp
    ConfigurationRevision
    MetadataRevision

The precise fields remain defined by the canonical event contracts.

### 29.3 Publication Ordering

For one logical L2 source stream:

    Event N
        |
        v
    Event N+1
        |
        v
    Event N+2

Canonical publication order must preserve committed BookStore transition order.

The Publisher must not reorder accepted L2 updates within one source stream.

Cross-stream ordering is handled separately by the merge and reorder subsystem.

### 29.4 Backpressure

Publisher backpressure must not silently discard committed L2 updates.

The BookStore processing pipeline must use bounded queues and explicit overload handling.

When publication cannot keep up:

- Apply the configured backpressure mechanism.
- Preserve committed event ordering.
- Report queue pressure.
- Avoid unbounded memory growth.
- Escalate when lossless publication cannot be maintained.

If a committed event cannot be delivered under the established publication contract, the runtime must report the delivery failure explicitly.

### 29.5 Snapshot Publication

A newly synchronized book generation must publish an authoritative canonical snapshot before publishing its incremental updates.

Conceptually:

    Book Generation N
            |
            v
    Canonical Snapshot
            |
            v
    Incremental Update 1
            |
            v
    Incremental Update 2

Downstream consumers must not receive deltas for a generation before receiving the corresponding initialization event when their subscription contract requires a synchronized starting state.

### 29.6 Subscriber Consistency

A consumer requesting current book state must receive a consistent snapshot associated with one committed book version.

The snapshot must identify:

    BookGeneration
    BookVersion
    DepthCoverage

Subsequent deltas must continue from the appropriate publication boundary.

If that boundary cannot be maintained, the consumer must receive a new snapshot rather than silently missing updates.

### 29.7 Recording Consistency

Optional PostgreSQL recording consumes accepted canonical events.

The Recording Manager must preserve the event identity and ordering information needed for downstream reconstruction.

Recording must not alter the BookStore's authoritative sequence state.

A database failure must not retroactively change whether an L2 update was valid.

Recording failures are handled according to the independent recording policy.

### 29.8 Publication Failure Classification

Possible failures include:

    PublisherUnavailable
    SubscriberBackpressure
    PublicationQueueOverflow
    SerializationFailure
    DeliveryDeadlineExceeded

Publication failure is distinct from native sequence failure.

The runtime must not incorrectly report a sequence gap merely because an accepted event could not be delivered.

However, failure to preserve the configured lossless-delivery contract must result in explicit degradation or escalation.

## 30. Consistent Book Views

The BookStore must provide consistent read-only access to reconstructed L2 state without exposing partially applied mutations.

Consumers may include:

- Stream processors.
- Derived-stream and merge processors.
- Currency-conversion pipelines.
- The Publisher.
- The Recording Manager.
- Runtime diagnostics.
- The TUI and API.

The BookStore remains authoritative for its current synchronized state.

Consumers must not directly mutate book storage.

### 30.1 BookView

A `BookView` represents one committed version of an order book.

Conceptually:

    BookView {
        stream_id
        instrument_id

        connection_generation
        subscription_generation
        book_generation
        book_version

        metadata_revision
        configuration_revision

        validity
        sequence_state
        depth_coverage

        event_timestamp
        committed_at

        bids
        asks
    }

This representation is illustrative.

The actual implementation must reuse domain types defined in **02 — Domain Models and Contracts**.

A view must not combine bids from one book version with asks from another.

### 30.2 Read Operations

The initial BookStore interface should support:

    GetBestBid
    GetBestAsk
    GetBestBidAsk
    GetTopN
    GetFullObservableBook
    GetBookStatus
    GetBookSequence
    GetBookCoverage

All operations must return data from a consistent committed state.

The API must distinguish unavailable values from zero values.

For example:

    No Best Bid

must not be represented as:

    Best Bid = 0

### 30.3 Snapshot Consistency

A book snapshot returned to a consumer must represent one atomic state.

Conceptually:

    Read Request
          |
          v
    Locate Book
          |
          v
    Select Committed Version
          |
          v
    Construct Consistent View
          |
          v
    Return Snapshot

The view must include the book generation and version used.

A reader must never observe intermediate mutations.

### 30.4 Concurrent Reads

Multiple consumers may request book state concurrently.

The implementation may use:

- Read locks.
- Immutable snapshots.
- Actor-based queries.
- Versioned state publication.
- Copy-on-write structures.

The initial implementation should prioritize correctness and bounded resource usage.

Lock-free structures are not required unless benchmarks justify them.

### 30.5 Read Performance

Read operations should avoid copying the entire order book unnecessarily.

For example:

    GetTopN(10)

should not require cloning 1,000 levels per side.

The implementation should support efficient ordered traversal and bounded snapshot construction.

### 30.6 Slow Readers

A slow consumer must not indefinitely block the authoritative book mutation owner.

Read interfaces must define:

- Maximum request duration.
- Snapshot size limits.
- Cancellation behavior.
- Backpressure handling.
- Resource ownership.

Long-running read operations should use owned or immutable snapshots where appropriate.

### 30.7 Invalid Book Views

A book may exist in memory while its synchronization state is invalid.

The read interface must expose this condition explicitly.

Conceptually:

    BookView {
        validity = Invalid
    }

A consumer must not interpret an invalid book as synchronized current market state.

Depending on the API, invalid books may be:

- Excluded from synchronized-state queries.
- Returned only through diagnostic interfaces.
- Returned with an explicit invalidity marker.

The initial recommended policy is to separate synchronized market-data views from diagnostic book-state inspection.

## 31. BookStore Resource Management

The BookStore must maintain bounded memory consumption across all active L2 streams.

Memory allocation depends on:

- Number of books.
- Number of retained price levels.
- Decimal representation size.
- Optional level metadata.
- Synchronization buffers.
- Concurrent snapshot construction.
- Read-only snapshots.
- Publication queues.

Resource management must not compromise book integrity.

### 31.1 Resource Ownership

| Resource | Owner |
|---|---|
| Book identity | BookStore Registry |
| Bid and ask storage | Per-book mutation owner |
| Sequence state | Per-book mutation owner |
| Book generation | Per-book mutation owner |
| Synchronization buffer | Synchronization Coordinator |
| Candidate snapshot | Synchronization Coordinator |
| Immutable instrument context | Instrument Context Registry |
| Published canonical event | Publisher |
| Read-only book snapshot | Requesting consumer or snapshot service |
| Book metrics | Metrics Registry |

Each resource must have a defined lifetime.

### 31.2 Resource Limits

The initial implementation should support:

    MaximumBooks

    MaximumLevelsPerBook

    MaximumBookMemory

    MaximumSynchronizationBufferBytes

    MaximumConcurrentSnapshots

    MaximumReadSnapshotSize

These limits belong to runtime configuration.

They must be validated before resource admission.

### 31.3 Memory Accounting

Memory accounting should distinguish:

    Authoritative Book Storage

    Candidate Book Storage

    Synchronization Buffers

    Read Snapshots

    Pending Publication Data

These components may temporarily coexist.

For example, snapshot replacement may require retaining the old book while constructing the new one.

The memory budget must account for this temporary duplication.

### 31.4 Book Admission

Before creating a new L2 BookStore instance:

    L2 Stream Activation
            |
            v
    Validate Book Requirements
            |
            v
    Check Resource Capacity
            |
            v
    Reserve Book Resources
            |
            v
    Create Book Instance

If admission fails, the Stream Registry receives an explicit resource-capacity error.

The system must not create unbounded book instances.

### 31.5 Memory Pressure

When memory consumption approaches configured limits:

- Report the condition.
- Prevent unbounded allocation.
- Apply only supported retention policies.
- Avoid silent level deletion.
- Reduce optional diagnostic retention where safe.
- Escalate when authoritative book correctness cannot be maintained.

Memory pressure must not cause a synchronized book to silently become incomplete.

### 31.6 Resource Exhaustion

If the BookStore cannot safely allocate resources required for a valid update:

    Resource Exhaustion
           |
           v
    Reject Candidate Mutation
           |
           v
    Preserve or Invalidate Current State
           |
           v
    Report Failure
           |
           v
    Recovery / Resource Escalation

The current state may remain valid if the failed update has not affected continuity and a safe continuation procedure exists.

Otherwise, the book must be invalidated.

The system must not continue processing later deltas after an unaccounted missing update.

### 31.7 Book Removal

Removing a BookStore instance requires:

- Fencing the active book generation.
- Stopping new mutations.
- Cancelling synchronization attempts.
- Releasing candidate snapshots.
- Releasing buffered updates.
- Releasing bid and ask storage.
- Releasing retained metadata references.
- Reporting final diagnostics.

Removal must be idempotent.

A late synchronization completion must not recreate a removed book.

## 32. Instrument Metadata Revisions

The BookStore uses immutable instrument metadata supplied through the Rust Instrument Context Registry.

The authoritative metadata remains owned by Python orchestration.

This contract is defined in **06 — Normalization and Integrity**, Section 13.

### 32.1 Revision Association

Every book generation is associated with:

    InstrumentId

    MetadataRevision

    ConfigurationRevision

These values identify the normalization rules used to construct the book.

They must remain stable throughout one authoritative generation unless an explicitly supported migration procedure is performed.

### 32.2 Metadata Changes

Relevant changes include:

- Quantity denomination.
- Contract value.
- Contract-value asset.
- Price representation.
- Tick size.
- Quantity step.
- Instrument identity.
- Native market classification.

Not every metadata change requires book reconstruction.

However, changes affecting the economic meaning of stored quantities require controlled handling.

### 32.3 Normalization-Critical Changes

Suppose the active book contains:

    100 contracts

with:

    contract_value = 1 USD

A new metadata revision changes:

    contract_value = 10 USD

The same native contract quantity now represents a different economic amount.

The BookStore must not retain previously normalized quantities while applying future updates using the new multiplier.

That would produce inconsistent economic state.

### 32.4 Supported Replacement Strategies

Two strategies are permitted.

**RebuildFromAuthoritativeSnapshot**

Invalidate the affected book and establish a new authoritative snapshot using the replacement normalization context.

**RecalculateFromPreservedNativeLevels**

Recalculate existing quantities using preserved exact native values.

This is permitted only when:

- Native quantities are retained.
- The new conversion is well-defined.
- The metadata revision is valid for the affected state.
- Every stored level can be recalculated consistently.
- The migration is atomic.
- Sequence and generation guarantees remain valid.

### 32.5 Initial Policy

The initial recommended policy is:

    RebuildFromAuthoritativeSnapshot

for normalization-critical changes.

This avoids introducing complex migration logic before the BookStore's correctness and performance characteristics are established.

### 32.6 Metadata Transition

    New Metadata Revision
             |
             v
    Validate New Context
             |
             v
    Identify Affected Book
             |
             v
    Stop Old-Context Processing
             |
             v
    Fence Old Book Generation
             |
             v
    Initialize Replacement Context
             |
             v
    Synchronize New Book
             |
             v
    Commit New Book Generation

No atomic L2 update may be partially normalized under two metadata revisions.

### 32.7 Historical Applicability

A newly fetched metadata revision is not necessarily valid for earlier market-data events.

The BookStore and Recovery Coordinator must distinguish:

    Metadata Fetched Time

from:

    Metadata Effective Time

When an authoritative effective-time boundary is unavailable, the runtime must preserve the uncertainty.

It must not claim exact historical normalization using an unverified revision.

## 33. Recovery Coordination

The BookStore detects integrity failures and reports them to the Recovery Coordinator.

It does not independently manage reconnection, REST retries, or exchange outage policies.

### 33.1 Recovery Triggers

Recovery may be required following:

- Native sequence gaps.
- Invalid snapshot bridges.
- Checksum mismatches where checksums are supported.
- Malformed state-changing updates.
- Connection loss.
- Subscription replacement.
- Unsupported sequence transitions.
- Normalization-critical metadata changes.
- Book-state corruption.
- Resource exhaustion affecting continuity.

### 33.2 Recovery Request

Conceptual structure:

    BookRecoveryRequest {
        stream_id
        instrument_id

        connection_generation
        subscription_generation
        book_generation

        configuration_revision
        metadata_revision

        failure_reason
        last_valid_sequence
        failure_timestamp
    }

The request must contain enough information for the Recovery Coordinator to select an appropriate recovery procedure.

### 33.3 Recovery Ownership

The responsibilities remain:

    BookStore
        |
        v
    Detect Integrity Failure
        |
        v
    Recovery Coordinator
        |
        v
    Select Recovery Strategy
        |
        v
    Synchronization Coordinator
        |
        v
    Establish New Book Generation
        |
        v
    BookStore

The BookStore must not create independent retry loops.

### 33.4 Recovery Policies

Possible recovery actions include:

    RetrySnapshot

    RestartSynchronization

    Resubscribe

    ReplaceConnection

    EscalateFailure

The Recovery Coordinator selects the action based on:

- Exchange protocol.
- Failure classification.
- Current connection health.
- Subscription state.
- Retry history.
- Rate-limit availability.
- Resource capacity.

### 33.5 Current-State Recovery

A new authoritative snapshot may restore the current book.

However:

    Current Book Restored

does not imply:

    Historical L2 Coverage Restored

The system must preserve any missing incremental-update interval.

### 33.6 Repeated Synchronization Failure

Repeated failures must not produce uncontrolled retry loops.

The Recovery Coordinator may:

- Increase backoff.
- Request subscription replacement.
- Replace the physical connection.
- Escalate stream degradation.
- Require configuration correction.
- Suspend recovery when a permanent failure is identified.

The Stream Registry retains the user's desired activation state unless explicitly changed.

Shutdown must have a finite deadline.

The system must not leave detached synchronization tasks or retained candidate snapshots after termination.

### 34.5 Restart Safety

After process restart, the BookStore must not assume that previous in-memory sequence state remains authoritative.

The runtime reconstructs logical book declarations and begins the configured synchronization procedure.

A previously persisted operational snapshot may support diagnostics but does not establish a valid current exchange order book.

## 44. Final Architectural Contract

The BookStore maintains authoritative reconstructed L2 state for each active order-book source stream.

It guarantees:

- Exact price-level representation.
- Correct interpretation of absolute quantities.
- Atomic snapshot replacement.
- Atomic incremental updates.
- Native sequence continuity according to the selected protocol.
- Generation-safe processing.
- Explicit depth coverage.
- Consistent read-only book views.
- Controlled invalidation after integrity failure.
- Coordination with recovery and publication components.

It does not guarantee:

- Visibility of hidden or unreported liquidity.
- Unlimited depth from a depth-limited feed.
- Complete historical L2 coverage after disconnection.
- Recovery of missed updates solely from a new snapshot.
- Validity of unsupported exchange protocol variants.
- Correct economic normalization without authoritative instrument metadata.

The ownership chain is:

    Stream Registry
          |
          v
    Subscription Manager
          |
          v
    Connection Manager
          |
          v
    Exchange Protocol Adapter
          |
          v
    L2 Normalization
          |
          v
    Sequence Validation
          |
          v
    Synchronization Coordinator
          |
          v
        BookStore
          |
          v
    Committed Canonical L2 Events
          |
          v
    Publisher / Optional Recording

The BookStore remains exchange-agnostic.

Exchange-specific synchronization semantics are compiled from validated protocol configurations.

The Recovery Coordinator owns recovery policy and escalation.

The Publisher owns canonical event distribution.

The Recording Manager owns optional persistence.

## Shared Historical and Live BookStore Implementation

MarketForge Live must reuse the existing Rust `book/` module
as the authoritative order-book state implementation.

The shared components include:

- `BookStore` — bid/ask price-level state.
- `BookLevel` — normalized level quantities.
- `SequenceTracker` — generic sequence-state tracking.
- `SequencePolicy` — sequence continuity policies.
- `emit_l2_changes` — canonical L2 event emission.
- `BookSegment` and `SegmentTracker` — reconstruction segments.

The Live implementation must not create a separate,
incompatible order-book state machine.

### Exchange-Specific Synchronization

The existing `SequenceTracker` provides the foundation
for sequence validation.

Exchange-specific adapters must implement additional
synchronization rules where the generic policies are
insufficient.

These may include:

- Snapshot-to-delta bridging.
- Sequence ranges.
- Previous-update references.
- Sequence resets.
- Recovery after discontinuities.

Generic book-state logic remains shared between
Historical and Live.

### Authoritative Initialization

The existing `BookStore::apply_snapshot()` emits only
levels that differ from the previous book state.

This is suitable for ordinary change propagation.

However, beginning a new independently reconstructable
book generation requires a complete initialization
representation.

The Live depth processor must preserve:

- The complete authoritative initialization state.
- The initialization event boundary.
- The source book generation.
- Applicable sequence metadata.
- The ordered canonical level changes.

A new generation must not depend on the state of an
earlier invalidated generation.

### Canonical Event Grouping

One native depth message may produce multiple canonical
`L2LevelUpdate` values.

These values must retain their logical source-event
boundary and deterministic ordering.

The existing historical `DepthProcessingOutcome`
provides a reference for this contract.

The implementation should reuse or extend that
representation rather than inventing an incompatible
Live-only depth-event model.

### Shared Implementation Invariant

Historical and Live depth processing must use
equivalent book-state transition semantics.

Differences in transport, buffering, and recovery
must not redefine canonical L2 behavior.
