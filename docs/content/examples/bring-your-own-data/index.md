# Bring your own historical data

Use managed registration for purchased files, recordings, or exports you already have. Exchange acquisition locates and downloads archives from configured venues. Registration copies the files you select into managed raw storage and records their provenance and interpretation in the same PostgreSQL registry.

1. Inspect representative source records, including unusual trade sides, missing values, and depth messages at the beginning and end. Confirm timestamp encoding, quantity denomination, instrument identifiers, ordering guarantees, and whether a depth message represents a state or a change. Use provider documentation to establish sequence semantics.
2. Declare the venue, instrument, and time-bounded specifications through `mf catalog`. For equities use the `equity.equity` instrument/category pair, the ticker as the base asset, the currency as quote asset, and base quantity for shares. Supply applicable price and quantity increments with provenance. See the [catalogue setup](../../workflows/catalogue/index.md).
3. Author a self-contained schema-2 TOML profile. Match its filename and ID to `venue.instrument_type.market_category.trades` or `venue.instrument_type.market_category.depth`. Declare the physical format in `[source]`, the raw fields in `[fields.*]`, and explicit transformations in `[normalization]`. Use `mf acquisition profiles validate --file PATH` for Rust semantic validation, then `mf acquisition profiles add ID --from PATH --testing` to install it. One layout can be installed per profile ID, subject to the existing Gate.io feed variants. See the [profile authoring reference](../../workflows/acquisition/external-data.md#creating-historical-normalization-profiles).
4. Write a registration TOML with provider, product, source key, provenance, root, coverage, and file selections. Each input pairs a concrete catalogue instrument with an installed profile. The root is relative to the project root unless absolute. Use `mf acquisition register plan PATH --testing` to check resolved bindings, then `mf acquisition register run PATH --testing` to checksum and copy files. Repeat registration can reuse verified files.
5. Write a normalization recipe selecting the registered source key, venue, instrument, data type, and interval. Run `mf --json normalize prepare PATH --testing`. Forge uses PostgreSQL to select managed copies and resolve instrument and specification authority, then validates the prepared batch with Rust. Use `mf normalize run BATCH.json --testing` to execute it. The result identifies the registered dataset directories.
6. Inspect each dataset's `manifest.json` and the Parquet paths listed there. Compare physical records read and processed, logical events, canonical rows, exclusions, and integrity counters. For depth, use `events.parquet` to associate each observation with its canonical row range, including zero-row observations. Check the boundary coverage before interpreting reconstructed state.

Use an export to supported CSV or JSONL when your original format has no reader. Preserve the originals and record the conversion and format in provenance. Native DBN is outside the current normalization workflow. The managed registration and publication commands currently require the configured testing PostgreSQL database.

The [Databento AAPL walkthrough](databento/index.md) includes complete declarations, profiles, and a recipe for both trades and bounded order-book observations.
