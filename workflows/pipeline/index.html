Historical pipeline

A single Forge recipe acquires and registers raw archives, normalizes them, and publishes and registers a merged dataset. Add a [convert] table to value the merged output in a target quote and index the verified result.

Recipe

Save named recipes under data/.config/workflows/data_engineering/pipeline/. The version 1 recipe uses the acquisition request schema and one half-open UTC interval [start, end). Use the existing scopes and feed options for each exchange. Forge resolves archive, instrument, job, dataset, and registry identities.

The example is checked in at data/.config/workflows/data_engineering/pipeline/bybit_spot.toml. To inspect or edit it, run nvim data/.config/workflows/data_engineering/pipeline/bybit_spot.toml.

Use the maintained sample recipe as the complete example. See the recipe reference for field definitions.

[normalize] and [merge] are optional. Normalization defaults to turnover ranking. Merge accepts causal and chronological. When omitted, the existing merge planner picks the ordering required by the selected inputs. It derives trade, depth, or mixed processing from registered files.

An optional [convert] table takes a target quote and conversion policy. The pipeline uses the exact merge registered by the preceding stage. Install the managed converter with mf engine build convert and configure its base runtime before running this stage. See pipeline recipe options and reference-trade requirements.

Inspect and run

Use a configured marketforge_test database with the testing identity and current migrations. Install the managed normalize and merge engines and use the operation runtime files, pipeline runtime and normalization profiles. The catalogue must supply instrument identity and applicable historical specifications for the requested archives. Forge reads its ordinary application and HTTP configuration.

set -o pipefail
mf engine build normalize
mf engine build merge
mf pipeline validate bybit_spot
mf pipeline plan bybit_spot --testing

Validation checks recipe structure and options. Planning reads existing registered evidence and identifies deferred work. It issues no HTTP requests, allocates no output identities, and writes no recipe, job, or registry rows. Local archive readiness is confirmed on run.

mf pipeline run bybit_spot --testing

Forge runs processing stages sequentially to preserve their configured engine budgets. Acquisition uses the usual HTTP concurrency and source rate limits. Preparation and validation are distinct phases. A processing stage completes only once Forge verifies and records its required outputs. Normalization and Merge register their publications. Conversion indexes a verified output reference. This can come from a new execution or verified reuse. Archive discovery, nominal archive intervals, verified local files, and observed event extents describe different evidence.

Acquisition passes its exact verified local archive IDs, paths, checksums, and source revision evidence to normalization. Normalization keeps its existing coverage and readiness checks, and uses only those inputs. After normalization registers every required publication, merge takes the exact registered primary-file dataset IDs in that receipt. Engine job and publication IDs stay distinct from registry publication and primary-file IDs.

Stage windows

In an interactive Linux desktop session with supported Ghostty, the command opens a separate window for each stage that executes. The original terminal keeps the pipeline dashboard and final summary. Acquisition shows discovery and download progress. Processing windows show the managed Engine monitor when available, or the Engine's live terminal output. The window closes after Forge has retained the stage outcome, including failures.

mf pipeline run bybit_spot --testing --stage-terminal window
mf pipeline run bybit_spot --testing --stage-terminal inline

The default auto uses inline execution for headless sessions, redirected output, and JSON. If Ghostty cannot start a worker, an interactive run reports the reason and continues inline. window requires a supported desktop terminal and fails if a required window cannot start. Use inline on macOS or when debugging. In tmux, Ghostty still opens a desktop window. A restored tmux session needs access to the current Wayland or X11 display.

Preparation, recovery of a committed output, and completed-work reuse can finish without opening a processing window. Only stages declared by the recipe are scheduled. --tui explicitly enables the pipeline dashboard in the original terminal. The window mode enables it automatically when that terminal supports it.

Inspect a preparation and resume

mf pipeline run bybit_spot --testing --stop-after normalize.prepare --tui

This stops with validated normalization jobs before execution. The command prints the retained run ID and the resume command.

set -o pipefail
mf pipeline status RUN_ID
mf --json pipeline status RUN_ID

mf pipeline resume RUN_ID --testing --tui

Resume uses the original workspace, storage root and testing registry. It checks retained TOML, settings, profile and executable hashes, prepared jobs, and acquisition evidence. Retained jobs preserve the ranking and stream ordering selected during preparation. Completed acquisition scans and verified archives from an interrupted acquisition are retained. A request whose discovery never finished may still need discovery. Changed or missing pinned inputs require investigation. A new selection belongs to a fresh run.

If processing committed a valid publication but registration failed, resume verifies that publication and retries registration through the existing registration service. It keeps failed attempts and any published outputs. A processing retry allocates fresh output identities. A fresh pipeline run also allocates fresh outputs and may reuse verified raw archives.

Progress and reports

Press Ctrl+C in the original terminal to request cancellation. Closing an active stage window also interrupts its worker. Forge uses the retained result to decide whether the work completed. If the outcome is uncertain, the pipeline stops and retains its evidence for reconciliation. Resume the same run to verify a prior commit before starting more processing.

mf runs show RUN_ID --testing
mf runs report RUN_ID --testing

The parent report lists stage outcomes and relevant publication references. Acquisition counts during discovery can be provisional. Detailed Engine throughput, job progress, and diagnostics belong to the stage window or retained attempt. Use the run report to find the failed stage and its evidence after the window closes.

Run artifacts live under <storage>/runs/<run-id>/. Start with report.json and events.jsonl. The run also retains submitted.toml, resolved-plan.json, frozen engines, and historical settings and profiles. steps/ links execution attempts and stores the exact acquisition selection. The report points to the existing child preparation, execution, verification, and registration receipts. Each engine attempt retains separate diagnostic logs and its structured result when available.

Read the reported child error before retrying. Build missing managed engines, verify access to the testing registry, and supply missing catalogue or profile evidence as indicated. Preserve existing outputs and staging when inspecting interrupted attempts. Use a fresh run when the recipe, data selection, or interpretation needs to change.

To inspect an indexed conversion result, follow Conversion output inspection.
