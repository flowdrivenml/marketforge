Trades and L2 depth profiles

Create a complete standalone schema-2 TOML file for each source interpretation. The canonical name is exchange.instrument_type.market_category.trades or exchange.instrument_type.market_category.depth. Use the exact ID as the filename. Format codes use the uppercase venue prefix with hyphens for underscores, followed by -T1 or -B1 for the first format.

These Rust-validated examples describe only the supplied synthetic trade CSV and depth JSONL. The example files have explicit side values and independent depth snapshots.

  • Complete trades profile
  • Complete L2 depth profile
examples=docs/content/examples/catalogue
trade=example_exchange.equity.equity.trades
depth=example_exchange.equity.equity.depth
mf acquisition profiles validate --file "$examples/$trade.toml"
mf acquisition profiles validate --file "$examples/$depth.toml"
mf acquisition profiles add "$trade" --from "$examples/$trade.toml" --testing
mf acquisition profiles add "$depth" --from "$examples/$depth.toml" --testing
mf acquisition profiles list --exchange example_exchange
mf acquisition profiles inspect "$depth"

Validation stages the submitted definition beside installed profiles and asks Rust to compile the catalogue. Installation checks the venue in PostgreSQL, retains the Rust fingerprint, and rejects a changed interpretation under the same ID. A canonical ID currently selects one physical format. Gate.io depth has existing explicit feed variants. A second arbitrary source layout under the same logical ID requires an engine contract extension.

Registered equity venues can run through the managed normalization workflow. The Databento reference profiles show nested JSONL timestamps, explicit unknown trade sides, and bounded depth observations.

Validate and install a candidate

Validate a Candidate Profile

Once you have written a profile, validate it using the production normalizer.

For example:

mf acquisition profiles validate \
    --file /absolute/path/to/binance.spot.spot.trades.toml

This selects a candidate file.

Validate an installed profile

You can also validate a profile by ID:

mf acquisition profiles validate \
    bitget.perpetual.linear.depth

Important: supply one source

Use either:

PROFILE_ID

or:

--file PATH

Do not supply both in one validation command.

What happens during validation?

Forge invokes the installed normalizer's supported validation interface.

Rust parses and semantically compiles the profile.

The candidate is checked using a staged catalogue.

Does validation install the profile?

No.

Validation does not publish the candidate into the managed profile catalogue.

Does validation process source records?

No.

It checks the declaration.

It does not perform a complete historical normalization workload.

Does validation prove the source semantics?

No.

A profile can compile successfully while containing a wrong timestamp unit or side mapping.

Validation should be followed by testing against representative source records.

Install a Profile

Once a candidate is valid and the relevant catalogue prerequisites are satisfied, it can be installed.

For example:

mf acquisition profiles add \
    bitget.perpetual.linear.depth \
    --from /absolute/path/to/bitget.perpetual.linear.depth.toml \
    --testing

This example assumes the candidate matches the actual intended source format and does not conflict with an existing installed interpretation.

What does installation do?

Forge checks the candidate and publishes or reuses the supported definition.

The installed file belongs to the managed profile catalogue.

Does it require PostgreSQL?

Profile publication checks the guarded testing catalogue.

The relevant execution venue must be available.

Is --testing required?

The parser accepts it as optional for profile installation.

However, the publication operation still uses the guarded testing catalogue.

Including --testing explicitly makes the intended environment clear.

Does installation replace a different existing profile?

No.

A conflicting compiled interpretation under the same ID is rejected.

Why is the operation called add?

add is the canonical profile-publication command.

The CLI also accepts:

profiles register

as an alias.

For new workflows, prefer add.

Why Structural Validation Is Not Enough

A profile can be valid according to the compiler and still misinterpret source data.

Consider a timestamp:

1767225600000

Suppose the profile incorrectly declares:

encoding = "unix_microseconds"

when the source actually uses milliseconds.

The field declaration may still be structurally valid.

However, the interpreted timestamp would be wrong.

Another example: trade side

Suppose the actual source defines:

B = Buy

but the profile maps:

B = Sell

The profile may compile successfully.

The resulting dataset would contain incorrect trade directions.

Why is this dangerous?

The output can look plausible.

For example, prices and quantities might still be valid decimals.

This means source interpretation must be tested against known expected values.

Draft an installed profile

Start with an installed definition for the same content and source format. Inspect opens the original read-only, while show summarizes only its configured settings and any displayed schema defaults.

mf acquisition profiles list --exchange bybit
mf acquisition profiles inspect bybit.perpetual.linear.depth
mf acquisition profiles show bybit.perpetual.linear.depth
mf acquisition profiles schema --field 'normalization.rules[].target'
mf acquisition profiles edit bybit.perpetual.linear.depth

Quote field paths containing shell metacharacters in shells that expand them. The draft keeps the original filename and bytes when first copied. The edit command prints its path. Continue an existing draft with nvim at that path.

mf acquisition profiles validate --file data/.config/engine/normalize/profile-drafts/bybit.perpetual.linear.depth.toml

The draft can pass Rust validation while still being ineligible to replace the installed profile. A changed interpretation under an installed ID is rejected by add and register. For a genuinely new supported identity, keep the file name and declared ID consistent and use the documented installation command with the verified venue. Read the profile CLI reference and choose the trade tutorial or depth tutorial for representative mappings and sample checks.
