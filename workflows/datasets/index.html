Inspect registered datasets

For local Python discovery, previews and schema inspection, see the Jupyter workflow.

Run from the checkout with the testing registry and Arrow inspection tools. Start with the file IDs returned by normalization or merge. To discover them later, use mf datasets find --testing --exchange bybit --instrument BTCUSDT --instrument-type perpetual --market-category linear.

For each ID, run mf datasets show ID --testing to identify the owning publication, mf datasets schema ID --testing for physical types, and mf datasets head ID --testing --limit 5 --precise for stored records. mf datasets verify ID --testing checks the selected file and shared manifest fingerprints. mf datasets streams ID --testing reports stream membership and observed bounds. mf datasets lineage ID --testing --publication includes the publication's input selections.

An observed envelope gives the earliest and latest timestamps. For depth, inspect the publication's indexed observations and reconstruction boundaries before treating rows as a usable book. Preserve the shared manifest and auxiliary files. To merge, first check layout, stream namespace and required parts in the merge guide.

Inspect from Python

Use a primary file path returned by normalization, or its path shown by datasets show. With the lab dependencies installed, open the physical file through the checkout's dataset API:

from forge.datasets.discovery import open_dataset

dataset = open_dataset(path)
print(dataset.schema())
print(dataset.head(5, columns=["event_timestamp_ns", "price"]))

Substitute the returned primary path for path. Use batches(columns=..., start=..., end=...) for bounded Arrow iteration with optional half-open timestamp filtering. To interpret depth observations, use the publication's event index and boundary metadata. Bybit example

Inspect lineage and verify files

Inspect File-Level Lineage

To inspect the registered contributions to a particular primary file, use:

mf datasets lineage FILE_ID --testing

What does the command show?

The lineage view distinguishes between raw archive inputs and parent dataset inputs.

For example:

Normalization output

A normalized file may have proven contributions from registered raw archives.

Merge output

A merged file may have contributions from registered normalized dataset files.

Raw archive lineage

For a normalized trade dataset, the lineage may identify:

Raw Archive 101
Raw Archive 102
Raw Archive 103

These are illustrative local archive IDs.

The records can include information about the exchange, source filename, archive scope, and recorded interval.

Parent dataset lineage

For a merged file, the lineage may identify:

Normalized Dataset 301
Normalized Dataset 302

These are illustrative PostgreSQL file dataset IDs.

This helps trace the merged result back to its registered normalized inputs.

Why distinguish the two?

Raw archives and normalized datasets are different types of inputs.

A normalization publication normally derives from raw market-data recordings.

A merge publication derives from compatible normalized datasets.

Separating these relationships makes the processing history easier to understand.

Inspect Source Checksums

Lineage can also display retained raw-input checksums.

Use:

mf datasets lineage FILE_ID \
    --testing \
    --checksums

Why are checksums useful?

A checksum helps identify the exact file contents associated with a registered source.

For example, two archives may have identical filenames but different contents.

Their SHA-256 checksums can distinguish them.

This is useful when investigating:

  • Source-file changes.
  • Duplicate or conflicting recordings.
  • Reproducibility.
  • Historical processing evidence.
  • Unexpected data differences.

Does displaying a checksum verify the current raw file?

No.

The lineage command displays retained checksum evidence.

It does not automatically rehash every original raw archive during ordinary lineage inspection.

For current raw-file integrity, use the applicable storage verification command.

Combine publication and checksum inspection

You can request both:

mf datasets lineage FILE_ID \
    --testing \
    --publication \
    --checksums \
    --limit 10

This displays a bounded set of lineage entries together with the expanded publication selection.

Lineage display limits

The terminal lineage view defaults to:

25 rows per section

The accepted limit is:

1–1000

For example:

mf datasets lineage FILE_ID \
    --testing \
    --limit 100

The limit affects displayed lineage entries, not the underlying registered relationships.

Full JSON lineage

For machine-readable lineage:

mf --json datasets lineage FILE_ID --testing

JSON returns the underlying file-contribution and publication-selection information.

This is useful when performing more detailed provenance analysis.

Verifying Datasets

Preview a Registration Migration

Before changing the registry, inspect which legacy registrations need migration.

First, ensure the database schema is current:

mf database migrate --testing

Then run:

mf datasets migrate-registration \
    --all \
    --testing \
    --dry-run

Why use dry-run?

The migration may involve existing publication records and file relationships.

A dry-run allows you to inspect the proposed work before applying database changes.

What does the preview inspect?

The migration workflow examines eligible legacy aggregate registrations.

It verifies the corresponding committed publication evidence.

This can include reading existing files and checking their SHA-256 fingerprints.

Does dry-run read Parquet files?

It can read existing publication file bytes to perform the required verification.

Therefore, dry-run should not be interpreted as a metadata-only operation.

However, it does not apply the final file-level registration changes.

What does the preview report?

The result can include:

  • Legacy dataset IDs.
  • Corresponding publication identities.
  • Primary files eligible for registration.
  • Existing matching file registrations.
  • Retained raw-input relationships.
  • Potential conflicts.
  • The number of primary files involved.

Why is --all required?

The migration is an explicit registry-wide operation for the supported legacy aggregate selection.

MarketForge requires:

--all

to make that scope explicit.

Both preview and apply use the selected registry. The examples pass --testing to keep them in the testing workspace.

Can I preview one arbitrary legacy ID?

The documented migration command requires --all.

It does not expose a separate single-ID migration action through this CLI.

Inspect the preview result to understand the individual legacy registrations included in the operation.

Apply the Registration Migration

Once you have reviewed the preview, apply the migration:

mf datasets migrate-registration \
    --all \
    --testing

What happens during migration?

For eligible legacy normalization registrations, MarketForge:

  1. Verifies the committed publication.
  2. Checks the retained publication fingerprints.
  3. Resolves the primary files.
  4. Reuses the existing registered raw-input relationships.
  5. Creates or reuses the corresponding file-level records.
  6. Preserves the legacy aggregate reference and its historical relationships.

Does migration rewrite the Parquet files?

No.

The migration updates database registration information.

It leaves the published Parquet files and their manifests in place.

Does migration rerun normalization?

No.

It uses the existing committed publication and its retained evidence.

It does not decode the original exchange archives again.

What happens to source lineage?

The migration reuses the relevant registered raw-input relationships.

This helps preserve the historical relationship between the existing publication and its original sources.

Can the migration be repeated?

Yes.

The supported migration is designed to reuse compatible existing file-level registrations.

Repeated application should not create duplicate primary file identities for identical evidence.

What if some registrations fail?

The migration can report conflicts for individual legacy aggregates.

Independent successful conversions may already have been applied before a later conflict is reported.

A nonzero exit code does not necessarily mean no changes were made.

Inspect the result carefully.

What about legacy merge registrations?

The current migration path does not automatically convert legacy merge aggregates.

These are reported as conflicts because the required historical merge input evidence cannot always be established through the supported migration procedure.

Do not invent missing lineage to make them pass.

How do I inspect an old ID afterward?

Use:

mf datasets show LEGACY_ID --testing

Replace LEGACY_ID with an actual legacy aggregate ID.

When the migration mapping exists, MarketForge can report the replacement file IDs.

Use those file IDs for subsequent inspection.

Recover Missing File Registrations

Sometimes Engine has committed a valid publication, but Forge could not complete the database registration.

For example, PostgreSQL might become unavailable after normalization finishes.

In this situation, you may already have a valid committed publication on disk.

Rerunning the entire processing workload could be unnecessary.

MarketForge provides registration-only recovery through the relevant processing command.

Recover a normalized publication

Use:

mf normalize register \
    /path/to/normalized-publication/manifest.json \
    --testing

Replace the path with an actual committed manifest.

Recover one normalized primary file

You can also specify one primary Parquet file:

mf normalize register \
    /path/to/publication/streams/STREAM/trades/part-000000.parquet \
    --testing

Recover a merged publication

For a committed merge manifest:

mf merge register \
    /path/to/merged-publication/manifest.json \
    --testing

Or one merged primary file:

mf merge register \
    /path/to/publication/timeline/partition-000000/part-000000.parquet \
    --testing

Why use the processing-specific registration command?

Normalization and merging have different publication contracts.

The corresponding registration services understand their applicable output structures and evidence.

Use the command associated with the operation that created the publication.

Can I recover using an execution intent?

Yes.

The supported registration-only workflows can accept retained execution-intent receipts.

These help locate and verify the committed outputs associated with a previous processing attempt.

See the normalization and merge guides for the appropriate recovery procedures.

Does registration-only recovery reprocess data?

No.

It verifies existing committed output and registers eligible files.

It does not repeat normalization or merging.

What if the output is incomplete?

An incomplete staging directory is not automatically a valid committed publication.

Registration requires the applicable committed files and verification evidence.

If Engine never completed publication, investigate the processing failure rather than trying to register incomplete files.
