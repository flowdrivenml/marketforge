Ranking and historical metadata policies

Configuration for ranking policies and historical specification and identity inference. Use market workflows for procedures.

Where Ranking Policies Are Stored

Managed ranking policies live under:

data/.config/markets/rankings/

For example:

data/.config/markets/rankings/
├── turnover.toml
├── volume.toml
├── activity.toml
└── base-volume.toml

These files contain the policies used by MarketForge's ranking system.

Create a policy

For example:

mf markets rank new activity

MarketForge creates:

data/.config/markets/rankings/activity.toml

The generated file is a version-2 turnover policy template.

Edit the policy

Open it with:

nvim data/.config/markets/rankings/activity.toml

Update its fields to match your intended comparison.

Does new open an editor?

No.

It creates the template file.

Edit it separately.

Does the policy name determine the metric?

No.

For example:

mf markets rank new volume-example

still creates a turnover template.

To create a volume policy, write the appropriate volume configuration explicitly.

Can policy names be arbitrary paths?

No.

Ranking commands use safe managed policy names.

For example:

activity
activity.toml

can refer to the managed policy.

Do not pass arbitrary directory paths or traversal expressions as policy names.

What does global --config do?

The global option:

--config PATH

selects application settings.

It does not select a ranking policy.

For example:

mf --config ./workspace-settings.toml \
    markets rank validate activity

still validates the managed ranking policy named activity.

Turnover Rankings

What Is Turnover?

Turnover represents monetary trading activity over a measurement window.

For example:

BTCUSDT
24h turnover: 500,000,000 USDT

This represents monetary activity denominated in USDT.

Why rank by turnover?

Turnover can provide a useful basis for comparing activity across different instruments.

For example:

BTCUSDT
ETHUSDT
SOLUSDT

have different base assets.

Their base quantities cannot be compared directly.

However, their monetary activity can be compared when expressed in a consistent currency and supported by compatible observations.

Is turnover always directly reported?

No.

Different exchanges provide different statistics.

Some supply monetary turnover directly.

Others provide contract volume or base volume that requires additional interpretation.

For example:

Base volume × Reference price

can produce an estimate of monetary activity.

But this is not necessarily equivalent to an exchange-reported accumulated turnover.

Why preserve the distinction?

Because an estimated amount may be less reliable than a directly reported amount for certain research purposes.

MarketForge preserves the relevant interpretation evidence.

Ranking policies can explicitly allow or exclude estimates.

A Complete Turnover Policy

The following example creates a ranking of supported Bybit markets using USDT as the comparison currency.

Save it as:

data/.config/markets/rankings/activity.toml

version = 2

metric = "turnover_24h"
comparison_currency = "USDT"

exchanges = ["bybit"]
markets = ["spot", "linear", "inverse"]
instruments = []

max_age_seconds = 3600
max_window_skew_seconds = 300

estimates = "exclude"
allow_partial_universe = true

manual_preferences = []

[conversion]
automatic = true
valuation = "reference_price_turnover"

max_price_age_seconds = 3600
max_leg_skew_seconds = 300

max_hops = 2
bridge_assets = []

prefer_same_exchange = true
allow_cross_exchange = false
allow_mixed_exchanges = false

source_exchanges = [
    "bybit",
    "binance",
    "okx",
    "gateio",
    "bitget",
]

equivalent_currencies = []

This is a complete version-2 turnover policy.

What does it do?

The policy requests:

Property Value
Metric 24-hour turnover
Comparison currency USDT
Exchanges Bybit
Markets Spot, linear, inverse
Maximum observation age 1 hour
Maximum source-window skew 5 minutes
Estimated turnover Excluded
Partial universe Allowed
Automatic currency conversion Enabled
Maximum conversion hops 2
Mixed-exchange conversion legs Not allowed

Important limitation

This policy is structurally valid.

However, a successful ranking build still requires suitable stored observations and eligible currency conversion references.

The example does not claim those observations are currently available.

Why allow partial coverage in this example?

The example uses:

allow_partial_universe = true

to demonstrate how MarketForge can publish eligible entries while recording exclusions.

The generated turnover template is stricter and defaults to:

allow_partial_universe = false

Choose the behavior deliberately.

Policy Versions

Ranking policies support two versions.

Version Default conversion behavior
1 Automatic currency conversion disabled by default.
2 Automatic currency conversion enabled by default for turnover.

Version 1

For example:

version = 1

This uses the older policy behavior.

Automatic conversion is disabled unless explicitly configured.

Version 2

For example:

version = 2

This enables automatic spot-price conversion by default for turnover policies.

Why does the distinction matter?

Suppose your ranking includes BTC-denominated turnover but compares values in USDT.

Without an applicable conversion rule, the BTC amount cannot be scored in USDT.

Version 2 provides the supported automatic conversion configuration by default.

However, automatic conversion still depends on actual eligible stored spot-price observations.

What if version is omitted?

The policy defaults to version 1.

For new policies, explicitly use:

version = 2

when you want the current version-2 behavior.

Choose the Ranking Metric

The metric field specifies what MarketForge compares.

The current values are:

turnover_24h
volume

Turnover

Use:

metric = "turnover_24h"

This selects monetary activity comparison.

Volume

Use:

metric = "volume"

This selects grouped base-asset quantity comparison.

Can I rank by open interest?

Not through the current general ranking metric schema.

MarketForge can retain supported open-interest observations, but the ranking policy currently supports turnover and volume.

Can I rank by funding rate?

Not through the current ranking metric schema.

Funding rates are separate retained market statistics.

Does the metric determine how currency conversion works?

Yes.

Turnover policies can use a comparison currency and supported FX conversion rules.

Volume policies instead compare quantities within base-asset groups.

These are different comparison models.

Selecting the Ranking Universe

What Is the Ranking Universe?

The ranking universe is the set of instruments that the policy attempts to evaluate.

For example:

All supported Bybit spot instruments

or:

Bybit and OKX linear perpetual markets

A ranking cannot meaningfully compare every conceivable instrument without defining which markets belong to its intended selection.

MarketForge therefore provides explicit universe filters.

Example

exchanges = ["bybit"]
markets = ["spot", "linear"]

This restricts the policy to the supported instruments matching those exchange and market selections.

Why define the universe?

Suppose you want a ranking of Bybit spot activity.

Including unrelated inverse futures would change the meaning of the result.

The universe makes the comparison explicit.

When are filters applied?

Universe filters are applied during ranking evaluation.

They define which instruments are considered.

They are different from display filters used when inspecting an already published ranking.

Exchange Selection

Use:

exchanges = ["bybit"]

to restrict the ranking to Bybit.

Multiple exchanges

For example:

exchanges = ["bybit", "okx"]

This selects instruments from both exchanges.

All supported exchanges

An empty list means the supported exchange universe is not restricted by an explicit exchange filter.

Freshness and Measurement Windows

Why Ranking Freshness Matters

Market statistics describe observations made at particular times.

For example, one exchange may report a 24-hour turnover value ending at noon.

Another exchange may report its rolling window ending several hours earlier.

These observations may both be valid, but they are not necessarily suitable for direct comparison.

MarketForge therefore applies freshness and window-alignment requirements.

Example

Imagine:

Bybit BTCUSDT
Window end: 12:00 UTC

OKX BTCUSDT
Window end: 08:00 UTC

Comparing the two values as though they represented the same recent 24-hour period could be misleading.

Why not just check the fetch time?

Because a recently fetched statistic can still describe an old source window.

For example:

Fetched at: 12:00
Window end: 08:00

The HTTP request completed recently.

However, the underlying measurement ends four hours earlier.

MarketForge checks the relevant observation and source-window information separately.

Maximum Observation Age

Use:

max_age_seconds = 3600

This sets the maximum accepted observation age to one hour.

Accepted range

The supported range is:

1–604800 seconds

604800 seconds is seven days.

What does the policy check?

The ranking evaluator checks relevant timestamps, including:

  • Fetch time.
  • Source-window end.

An observation can be rejected when its timestamps are too old for the selected policy.

Why does this matter?

Suppose you build a ranking using observations collected yesterday.

If the policy requires data no older than one hour, the observations do not satisfy the policy.

MarketForge does not silently reinterpret the stale values as current.

Does a longer maximum age improve ranking quality?

Not automatically.

A larger age limit permits older observations.

That may be appropriate for some comparisons, but it also increases the chance of combining measurements from different market conditions.

Choose the limit based on the intended use.

Source-Window Alignment

Use:

max_window_skew_seconds = 300

This sets a five-minute tolerance.

Accepted range

The supported range is:

0–86400 seconds

Why compare source windows?

Suppose two turnover measurements were collected at different times.

For example:

Market A:
Window end 12:00

Market B:
Window end 11:58

A five-minute tolerance can permit this difference when the remaining requirements are satisfied.

Now consider:

Market A:
Window end 12:00

Market B:
Window end 10:00

These windows differ by two hours.

The second observation may be rejected under the five-minute alignment policy.

Does window skew control future timestamps?

It also participates in the supported future-time checks.

For example, a source observation reporting a measurement window far into the future relative to the ranking build time is not automatically accepted.

Volume-specific requirement

Volume ranking also requires a compatible 24-hour measurement duration.

This matters because comparing quantities measured over substantially different durations would not represent the same activity window.

Does a successful statistics refresh guarantee compatible windows?

No.

A provider may return observations whose source times or inferred measurement windows do not satisfy the ranking policy.

The build performs the relevant checks independently.

Estimated Values and Partial Coverage

Estimated Turnover

Some providers report monetary turnover directly.

Others supply quantities that can be used to estimate monetary activity.

For example:

Base volume × Last price

can produce an estimated turnover.

Why is this an estimate?

Because the last price is not necessarily the price at which every trade in the measurement window occurred.

For example:

Volume: 1,000 BTC
Last price: 80,000 USDT

gives:

Estimated turnover: 80,000,000 USDT

However, the actual trades may have occurred at several different prices.

The estimated result is not necessarily equal to the true accumulated execution turnover.

Configure estimate handling

The policy supports:

estimates = "exclude"

or:

estimates = "allow"

Exclude estimates

estimates = "exclude"

rejects relevant estimated values under the ranking eligibility rules.

This is the default.

Allow estimates

estimates = "allow"

permits the supported estimated values.

Their derivation evidence remains available.

Important distinction

The estimates setting controls the relevant volume-derived estimates.

It does not prohibit the separate ranking convention of valuing native monetary turnover using an eligible reference FX price.

These are different operations.

Strict Rankings

By default, a ranking policy uses:

allow_partial_universe = false

This is the strict behavior.

What does strict mean?

MarketForge expects the selected universe to satisfy the required comparison rules.

For example:

BTCUSDT  Eligible
ETHUSDT  Eligible
SOLUSDT  Missing turnover

If the policy requires a complete eligible universe, the missing observation can prevent publication.

Why reject the ranking?

Because publishing only BTCUSDT and ETHUSDT without acknowledging the missing SOLUSDT value could make the result appear more complete than it is.

What happens to an unsuccessful build?

An unsuccessful ranking build does not publish a valid new snapshot.

The attempted publication is rolled back.

Previously published snapshots remain available.

Partial Rankings

You can explicitly permit exclusions:

allow_partial_universe = true

What does this mean?

MarketForge can publish eligible entries while recording why other selected instruments were excluded.

For example:

Included:
BTCUSDT
ETHUSDT

Excluded:
SOLUSDT — missing turnover
XRPUSDT — stale observation

Does partial mode accept invalid values?

No.

Missing turnover remains missing.

Stale observations remain stale.

Invalid units remain invalid.

The setting permits eligible entries to be published with exclusions and the supported partial-refresh handling.

It does not convert invalid inputs into valid scores.

Can the result contain zero eligible instruments?

No.

At least one comparable entry is required.

Why preserve exclusions?

An excluded instrument is not equivalent to a low-ranked instrument.

For example:

Rank 100

means the instrument was included and received that position.

Excluded: missing turnover

means the instrument could not be scored under the policy.

This distinction is essential when interpreting ranking results.

Turnover Currency Conversion

Why Does Turnover Need Currency Conversion?

Suppose you want one ranking containing instruments whose monetary turnover is expressed in different currencies.

For example:

Instrument Native turnover
BTCUSDT 500 million USDT
BTCUSDC 450 million USDC
ETHBTC 2,000 BTC

You cannot compare the bare numeric values directly.

A turnover policy therefore uses:

comparison_currency = "USDT"

This tells MarketForge to express eligible monetary activity in USDT.

Does MarketForge assume USDT and USDC are identical?

No.

USD, USDT, and USDC remain distinct currencies.

Any equivalence must be explicit.

Where do conversion rates come from?

The current turnover-ranking policy supports:

  1. Identity conversion.
  2. Explicit manual rates.
  3. Explicit currency-equivalence assumptions.
  4. Eligible stored spot-market prices.

The ranking evaluator uses this precedence.

Automatic Spot-Price Conversion

Version-2 turnover policies support:

[conversion]
automatic = true

This enables automatic conversion using eligible stored spot-market prices.

Example

Suppose the native turnover is denominated in BTC.

The comparison currency is USDT.

An eligible BTCUSDT spot observation can establish:

BTC → USDT

Direct conversion

For example:

2 BTC × 80,000 USDT/BTC = 160,000 USDT

The values are illustrative.

Inverse conversion

The same currency relationship can be used in reverse when the supported source price is appropriate.

For example:

USDT → BTC

uses the inverse price relationship.

Why only use eligible spot prices?

Ranking conversion needs a currency relationship that can be interpreted according to the supported policy.

The current ranking system uses stored spot-market references.

Derivative last prices are not general-purpose ranking FX sources.

Does automatic conversion contact exchanges?

Not during rank build.

The build uses retained observations.

If the necessary spot prices are missing, obtain suitable market statistics through the separate collection workflow.

Maximum Conversion Hops

The policy supports:

max_hops = 2

Accepted values are:

1
2

One hop

A direct conversion path:

BTC → USDT

Two hops

A bridged conversion path:

USDC → BTC → USDT

This uses one intermediate asset.

Why limit the path length?

Each conversion leg introduces another observation with its own timestamp and source.

Longer paths can become more difficult to compare reliably.

The current policy therefore supports direct paths or one bridge.

Can I configure three or four hops?

Not in the current ranking conversion schema.

The historical conversion Engine has a separate policy and different supported hop limits.

Do not confuse the two systems.

Bridge Assets

The conversion policy supports:

bridge_assets = []

What is a bridge asset?

A bridge asset is an intermediate currency used when no direct conversion is available.

For example:

USDC → BTC → USDT

uses BTC as a bridge.

Empty bridge list

An empty list allows any eligible connecting spot asset under the supported conversion rules.

Restricted bridge list

For example:

bridge_assets = ["BTC", "ETH"]

restricts intermediate assets to the listed currencies.

The list also provides their configured preference order.

Why restrict bridges?

You may want to avoid conversion paths involving obscure or unsuitable intermediate markets.

A restricted bridge list makes the permitted intermediate assets explicit.

Default behavior

When the field is omitted, the supported default bridge assets are BTC and ETH.

An explicitly empty list is different.

For example:

bridge_assets = []

means the connecting-asset choice is not restricted to that default pair.

Limits

A nonempty bridge list can contain up to 16 unique uppercase currency codes.

Duplicate bridge assets are rejected.

Exchange Preferences

The conversion policy supports:

prefer_same_exchange = true
allow_cross_exchange = false
allow_mixed_exchanges = false

These fields control which exchanges can provide conversion references.

Prefer the same exchange

For example, suppose you are ranking a Bybit instrument.

A suitable Bybit spot reference is preferred over a foreign-exchange reference under the supported ordering rules.

The current schema requires:

prefer_same_exchange = true

Cross-exchange conversion

The policy can permit a complete conversion path from another allowed exchange.

For example:

allow_cross_exchange = true

This can be useful when the target exchange lacks an eligible conversion market.

However, the reference still needs to satisfy the applicable age and alignment checks.

Mixed-exchange paths

The current policy requires:

allow_mixed_exchanges = false

This means a two-leg conversion path cannot combine legs from different exchanges.

For example:

Leg 1: Bybit
Leg 2: Binance

is not a supported mixed-venue path.

Why restrict mixed exchanges?

Different exchanges can have different:

  • Liquidity conditions.
  • Price observations.
  • Measurement times.
  • Trading conventions.

Combining observations from different venues can introduce additional comparability problems.

The current policy therefore requires complete paths to satisfy its supported venue constraints.

Reference Exchange Selection

The policy supports:

source_exchanges = [
    "bybit",
    "binance",
    "okx",
    "gateio",
    "bitget",
]

This specifies the allowed reference exchanges and their preference order.

Why does order matter?

When several conversion paths are eligible, MarketForge uses deterministic preference rules.

The configured exchange order can help resolve otherwise comparable candidates.

Does listing an exchange guarantee its prices are used?

No.

The source must still be eligible under:

  • Exchange permissions.
  • Available spot instruments.
  • Observation freshness.
  • Currency path requirements.
  • Measurement timing.
  • Other conversion constraints.

Does source_exchanges override allow_cross_exchange?

No.

Listing another exchange as a possible reference source does not automatically authorize cross-exchange conversion.

The applicable permission settings still control eligibility.

How MarketForge Chooses a Conversion Path

When several eligible spot-price paths exist, MarketForge applies a deterministic preference order.

The supported rules consider:

  1. Same-exchange paths before permitted foreign-exchange paths.
  2. Fewer conversion legs.
  3. Configured source-exchange preference.
  4. Freshness of the weakest conversion leg.
  5. Configured bridge-asset preference.
  6. Stable identity tie-breakers.

Why use deterministic selection?

Suppose several exchanges provide a BTCUSDT reference price.

Without a defined preference policy, the selected rate could depend on incidental database ordering.

That would make ranking results harder to explain.

MarketForge therefore defines how eligible paths are selected.

Can a local bridged path beat a foreign direct path?

Yes.

Same-exchange preference is evaluated before the number of legs under the current policy.

For example:

Bybit:
USDC → BTC → USDT

may be preferred over:

Binance:
USDC → USDT

when both are eligible and the policy permits the foreign reference.

Does fewer hops always win?

Not across every possible exchange relationship.

The complete preference order matters.

Does selecting a path guarantee the underlying rate is perfect?

No.

The conversion uses eligible retained observations and the specified valuation convention.

It does not reconstruct every actual execution-time currency rate within the turnover measurement window.

Conversion Reference Freshness

The conversion policy has separate limits for spot-price references.

For example:

max_price_age_seconds = 3600
max_leg_skew_seconds = 300

Maximum price age

max_price_age_seconds = 3600

sets the maximum accepted age of relevant conversion-price observations.

1–604800 seconds

If omitted, the setting inherits the policy's general maximum observation age.

Maximum leg skew

max_leg_skew_seconds = 300

controls the allowed timing difference between relevant conversion legs.

The supported explicit range is:

0–86400 seconds

If omitted, it inherits the general source-window skew setting.

Why have separate limits?

The turnover observation and the conversion prices are different pieces of evidence.

For example:

Turnover observation:
12:00

Conversion reference:
09:00

The turnover may be fresh while its reference price is too old.

MarketForge checks these conditions independently.

Can a stale reference be accepted because the turnover is fresh?

Not when it violates the configured conversion policy.

A valid turnover observation does not make an invalid reference price suitable.

Explicit Currency Equivalence

Sometimes users want to make an explicit 1:1 currency assumption.

For example, a policy might use USDT as its comparison currency while treating USD as equivalent.

This can be declared as:

[conversion]
equivalent_currencies = ["USD"]

What does this mean?

It explicitly assumes:

1 USD = 1 USDT

for the ranking comparison.

Is this an actual market-price observation?

No.

It is a user-supplied modeling assumption.

MarketForge does not independently prove that the currencies were trading at exactly the same value.

Why is this important for stablecoins?

Stablecoin prices can differ from their intended reference currencies.

For example, USDC and USDT are distinct assets.

A 1:1 equivalence should not be silently assumed.

Does MarketForge enable equivalence by default?

No.

The default is:

equivalent_currencies = []

Can the comparison currency appear in the list?

No.

For example, if the comparison currency is USDT, do not include USDT itself.

Identity conversion already handles that case.

Manual Conversion Rates

A policy can provide explicit rates when appropriate.

For example:

[conversion.manual_rates.EUR]
rate = "1.08"
as_of = 2026-11-20T12:00:00Z
source = "Documented reference observation"

This is an illustrative declaration.

It is not a verified historical EUR/USDT rate.

What does the rate mean?

The rate represents units of the comparison currency per one unit of the native currency.

For example, with USDT as the comparison currency:

1 EUR = 1.08 USDT

under the supplied manual assumption.

Why use a decimal string?

Financial rates benefit from exact decimal representation.

For example:

rate = "1.08"

preserves the intended decimal value.

Why require as_of?

MarketForge needs to know when the rate was actually observed.

The timestamp must include a timezone.

Why require source?

A manual rate can materially affect ranking scores.

The source field records its provenance.

Does a stale manual rate fall back to automatic conversion?

No.

If a configured manual override fails the applicable freshness or future-time checks, MarketForge does not silently replace it with an unrelated spot-price path.

Review the manual rate deliberately.

What about a manual rate for the comparison currency?

If a manual rate is supplied for the comparison currency itself, it must equal 1.

Identity conversion always takes precedence.

Legacy Manual Rate Fields

Older ranking policies may contain top-level conversion fields.

The supported legacy fields include:

conversion_rates
conversion_as_of
conversion_source

These remain readable for compatibility.

Why retain them?

Existing ranking policies should not become unreadable merely because the supported configuration has evolved.

Should new policies use them?

For new version-2 policies, prefer the structured manual-rate declarations under:

[conversion.manual_rates.CURRENCY]

Can I declare the same currency twice?

No.

A currency cannot appear in both the legacy manual-rate map and the newer structured manual-rate configuration.

This prevents conflicting declarations.

Do legacy rates require provenance?

Yes.

The relevant manual conversion information requires an observation time and source.

For legacy rates, the supported top-level provenance fields must be supplied.

Precision of Ranking Scores

MarketForge uses decimal representations and retained conversion evidence when calculating ranking scores.

Why does precision matter?

A ranking may compare very large monetary amounts.

For example:

1,000,000,000 USDT

It may also use conversion rates with many decimal places.

Unnecessary floating-point rounding can affect close comparisons.

How are rates and scores retained?

The current implementation preserves exact-ratio evidence from decimal inputs.

Stored rates and scores are rounded to 80 significant digits.

Does the terminal display all 80 digits?

Not necessarily.

Terminal presentation can abbreviate large or precise values.

The displayed representation is not the full calculation precision.

How can I inspect the evidence?

Use the ranking inspection commands.

For example:

mf markets rank show activity \
    --testing \
    --conversion 1

Replace 1 with a valid stored position or use an exact returned instrument reference.

The output exposes the applicable conversion or volume derivation evidence.

What Are Manual Preferences?

A turnover ranking normally orders eligible instruments by their calculated scores.

For example:

1. BTCUSDT
2. ETHUSDT
3. SOLUSDT

However, the policy can also specify manual ordering preferences.

These are declared through:

manual_preferences = []

Why support manual preferences?

A research workflow may intentionally prioritize certain instruments.

For example, you might want a particular reference market to appear before otherwise higher-scoring instruments.

How are preferences supplied?

Use exact stored instrument references.

For example:

manual_preferences = [
    "bybit.spot.BTCUSDT",
]

This is an illustrative reference.

Use the exact reference returned by the catalogue.

What happens during ranking?

Specified preferences can move the selected turnover instruments ahead of the ordinary score ordering.

The remaining eligible instruments are ordered according to the supported score and stable-reference rules.

Does this mean the ranking is purely descending turnover?

Not necessarily.

When manual preferences are present, the final order includes an explicit policy decision.

The published snapshot retains the policy and ordering evidence.

Are manual preferences allowed in volume rankings?

No.

Volume rankings reject manual preferences.

Their ordering is based on supported base-asset quantity comparisons within each group.

Can preferences contain duplicates?

No.

Duplicate references are rejected.

References outside the selected ranking universe are also invalid.

Volume Rankings

Why Volume Rankings Are Different

Turnover rankings compare monetary activity.

Volume rankings compare quantities.

These are different measurements.

For example:

BTCUSDT:
Volume = 1,000 BTC

ETHUSDT:
Volume = 20,000 ETH

The numeric values cannot be interpreted as one universal quantity comparison.

The assets are different.

Why not rank them together?

Because 1,000 BTC and 20,000 ETH are quantities expressed in different units.

Comparing their bare numbers does not establish which market has greater monetary activity.

How does MarketForge handle this?

Volume rankings group instruments by base asset.

For example:

BTC Group
    BTCUSDT
    BTCUSDC
    BTCUSD

ETH Group
    ETHUSDT
    ETHUSDC
    ETHBTC

Each group is ranked independently.

Why is this useful?

You may want to compare trading activity across markets for the same underlying asset.

For example:

BTC Spot
BTC Linear Perpetual
BTC Inverse Perpetual
BTC Futures

When the required quantity evidence is available, MarketForge can compare their supported base-asset volumes.

How Volume Is Interpreted

Some exchanges report quantities directly in base-asset units.

For example:

BTCUSDT Spot
Volume: 1,000 BTC

This can be used as base volume when the reported interpretation is trustworthy.

However, derivative markets may report contract counts.

Example: Contract quantity

Suppose an exchange reports:

Volume: 100,000 contracts

This does not directly tell us how many BTC were traded.

MarketForge needs the contract specification.

Base-denominated contract value

Suppose the registered contract specification states:

1 contract = 0.01 BTC

Then:

100,000 contracts × 0.01 BTC
= 1,000 BTC

When the relevant specification evidence is valid, this supports an exact contract-count conversion.

Quote-denominated contract value

Another derivative might specify:

1 contract = 100 USD

Converting that count into BTC quantity may require a price observation.

For example:

Contract count × USD face value ÷ BTC price

This introduces a price-based estimate.

Why distinguish exact and estimated quantities?

Because a contract-count conversion using a verified base-denominated multiplier is different from a conversion that depends on a reference market price.

The latter introduces additional assumptions.

MarketForge retains the relevant derivation evidence.

What if the contract specification is missing?

The quantity cannot be safely converted into base units under that method.

The instrument may be excluded or cause strict ranking rejection.

Do not invent a contract multiplier merely to obtain a score.

Zero Volume vs. Missing Volume

This distinction matters for ranking.

Suppose one instrument reports:

Volume: 0 BTC

Another has no trustworthy base-volume observation.

These cases are different.

Reported zero

A reliable reported zero is a valid numeric observation.

It may indicate no measured volume during the applicable window.

Missing observation

A missing value means the relevant quantity is unavailable.

It does not mean zero trading occurred.

Why preserve this distinction?

Treating missing values as zero would place instruments at the bottom of a ranking without evidence that they actually had no trading activity.

MarketForge therefore keeps missing information separate from valid zero quantities.

Does partial mode change this?

No.

Partial mode can permit exclusions.

It does not turn missing values into zeros.

Volume Ranking Positions

Volume rankings retain both a unique stored position and a rank within each base-asset group.

Example

BTC Group

Group rank 1: BTCUSDT
Group rank 2: BTCUSDC


ETH Group

Group rank 1: ETHUSDT
Group rank 2: ETHBTC

Each group has its own rank 1.

Why is this important?

A BTC instrument at stored position 2 is not automatically economically comparable to an ETH instrument at stored position 3.

The relevant volume comparison occurs within each base-asset group.

What is group_rank?

It identifies the instrument's position within its asset group.

Does filtering change group ranks?

No.

Published positions and group ranks remain fixed.

For example, filtering to Bybit perpetual instruments does not cause MarketForge to recalculate the original ranking.

What if quantities are equal?

The ranking uses deterministic reference-based tie-breaking under its supported ordering rules.

This helps keep results stable when eligible quantities are equal.

Validating and Publishing Rankings

Historical metadata inference

MarketForge works with historical financial data.

However, exchanges do not always provide a complete historical catalogue of every instrument and its specifications.

For example, you might have an OKX futures archive containing trades from a contract that expired several years ago.

The source file may still be available.

However, the exchange's current API might no longer provide all the corresponding historical specifications.

Why is this a problem?

To normalize the trades correctly, MarketForge needs to know the contract's economic properties.

For example:

  • The instrument identity.
  • Contract value.
  • Contract denomination.
  • Quantity type.
  • Base and quote assets.
  • Settlement asset.
  • Historical applicability.

Without this information, a raw quantity such as:

100 contracts

cannot be safely interpreted.

What if historical specifications are missing?

MarketForge supports a controlled metadata-enrichment policy.

It can use retained catalogue information and compatible reference-contract evidence to establish operationally applicable metadata.

This is different from inventing arbitrary contract specifications.

Why is the distinction important?

A metadata value inferred from a related instrument may be operationally useful.

However, it is not necessarily independently verified as historically correct.

MarketForge distinguishes operational inference from verified historical authority.

  • Report unresolved metadata.

Does enrichment download raw archives?

No.

It operates on the relevant existing registered information and managed raw inputs.

It does not replace the historical acquisition workflow.

Does it copy or re-register raw files?

No.

The enrichment stage does not create a separate raw-data registry or move existing raw files into another storage subsystem.

What if an exchange metadata scope fails?

Previously retained observations can remain available.

Initialization reports exchange collection failures separately from historical metadata readiness.

One successful metadata stage does not automatically mean every historical archive is ready for normalization.

The Historical Inference Policy

MarketForge currently uses a named historical metadata inference policy:

catalogue-btc-reference-v1

This policy defines how supported historical specifications are resolved.

Why use a named policy?

Inference rules should be explicit and traceable.

For example, a future change to the inference algorithm should not silently redefine the meaning of earlier evidence.

A named policy allows MarketForge to record which interpretation rules were used.

Evidence precedence

The current policy considers evidence in the following order:

  1. Historically verified specifications.
  2. Immutable historical declarations.
  3. Exact retained catalogue specifications.
  4. Compatible BTC futures or options reference evidence.

Why is precedence important?

Not all metadata sources provide the same authority.

For example, an explicit historical specification supported by exchange documentation should not be silently replaced by a value inferred from another contract.

The policy therefore gives stronger evidence precedence over weaker inference.

Can inference override conflicting explicit declarations?

No.

Conflicting explicit declarations block preparation.

MarketForge does not resolve those conflicts by silently falling back to inferred values.

Why?

Because doing so could replace historically established instrument rules with an assumption.

For financial data, such substitutions can materially change the interpreted quantities.

Why Use BTC Reference Contracts?

Some derivative markets contain families of contracts with shared economic conventions.

For example, a futures chain may contain several dated BTC contracts belonging to the same product family.

A compatible contract may provide useful evidence about shared specification fields.

Example

Imagine an exchange lists several BTC futures:

BTC Contract A
BTC Contract B
BTC Contract C

Their expiration dates differ.

However, certain shared properties may be the same.

For example:

Quantity denomination
Contract-value convention
Market category
Settlement asset

When the required compatibility conditions are satisfied, MarketForge can use a reference contract to fill missing shared specification information.

Does this mean every BTC contract is identical?

No.

Even related contracts can differ.

For example, contract values or other economic properties may change across products or historical periods.

The inference policy therefore imposes compatibility requirements.

What must match?

The reference and target must agree on the applicable known properties, including:

  • Exchange.
  • Product type.
  • Market category.
  • Base asset.
  • Quote asset.
  • Settlement asset.
  • Known quantity denomination.
  • Known contract-value denomination.

Can a Binance contract be used for an OKX instrument?

Not under the described same-exchange reference requirement.

The reference must belong to the compatible exchange and product context.

Does this apply only to BTC?

The current named policy uses compatible BTC reference evidence for supported futures and options cases.

Do not generalize this into unrestricted cross-asset specification inheritance.

What Information Can Be Inherited?

The inference policy is deliberately limited.

It can inherit compatible missing shared specification fields.

It does not blindly replace all metadata.

Example

Suppose the target contract already has:

Exchange: OKX
Instrument type: Future
Market category: Linear
Base asset: BTC
Quote asset: USDT
Expiration: Known
Contract value: Missing

A compatible reference may provide evidence for the missing contract-value information under the current policy.

However, the actual inheritance depends on the available source evidence and compatibility rules.

What cannot be invented?

MarketForge preserves instrument-specific information.

For example:

  • Expiration dates.
  • Option strike prices.
  • Call or put classification.
  • Underlying identity.
  • Exact known specifications.
  • Other contract-specific values.

Why preserve these fields?

Two futures contracts may share an economic contract convention while expiring on different dates.

They remain different instruments.

Similarly, two options may share a base asset while having different strikes and expirations.

Inference must not erase those distinctions.

What if the reference conflicts with known target information?

The inference is not accepted as a silent replacement.

Conflicts must be reported and resolved through the supported evidence system.

Operational Inference vs. Historical Verification

MarketForge distinguishes several kinds of specification evidence.

Two important inference methods are:

catalogue_inferred
reference_contract_inferred

Catalogue-inferred evidence

This records information inferred from retained catalogue observations under the supported policy.

Reference-contract-inferred evidence

This records information inherited from a compatible reference contract.

Why are these not historically verified?

Because the available evidence may not independently prove that the same specifications applied throughout the target archive's historical period.

For example, a reference contract observed today may share the target's current product conventions.

However, that does not automatically establish the target's exact historical contract value several years earlier.

What does operationally accepted mean?

The current project policy allows qualifying inferred evidence to be used operationally when its compatibility and applicability requirements are satisfied.

This makes it possible to prepare some historical processing work that would otherwise lack required metadata.

Does operational acceptance prove the inference is correct?

No.

The distinction should remain visible.

For example:

Evidence Interpretation
Historically verified Supported by applicable historical authority.
Historical declaration Explicitly supplied historical information.
Catalogue inferred Derived from retained catalogue evidence under policy.
Reference-contract inferred Derived from a compatible reference contract under policy.

The last two are operational inference methods.

They should not be presented as independent historical verification.

Inferred Applicability Intervals

Historical normalization requires specifications applicable to the processed source interval.

When MarketForge creates operational inference evidence, it records the assumed applicability interval.

What does the interval represent?

The current policy can assign an assumed interval covering the relevant registered inventory.

This makes the inferred specification operationally usable for the selected archive collection under the project's policy.

Does the interval prove historical validity?

No.

The interval is an explicit applicability assumption.

It is not proof that the exchange historically used the same specifications throughout the entire interval.

Why distinguish observation time?

The evidence also retains when its source information was actually observed.

For example:

Observation date:
November 2026

Assumed applicability:
Historical archive interval

These are different timestamps.

The observation time should not be rewritten to look as though the metadata was collected at the historical archive date.

Why is this important?

Otherwise, a current specification could appear to be a historical observation.

That would make later research and auditing misleading.

What Evidence Does Inference Preserve?

Historical inference records more than the resulting economic values.

The retained evidence includes information such as:

  • Source catalogue identities.
  • Source API identifiers.
  • Source snapshot hashes.
  • Inherited fields.
  • Inference policy version.
  • Applicability information.
  • Deterministic evidence fingerprints.

Why preserve this information?

Suppose a contract multiplier was inferred from a compatible reference.

Later, you discover a verified historical specification.

You need to know how the earlier value was obtained.

The retained evidence makes that interpretation traceable.

Why use fingerprints?

Fingerprints identify the relevant source evidence and interpretation.

For example, unchanged recollection of the same evidence can reuse the corresponding immutable revision.

If the source metadata or applicability changes, MarketForge can append a new revision.

Does updating current metadata overwrite historical evidence?

Not automatically.

The historical evidence store is append-oriented and preserves immutable revisions.

This allows MarketForge to retain the history of the information used for previous processing decisions.

Does a new revision silently replace an explicit declaration?

No.

Conflicting explicit historical declarations remain authoritative conflicts that must be resolved.

Futures Families and Archive Identity

Why Are Futures Families Difficult?

Some historical derivative archives contain several concrete contracts.

For example, a dated-futures family may include:

BTC-USD Contract A
BTC-USD Contract B
BTC-USD Contract C

Each contract has its own expiration and canonical instrument identity.

However, the archive provider may distribute their records together.

Why is this difficult?

The archive filename may identify only the family.

For example:

BTC-USD

This does not identify every concrete contract represented inside the file.

MarketForge needs additional source-native identity evidence.

What does family membership mean?

A family membership describes which concrete instruments are associated with a particular source family.

For example:

BTC-USD Family
      |
      +-- BTC Contract A
      +-- BTC Contract B
      +-- BTC Contract C

Does a current family listing prove historical completeness?

No.

A current exchange API may omit expired contracts.

An archive may also contain historical instruments not present in the current catalogue.

Therefore, the current family population is not automatically a complete historical record.

Catalogue vs. Archive-Derived Family Membership

MarketForge retains different sources of family membership evidence.

Catalogue membership

This comes from the retained instrument catalogue.

For example, current exchange metadata may identify several related contracts.

Archive-derived membership

This comes from supported identity discovery performed against registered historical archive contents.

Why retain both?

Because current metadata and historical archives can describe different instrument populations.

For example:

Current catalogue:
Contract B
Contract C

Historical archive:
Contract A
Contract B

The example is illustrative.

The current catalogue does not automatically prove that Contract A never existed.

Likewise, discovering Contract A in an archive does not establish that every historical contract has been discovered.

Does MarketForge merge the two into one complete authority?

It retains the relevant evidence and identity mappings under the supported policy.

However, it does not claim that the resulting family membership is historically exhaustive.

OKX Historical Instrument Discovery

OKX provides an important example of family-based historical data.

Perpetual archives

For supported OKX perpetual archives, MarketForge uses the relevant source-native instrument identity.

Dated futures

Dated-futures archive bundles may contain several concrete contracts.

MarketForge can perform bounded identity discovery using the production Rust Engine.

Why use Rust for discovery?

The archive may contain substantial data.

The Engine has the source-format processing capabilities needed to inspect the supported native instrument identities.

Current discovery limits

The documented bounds are:

Limit Value
Maximum bytes inspected per managed copy 256 MiB
Maximum discovery time 180 seconds

These limits constrain the discovery operation.

Does discovery read the entire archive?

Not necessarily.

The byte and time budgets can prevent full inspection.

Does discovering several contracts prove that no others exist?

No.

A bounded scan can establish observed identities.

It cannot guarantee that every historical contract appears within the inspected portion.

Why is this still useful?

It can identify concrete instruments represented by a registered family archive without requiring every contract to remain listed in the current exchange API.

This provides additional historical identity evidence for normalization preparation.

Historical Identity Discovery Caching

Archive identity discovery can be expensive.

MarketForge therefore caches supported discovery results.

What identifies a cached result?

The cache uses information including:

  • Managed copy checksum.
  • Compiled profile fingerprint.
  • Inference policy.

Why use these values?

A discovery result depends on both the source bytes and how those bytes are interpreted.

For example, changing the source profile may change which native instrument fields are decoded.

Similarly, changing the archive contents may change the observed instrument population.

When can a cached result be reused?

When the relevant source bytes, compiled interpretation, and policy identity remain compatible with the cached evidence.

What if the archive changes?

A changed copy checksum requires the discovery result to be reconsidered.

What if the profile changes?

A different compiled profile fingerprint can require rediscovery.

What if the inference policy changes?

The discovery evidence must be evaluated under the appropriate policy version.

Does cached discovery create normalized datasets?

No.

Identity discovery produces metadata evidence.

It does not publish normalized Parquet datasets.

Does discovery remove expired instruments?

No.

The historical identity infrastructure retains relevant inactive and expired catalogue entries.

Archive-discovered expired identities can receive stable canonical mappings.

Options and Historical Metadata

What About Options?

Options require additional instrument-specific information.

For example:

  • Underlying asset.
  • Expiration date.
  • Strike price.
  • Call or put classification.
  • Contract value.
  • Settlement convention.

These properties distinguish individual option contracts.

Why can't MarketForge infer everything from the base asset?

Because one underlying can have many options.

For example:

BTC Call
BTC Put
Different strikes
Different expirations

These are separate instruments.

What can the inference policy preserve?

The historical specification inference mechanism preserves available option identity fields.

It does not fabricate missing strike prices, expirations, or underlying identities.

Are options fully supported for normalization?

Not currently.

The existing Rust offline catalogue and installed normalization profiles do not provide general options-normalization support.

Important distinction: acquisition vs. current-market collection

The current mf markets sync collection adapters omit options.

However, certain historical acquisition adapters support options archive discovery.

For example, the separate historical acquisition subsystem supports relevant Bybit and OKX options archive selections.

These are different capabilities.

Being able to obtain an options archive does not mean MarketForge can already normalize its contents.

What happens when required options support is missing?

Initialization and preparation report the applicable limitation.

They do not invent missing instrument identity or Engine support.

Initialization and Historical Readiness

Historical Evidence Storage

The historical metadata system uses immutable evidence records.

The relevant database support was introduced through migration 0014.

Why retain evidence separately?

MarketForge needs to distinguish:

  • Current catalogue observations.
  • Explicit historical declarations.
  • Inferred historical specifications.
  • Family membership evidence.
  • Archive-derived identity information.

These records have different meanings and levels of authority.

Does this create a second raw-data registry?

No.

The evidence tables are not a replacement for the managed raw-data registry.

Raw archives remain tracked through the existing acquisition and storage infrastructure.

Does this replace current catalogue observations?

No.

Current observations remain useful for market discovery, statistics, and reference metadata.

Historical evidence adds information needed to interpret older registered recordings.

Why preserve immutable revisions?

Because financial-data processing should remain traceable.

If the source evidence changes, the new interpretation should not silently erase the information used for earlier work.
