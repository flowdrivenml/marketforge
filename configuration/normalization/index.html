Normalization recipes

A normalization recipe selects registered archives and metadata for Forge to prepare. Its generated Engine input has a separate batch contract. Use the normalization guide to validate, prepare, execute and recover registration.

Editable recipe

A managed name resolves under data/.config/workflows/data_engineering/normalization/. Validate and prepare also accept explicit TOML paths. Forge can prepare from a modern acquisition recipe with compatible requests. The Bybit example selects both supported data types. Unknown fields are rejected.

Path Accepted type Requirement and behavior
version Integer 1 Optional, defaults to 1
interval.start, interval.end TOML offset datetimes Both required. Start precedes end. The request is half-open
requests Array of tables Required, nonempty. Shared fields and feed options follow acquisition requests
requests[].instrument_type spot, perpetual, future, option, equity Required. Equity must also use the equity market category
requests[].market_category spot, linear, inverse, option, equity Required. Equity must also use the equity instrument type
requests[].source_key Nonempty string without whitespace Required for equity, otherwise optional. Requires an instrument scope and an applicable registered source
ranking_policy Token matching ^[a-zA-Z0-9_-]+$ Defaults to turnover. Used when ranks need a ranking snapshot

Selections apply to whole inputs. Preparation checks archive provenance, local integrity, profiles, historical specification applicability and coverage. A successful structure check can be followed by a blocked preparation. For current policy and settings, see historical metadata inference and runtime policies.

Legacy file-ID preparation

Forge can still load the explicit legacy request documented below. Source-derived merge and conversion require modern retained request evidence where specified by their own recipe contracts.

Source Key Requirements

The source_key field is optional for the general normalization recipe.

When supplied, it must be:

  • Nonempty.
  • Free of whitespace.
  • Associated with the intended registered source.

For example:

source_key = "synthetic-equity"

is valid.

Why must source-key selections use instrument scope?

When a source key is supplied, the request must use a concrete instrument scope.

For example:

source_key = "synthetic-equity"

[requests.scope]
kind = "instrument"
identifier = "AAPL"

This is supported.

However, a source-key request using family scope is rejected by the current recipe validator.

Why enforce this?

The source-key selection identifies a concrete registered external source.

The current normalization recipe contract requires that source to be associated with an explicit instrument selection.

This avoids ambiguity between external source identity and provider-native family grouping.

Does source key replace the exchange?

No.

You still need to declare the actual market identity.

For example:

exchange = "example_exchange"
source_key = "synthetic-equity"

The exchange describes where the instrument belongs.

The source key identifies the registered recording collection.

Complete External Equity Recipe

The repository includes a synthetic AAPL example.

Its normalization recipe is located at:

docs/content/examples/catalogue/normalization.toml

The example uses a fictional execution venue and explicitly declared synthetic market specifications.

The following is a complete recipe:

version = 1

[interval]
start = 2024-10-28T00:00:00Z
end = 2024-10-29T00:00:00Z

[[requests]]
exchange = "example_exchange"
instrument_type = "equity"
market_category = "equity"
data_type = "trades"
source_key = "synthetic-equity"

[requests.scope]
kind = "instrument"
identifier = "AAPL"

[[requests]]
exchange = "example_exchange"
instrument_type = "equity"
market_category = "equity"
data_type = "order_book_l2"
source_key = "synthetic-equity"

[requests.scope]
kind = "instrument"
identifier = "AAPL"

What does this request?

It selects:

Property Value
Exchange Example Exchange
Instrument AAPL
Instrument type Equity
Market category Equity
Source key synthetic-equity
Content Trades and L2 depth
Interval October 28, 2024

What are the prerequisites?

The synthetic example requires:

  • Registered Example Exchange.
  • Registered AAPL instrument.
  • Applicable historical specifications.
  • Installed trade profile.
  • Installed depth profile.
  • Registered synthetic raw recordings.

Does the recipe create these prerequisites?

No.

The recipe only selects existing registered inputs.

Complete the catalogue, profile, and raw-registration steps before preparing normalization.

See Synthetic Trade and Depth Recordings.

How Stream Ranks Are Assigned

Suppose a normalization recipe selects three instruments.

A published turnover ranking might contain:

Instrument Stored position
BTCUSDT 1
ETHUSDT 2
SOLUSDT 3

Forge can use these positions when ordering the requested streams.

Are stored positions copied directly into Engine ranks?

Not necessarily.

The stored ranking positions provide ordering evidence.

Forge constructs dense stream ranks for the selected processing work.

For example:

Selected streams:
BTCUSDT
SOLUSDT

Even if their stored ranking positions are 1 and 3, the generated stream ranks can be:

BTCUSDT → 1
SOLUSDT → 2

The generated ranks describe the selected workload.

What happens when an instrument is not ranked?

The current preparation logic can fall back to deterministic stream identity ordering for unranked streams.

This avoids requiring every registered instrument to appear in a market ranking.

What if no published ranking exists?

Forge can use deterministic stream identity order.

For example:

Stream A
Stream B
Stream C

can be ordered using their stable identities.

Why is determinism important?

A processing request should not produce arbitrary stream ordering merely because PostgreSQL returns rows in a different order.

Deterministic ranks help make the prepared execution contract consistent.

Does stream rank change event timestamps?

No.

A stream rank is ordering metadata.

It does not change the original recorded event timestamps.

Does a higher market ranking mean higher event priority?

Not in the sense of overriding source integrity or chronology.

Ranking positions are used by the supported stream-ordering contract.

They do not authorize arbitrary rearrangement of order-book updates or other stateful source events.

Family-scoped archives

Family archives may contain several concrete instruments.

Their source-stream ranking and later concrete stream expansion require the appropriate Engine identity resolution.

Do not assume a family rank automatically establishes every individual contract's final stream order.

Nominal Coverage Checks

Preparation evaluates the recorded coverage of the selected raw inputs.

For example, suppose you request:

October 27 ───────────────── October 30

But the registered archives cover:

October 27 ── October 28

October 29 ── October 30

October 28 is not represented by the selected nominal intervals.

Forge can report a coverage gap.

Why does this block preparation?

The requested processing period may not have the required registered source coverage.

Silently executing an incomplete selection could produce a dataset that appears to represent a complete requested interval.

MarketForge therefore reports nominal gaps as blockers under the current preparation rules.

Does nominal coverage prove every event exists?

No.

For example, a registered daily archive can nominally cover:

October 27 00:00 ── October 28 00:00

while containing missing events inside that interval.

The declared archive coverage does not prove uninterrupted market-data capture.

Two different questions

Nominal coverage

Do the registered source intervals cover the requested selection?

Event completeness

Does the source actually contain every event that should exist?

These are not equivalent.

Normalization can detect some source-level problems through its processing and integrity rules, but a nominally complete archive inventory is not proof of complete historical market activity.

Legacy Request Structure

A legacy preparation request contains:

  • Job ID.
  • Dataset ID.
  • Content type.
  • One or more explicit inputs.
  • Optional output paths.
  • Optional ranking policy.

Example

version = 1

job_id = 123456
dataset_id = 123457

content_type = "trades"
ranking_policy = "turnover"

[[inputs]]
task_id = 1

archive_id = 72
instrument_id = 18

This is an illustrative legacy declaration.

The IDs are placeholders representing positive integers.

They must be replaced with valid registered identities appropriate to the intended testing workspace.

Does this example guarantee successful preparation?

No.

The referenced archive and instrument IDs must actually exist and satisfy the required source and historical interpretation checks.

The job and dataset IDs must also satisfy the applicable identity and collision constraints.

Are these IDs allocated automatically?

No.

Legacy explicit preparation requests require the relevant IDs to be supplied.

They are not automatically allocated or reserved in PostgreSQL merely because the TOML file contains them.

Why is this risky?

Manually selecting numeric IDs can create conflicts or reference the wrong records.

For ordinary workflows, use scoped recipes and let Forge construct the appropriate processing identities.

Legacy Request Parameters

The legacy request schema supports the following fields.

Top-level fields

Field Requirement Meaning
version Optional; defaults to 1 Legacy request version.
job_id Required positive unsigned 64-bit integer Job identity.
dataset_id Required positive unsigned 64-bit integer Engine dataset identity.
content_type Required trades or depth.
ranking_policy Optional; defaults to turnover Ranking policy name.
[[inputs]] Required nonempty array Explicit source selections.
[output] Optional Explicit staging and final output paths.

Input fields

Field Requirement Meaning
task_id Required positive unsigned 64-bit integer Task identity.
archive_id Required positive signed 64-bit integer Registered local archive ID.
instrument_id Required positive signed 64-bit integer Canonical instrument ID.
format_profile Optional Legacy profile reference.
archive_member Optional Selected archive member.
source_compression Optional Source compression format.
stream_rank Optional unsigned 32-bit integer Explicit stream rank.

Accepted compression values

plain
gzip
zip
tar_gzip

Why are task IDs unique?

Each task identifies one selected unit of source work.

Duplicate task IDs would make the task structure ambiguous.

The legacy request validator therefore requires unique task IDs.

Can the same archive appear twice?

The same archive/member pair may appear only once.

For example, these two inputs conflict if they select the same archive and member:

[[inputs]]
task_id = 1
archive_id = 72
instrument_id = 18

[[inputs]]
task_id = 2
archive_id = 72
instrument_id = 18

A different archive member may be a distinct selection when the source and processing contract support it.

Do legacy profile fields override the modern profile catalogue?

Do not assume so.

The current preparation path delegates source interpretation to the supported Engine and registered metadata mechanisms.

Legacy fields remain readable, but they are not a general replacement for the modern profile and registration workflow.

Legacy Output Paths

Legacy requests can explicitly configure output destinations.

For example:

[output]
staging_path = "data/datasets/normalized/.123457.staging.123456"
dataset_path = "data/datasets/normalized/123457"

These are illustrative paths.

They must be appropriate for the actual workspace and must not already contain an existing publication.

What is the staging path?

The staging path is used while Engine constructs the output.

The resulting dataset is not treated as committed merely because some files exist in staging.

What is the dataset path?

The dataset path is the intended final publication location.

After successful processing and publication validation, Engine commits the output to that destination.

Why must paths be separate?

The Engine needs to distinguish temporary processing output from the final publication.

For example:

Staging:

data/datasets/normalized/.123457.staging.123456


Committed:

data/datasets/normalized/123457

Why must they share a parent?

The supported atomic publication procedure requires staging and final destinations to share a parent directory.

This allows the final publication step to use the appropriate filesystem rename semantics.

Can I overwrite an existing dataset?

No.

The supported preparation checks require fresh destinations.

Existing committed publications should not be silently replaced.

Do I need explicit output paths in new recipes?

No.

The scoped normalization workflow generates the appropriate output destinations.

For new workflows, prefer automatic preparation rather than legacy output overrides.
